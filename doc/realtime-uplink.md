# 실시간 경로 — ESP-NOW 업링크 + USB 싱크

> 상태: **CURRENT** (1-RX 실보드 검증 완료 2026-09-02, 3-RX 5보드 구성 실측 2026-09-10)
> firmware: `esp32s3_csi_recv_poc` (`CSI_UPLINK_ENABLED=1`) · `esp32s3_csi_sink`

학습 데이터 수집은 RX 를 USB 로 직결하지만, 실시간 분류는 RX 를 방 안에 흩어 놓아야 한다.
RX 는 호스트 연결이 없으면 데이터를 버리므로(링버퍼 4초) 무선 업링크가 필요하다.

```text
TX ──ESP-NOW 10ms 자극──▶ RX × N ──ESP-NOW 업링크──▶ SINK ──USB──▶ Mac
   (전원만)                (전원만)                    (유일한 USB 연결)
```

## 왜 싱크 보드가 따로 필요한가

맥북 Wi-Fi 로는 RX 의 업링크를 받을 수 없다 — ESP-NOW 는 Espressif 독자 프로토콜이라
일반 Wi-Fi 클라이언트가 해석하지 못한다. RX 를 일반 Wi-Fi 로 붙여 UDP 를 쓰는 경로는
association + DTIM 게이팅 때문에 22Hz 천장에 막혀 폐기했다
([ADR-0001](adr-poc-only.md), [troubleshooting/01-csi-rate.md](troubleshooting/01-csi-rate.md)).

**싱크는 RX 를 겸할 수 있다.** 어차피 USB 로 붙어 있으니 자기 CSI 도 함께 흘려보내면
된다. 그러면 필요한 보드는 N+2 가 아니라 **N+1** 이다.

## 역할별 MAC

모두 같은 MAC 을 쓰면 RX 가 송신을 시작하는 순간 서로의 업링크를 CSI 로 잡아 자기오염된다.

| 역할 | STA MAC | 비고 |
|---|---|---|
| TX | `1a:00:00:00:00:00` | **RX 의 CSI 필터 기준** — 이 MAC 의 프레임만 CSI 로 통과 |
| RX | `1a:00:00:00:00:<id>` | `CSI_RX_ID` (1~254), 보드마다 달라야 한다 |
| SINK | `1a:00:00:00:00:ff` | RX 가 unicast 로 보내는 주소 |

RX 의 CSI 필터는 TX MAC 에만 걸려 있어, 자기 업링크나 다른 RX 의 업링크·싱크의 ACK 는
CSI 로 잡히지 않는다.

## 프레임은 그대로 흘러간다

싱크는 프레임을 **해석하지 않고 그대로 전달한다.** RX 가 만든 v4 프레임(CRC 포함)이
host 까지 무손상으로 도달하는지 검증할 수 있고, host 파서가 USB 직결과 완전히 같다
(`scripts/csi_store.py`). 프레임 규격이 바뀌어도 싱크는 고칠 게 없다.

따라서 **수집 도구가 그대로 쓰인다** — reader 는 싱크 포트를 RX 인 것처럼 읽는다.
RX 가 보내는 IDENT 도 그대로 전달되므로 `device_id` 자동 식별도 동작한다.

### 싱크는 TX 자극을 걸러야 한다

같은 채널에는 RX 업링크만 오는 게 아니다 — TX 의 자극 broadcast(4바이트 카운터)도
같이 들어온다. 그대로 흘려보내면 프레임 사이에 4바이트가 끼어 host 가 매 프레임
재동기화한다. 싱크는 프레임 서명(magic + version)으로 우리 프레임만 통과시키고,
나머지는 `foreign` 으로 센다.

## 빌드·플래시

```bash
# SINK (registry 등록 불필요 — device_id 를 쓰지 않는다)
cd esp32s3_csi_sink && idf.py set-target esp32s3 && idf.py -p <포트> flash

# RX 업링크 모드 (보드마다 CSI_RX_ID 를 다르게, 오프셋은 rx_id × OFFSET_MS 로 자동 분산)
cd esp32s3_csi_recv_poc
idf.py -DCSI_UPLINK_ENABLED=1 -DCSI_RX_ID=1 -DCSI_UPLINK_OFFSET_MS=4 -p <포트> flash

# RX 를 학습 수집(USB)으로 되돌리려면
idf.py -DCSI_UPLINK_ENABLED=0 -p <포트> flash
```

업링크 모드에서 RX 는 **USB-Serial-JTAG 드라이버를 아예 설치하지 않는다** — USB 로
데이터를 내보내지 않는다. USB 는 플래시·전원 용도로만 쓴다.

다만 그 덕에 콘솔 secondary 경로가 비어 있어, 업링크 RX 의 USB 포트에는 **5초 진단 로그가
텍스트로 나온다**: `5s: cb=… (+…, 99.4Hz) uplink_ok=… fail=… ringbuf_drop=…`.
싱크 없이도 그 RX 의 CSI 콜백률과 업링크 성공률을 바로 볼 수 있다 (`screen`/`cat` 으로 충분).
`fail=0` 이면 싱크가 켜져 ACK 하고 있다는 뜻이다.

## 수집

싱크 포트를 평소처럼 읽으면 된다.

```bash
python scripts/csi_serial_reader.py --port <싱크 포트> --session-dir <세션>
python scripts/measure_csi_hz.py <세션>
```

## 실측 (2026-09-02, TX1 + RX103 + SINK(RX101), 60초)

TX 는 외부 전원, RX 는 USB 전원만(데이터 경로 미사용), 싱크만 데이터 연결.

```text
device_103.csi: n=5973 hz=99.58 median_dt=10.0ms gaps>200ms=0
      seq_gap=0 tx_back=0 tx_cov=0.996 rssi_med=-24 agc_levels=22
reader        : crc_fail=0 invalid=0 resync=0
RX 펌웨어     : csi_cb=5775 uplink_ok=5804 uplink_fail=0 ringbuf_drop=0
```

- **업링크 성공률 100%** (`uplink_fail=0`), 링버퍼 드롭 0
- **호스트 도달률 손실 0%** (`seq_gap=0`)
- **업링크가 CSI 수신을 방해하지 않는다** — 콜백 ~99Hz 로 USB 직결(~99Hz)과 같다.
  RX 가 송신하는 동안 반이중이라 못 듣는 시간은 100Hz × ~300µs ≈ 3% 인데, 실측상
  구분되지 않는다.

### 에어타임 여유

프레임 172B 를 MCS0 로 보내면 패킷당 약 450µs (프리앰블·백오프·ACK 포함) → RX 1대당
약 4.5%. RX 3대 + TX 자극이면 총 ~18% 로 여유가 있다. 다만 **RX 를 늘렸을 때도
CSI 콜백률이 유지되는지는 아직 미검증**이다 (현재 RX 1대로만 확인).

## 다중 RX — host demux

> 상태: **CURRENT** (host 측은 pty 로 검증, 실보드 다중 RX 는 미검증)

RX 는 업링크 모드에서 헤더 `rx_id` 에 `CSI_RX_ID` 를 찍는다. reader 는 한 포트 위의
프레임을 `rx_id` 로 갈라 RX 마다 `RxStream` 을 두고, 각 RX 의 IDENT(MAC)로 `device_id`
를 정해 `device_<id>.csi` 를 따로 쓴다. USB 직결은 `rx_id=0` 스트림 하나뿐인 특수 경우다.

pty 검증: RX 2대(rx_id 1·2)의 프레임을 한 포트에 교대로 흘렸을 때
`device_101.csi` / `device_103.csi` 로 분리되고 각각 `seq` 연속, USB 직결 회귀 없음.

## 다중 RX 실측 (2026-09-03)

TX(외부) + RX103(외부, 업링크) + RX102(업링크 rx_id=2) → SINK, 60초 × 3회:

```text
RX102: 99.8Hz seq_gap=0          RX103: 93.0Hz seq_gap≈400 (~7%)
싱크: drop=0 usb_timeout=0 foreign≈96Hz     cross-RX 공통 tx_seq 99.5%
```

**CSI 콜백률은 유지된다**(두 RX 모두 `csi_cb`≈5770/60s). 손실은 CSI 수신이 아니라
**업링크 수신 쪽** — RX 는 ACK 를 받아 성공으로 셌는데 싱크 `recv_cb` 에 안 온 프레임이
~7%. 두 RX 의 위치를 맞바꾸니 손실이 **싱크에서 먼 쪽을 따라갔다** (보드 무관).
업링크를 1대로 줄이면 0. 상세와 완화 후보는
[troubleshooting/08](troubleshooting/08-wireless-uplink.md).

## 3-RX 오프셋 3ms 실측 (2026-09-10)

> 상태: **CURRENT** (5보드 구성 실보드 검증 완료 — TX 1 + RX 3 + SINK 1)

5번째 보드를 확보해 목표 구성을 채웠다. SINK 는 신규 보드, RX 는 RX101(`rx_id=1`)·
RX103(`rx_id=2`)·RX102(`rx_id=3`) — 모두 `CSI_UPLINK_OFFSET_MS=3` (오프셋 3/6/9ms, 10ms
주기 안에 들어옴). 60초 수집:

```text
device_101.csi (rx_id=1, offset 3ms): 98.95Hz tx_cov=0.989 seq_gap=0
device_103.csi (rx_id=2, offset 6ms): 97.59Hz tx_cov=0.973 seq_gap=5
device_102.csi (rx_id=3, offset 9ms): 93.37Hz tx_cov=0.932 seq_gap=1
cross-RX 공통 tx_seq: 97.2% (5439 / 최소 RX 5596)
crc_fail=0 invalid=0 (전 RX)
```

- **RX 3대 모두 손실 발생** — 2-RX 실측(0/0.07%)과 달리 3대로 늘리자 손실이 뚜렷해졌다.
  가장 큰 손실(6.8%)이 오프셋 9ms(`rx_id=3`) 에서 났다 — 10ms 주기 경계에 가장 가깝다는
  우려가 실측으로 확인됐다.
- 원인 후보를 아직 좁히지 못했다: 오프셋 자체(9ms 가 다음 주기 3ms 와 너무 가까워
  충돌) 인지, 단순히 RX 3대의 총 에어타임(~18%, §에어타임 여유) 증가인지 구분되지
  않는다. `rx_id` ↔ 오프셋을 맞바꿔 재실측하면 위치(자리)효과인지 오프셋 값 자체의
  효과인지 가를 수 있다.
- **거리 조건이 이전 실측과 다르다.** 2-RX 0/0.07% 실측은 싱크 30cm 이내 근접
  배치였는데, 이번은 RX 를 싱크에서 1m ~ 3m 로 떨어뜨렸다. 최선인 rx_id=1 도 1.1%
  손실이 나 근접 실측보다 전반적으로 높다 — 거리에 따른 RSSI 저하가 오프셋·에어타임과
  별개로 기여했을 수 있다. 오프셋 값 / RX 대수 / 거리, 세 변수가 얽혀 이번 실측만으로는
  분리되지 않는다.

### 위치만 바꿔 재실측 (2026-09-10, rx_id/오프셋은 그대로)

`rx_id`↔오프셋 배정은 그대로 두고 RX 3대의 **물리적 자리만 서로 바꿔** 60초 재수집
(세션 `raw/20260910/223102_empty_s23`):

```text
device_101.csi (rx_id=1, 3ms): 99.25Hz tx_cov=0.992 rssi_med=-30  (이전 0.989, RSSI-37)
device_103.csi (rx_id=2, 6ms): 98.43Hz tx_cov=0.984 rssi_med=-30  (이전 0.973, RSSI-34)
device_102.csi (rx_id=3, 9ms): 92.27Hz tx_cov=0.922 rssi_med=-40  (이전 0.932, RSSI-40)
cross-RX 공통 tx_seq: 98.3% (이전 97.2%)
```

RX101·RX103 은 RSSI 가 좋아지며(−37/−34 → −30/−30) 손실도 줄었는데, **RX102(rx_id=3,
9ms)만 RSSI(−40)와 손실률(6.8%→7.8%, 오히려 소폭 악화)이 거의 그대로다.** 자리를
바꿨는데도 가장 나쁜 오프셋(9ms)을 가진 보드가 계속 가장 나쁘다는 건 순수 위치 효과보다
**오프셋 값 자체**를 가리키는 정황이다.

다만 RX102 의 RSSI 가 두 실측에서 정확히 같게 나온 게 걸린다 — 자리가 실제로는 크게
안 바뀌었을 가능성이 있어 완전히 결론 내리긴 이르다. 가장 깨끗한 확인은 위치를 고정한
채 **`rx_id`(오프셋)만 재플래시로 맞바꾸는 것**이다.

### 위치를 한 번 더 바꿔 재실측 — 위 결론 정정 (2026-09-10)

`rx_id`/오프셋 배정은 그대로 두고 위치만 한 번 더 바꿔 60초 재수집(세션
`raw/20260910/223715_empty_s24`):

```text
device_101.csi (rx_id=1, 3ms): 92.60Hz tx_cov=0.925 rssi_med=-38  (1차 0.989/-37, 2차 0.992/-30)
device_103.csi (rx_id=2, 6ms): 98.12Hz tx_cov=0.980 rssi_med=-30  (1차 0.973/-34, 2차 0.984/-30)
device_102.csi (rx_id=3, 9ms): 96.40Hz tx_cov=0.964 rssi_med=-31  (1차 0.932/-40, 2차 0.922/-40)
cross-RX 공통 tx_seq: 97.2%
```

**위 "오프셋 값 자체가 원인" 결론은 틀렸다.** 가장 안전하다고 봤던 오프셋(3ms,
`rx_id=1`)의 RX101 이 이번엔 가장 나쁘다(7.5% 손실) — 직전 두 번 모두 가장 나빴던
RX102(9ms)는 오히려 3.6%로 개선됐다. 3회 전체를 RSSI 로 정렬하면:

```text
RSSI-30: 0.8%, 1.6%, 2.0%   RSSI-31: 3.6%   RSSI-34: 2.7%   RSSI-37: 1.1%   RSSI-38: 7.5%   RSSI-40: 6.8%, 7.8%
```

RSSI −30 근처는 항상 2% 이하, −40 근처는 항상 6% 이상으로 대체로 RSSI(위치)를
따라간다 — 오프셋 값이 아니라 **위치가 지배적**이라는 쪽이 맞다. 다만 RX101 의
RSSI−37(1.1%)과 RSSI−38(7.5%)이 손실은 7배 차이 나 RSSI만으로 완전히 설명되진
않는다 — `agc_levels`(1차 5 vs 3차 13)로 보아 페이딩 안정성 같은 다른 요인이
섞였을 수 있다. 오프셋 값 자체를 확인하려면 여전히 위치를 고정한 채 `rx_id` 재플래시
스왑이 필요하다.

### RX101↔RX102만 스왑, RX103 위치 고정 — 위치 가설도 흔들림 (2026-09-10)

RX103(`rx_id=2`, 6ms)은 이번엔 **위치를 옮기지 않고** RX101↔RX102 자리만 서로 바꿔
60초 재수집(세션 `raw/20260910/224106_empty_s25`):

```text
device_101.csi (rx_id=1, 3ms): 97.30Hz tx_cov=0.973 rssi_med=-41
device_102.csi (rx_id=3, 9ms): 95.21Hz tx_cov=0.952 rssi_med=-37
device_103.csi (rx_id=2, 6ms, 위치 고정): 91.95Hz tx_cov=0.919 rssi_med=-42
cross-RX 공통 tx_seq: 98.1%
```

이번에도 RX103 이 가장 나쁘다(8.1% 손실, RSSI −42).

### 원인 확정 — 방 안 특정 자리 하나 (2026-09-10, 운영자 확인)

4회에 걸쳐 "가장 나쁜 보드"가 매번 바뀌었다(RX102 → RX102 → RX101 → RX103) — 처음엔
오프셋값도, 순수 RSSI 도 이 패턴을 깔끔히 설명 못 해 혼란스러웠다. 그런데 운영자가
**"안 좋게 나온 건 매번 실제로 방 안 같은 한 자리에 있던 보드였다"**고 확인했다 —
즉 보드나 `rx_id`/오프셋이 바뀐 게 아니라, **그 한 자리에 어떤 보드를 두든 그 보드가
나쁘게 나온 것**이다. 4회의 "최악 보드"가 매번 달랐던 건 그 사이 보드들이 자리를
서로 바꿔가며 매번 다른 보드가 그 문제 자리에 앉았기 때문 — 오프셋값·RX 대수 가설을
반박한 것처럼 보였던 3·4차 결과가 사실은 **위치 가설과 완전히 일치**했던 것이다
(2-RX 때의 "손실이 싱크에서 먼 쪽을 따라간다"와 같은 종류의 현상).

**결론: 오프셋 값(3/6/9ms)이나 RX 대수가 아니라, 그 한 자리의 RF 환경(거리·장애물·
다중경로)이 원인이다.** 다음 조치는 보드/오프셋 스왑이 아니라 **그 자리 자체를
조사**하는 것 — 싱크와의 거리·시야선(LOS) 차단 여부·주변 금속/벽 확인, 필요하면
그 자리를 피하거나 안테나 방향을 조정한다.

### 그 자리를 피해 재배치 — "방 안 자리" 결론도 반박됨 (2026-09-10)

문제 자리로 지목된 곳을 피해 재배치하고 60초 재수집(세션 `raw/20260910/225621_empty_s26`):


자리를 피했는데도 **RX103 이 또 가장 나쁘다** (8.7% 손실, RSSI −44 — 전체 실측 중
최악치). "방 안 특정 자리" 결론도 이걸로 반박된다 — 남은 후보는 RX103 **보드 자체**
(안테나·하드웨어) 아니면 아직 못 찾은 다른 변수다.

### TX 재배치 + 싱크 90도 회전 — 최고 결과 (2026-09-10)

TX 위치를 바꾸고 **싱크 보드를 90도로 세운** 뒤 60초 재수집(세션
`raw/20260910/230050_empty_s27`):

```text
device_101.csi (rx_id=1): 99.21Hz tx_cov=0.992 rssi_med=-34
device_102.csi (rx_id=3): 97.28Hz tx_cov=0.972 rssi_med=-32
device_103.csi (rx_id=2): 97.09Hz tx_cov=0.971 rssi_med=-33
cross-RX 공통 tx_seq: 97.2%
```

지금까지 중 가장 좋고 고른 결과다 — 손실 0.8~2.9%, RSSI 가 −32~−34 로 RX 세 대가
전부 좁게 모였다(이전엔 −30~−44 로 보드마다 크게 갈렸다). 계속 최악이었던 RX103 도
8.7%→2.9%로 크게 개선됐다. **싱크 안테나 방향(편파)이 원인이었을 가능성이 높다** —
방향이 안 맞으면 RX 의 상대 방위각에 따라 편파 손실이 갈리는데, 90도로 돌리자 세 RX
모두에 고르게 맞아떨어진 것과 일치한다.

TX 위치도 동시에 바꿔 두 변경이 섞여 있어 싱크 회전만의 효과라고 확정할 수는 없다.
다만 이 구성이 지금까지의 모든 배치·오프셋 조합 중 최선이므로, **이 배치를 파일럿
기준 구성 후보로 채택**하고 필요하면 싱크 회전 단독 효과는 나중에 별도로 검증한다.

## 남은 일

- **싱크 회전 단독 효과 검증** — TX 위치는 그대로 두고 싱크 방향만 원위치/90도를
  오가며 재실측해야 위 최고 결과가 회전 때문인지 TX 재배치 때문인지 분리된다.
- **3-RX 손실 원인 분리** — 오프셋 값(9ms 가 경계에 가까움) vs RX 대수(에어타임) 중
  무엇이 지배적인지 `rx_id`/오프셋 재배치로 확인. (위 최신 실측으로 보아 안테나
  방향·위치 쪽이 더 지배적일 가능성이 높아졌다.)
- ~~2-RX 동시 업링크 손실~~ — **송신 시점 분산으로 해결** (`CSI_UPLINK_OFFSET_MS`, RX 당
  `rx_id × 4ms`). 7.6% → 0.0% (2ms 는 1.05%, 부족; rx_id=2 의 8ms 도 손실 0).
- **싱크의 RX 겸용**: 싱크가 자기 CSI 도 함께 흘려보내면 보드 1대를 아낀다.
- **실시간 추론 훅**: 현재는 파일 저장까지다. 슬라이딩 윈도를 모델에 넘기는 경로는 없다.
