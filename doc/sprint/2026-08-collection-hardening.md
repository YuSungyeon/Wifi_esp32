# 스프린트: 수집 환경 정비 — 라벨·무결성·저장 포맷 (2026-08-25 ~ )

> 상태: **HISTORICAL** — 시간순 작업 일지. **트러블슈팅을 종류별로 찾으려면
> [troubleshooting/](../troubleshooting/README.md)** 를 본다 (이 일지를 종류별로 재정리한 것).

USB 수집 파이프라인을 "학습에 실제로 쓸 수 있는 데이터"를 뽑는 상태로 만드는 스프린트.
기록 포맷은 [troubleshooting/01-csi-rate.md](../troubleshooting/01-csi-rate.md)와 동일한
**문제 → 가설 → 시도 → 기대값 → 실제 결과 → 다음 조치** 6단 구조.

기록 규칙:
- 수치는 반드시 실측을 적는다. "개선됨"이 아니라 `hz=100.94 → 100.91, crc_fail=0`.
- 펌웨어를 건드린 시도는 **어느 보드에서 언제 측정했는지**까지 적는다
  (같은 문서 §10에 발열로 측정값이 오염된 전례가 있다).
- 되돌린 변경도 지우지 말고 "되돌림" 상태로 남긴다.

## 배경 — 왜 이 스프린트가 필요했나

시작 전제는 "유선·무선 둘 다 Hz가 낮다"였는데, **USB 경로는 이미 100Hz를 내고 있었다.**
저장된 세션을 직접 재측정한 결과:

| 세션 | hz | median_dt | gaps>200ms |
|---|---|---|---|
| `raw/20260615/session_21` dev101 | 100.94 | 10.0ms | 0.0% |
| `raw/20260615/session_21` dev103 | 100.84 | 10.0ms | 0.0% |
| `raw/20260616/session_4` dev102 | 102.59 | 10.0ms | 0.1% |

반면 AP(SoftAP+UDP) 경로는 저장된 12개 세션 전부 **0.18 ~ 22.8Hz**, `tx_seq` 유효 레코드
**0건**. 원인은 [troubleshooting/01-csi-rate.md](../troubleshooting/01-csi-rate.md)에
11단계로 기록되어 있고 결론은 "AP/STA association + DTIM 게이팅 + 자극/데이터 채널 공유".

**진짜 문제는 Hz가 아니라 모은 데이터를 학습에 쓸 수 없다는 점이었다.** 조사에서 확인한 사실:

1. **라벨이 어디에도 기록되지 않는다.** `Preprocessing.py --label`이 유일한 입력이고 기본값
   `empty`. 수집 시점에는 라벨이라는 개념 자체가 없다.
2. **같은 `session_id`로 재수집하면 JSONL에 append된다** (`csi_serial_reader.py:134`,
   `open("a")`). 실제로 오염됐다 — `20260615/session_21/device_101.jsonl`은 100번째 줄에서
   `seq 158 → 0`으로 되감기고, `20260523/session_15`는 `sample_count` 192와 128이 한 파일에
   섞여 있다. 위 표의 "깨끗한 100Hz 세션"들도 실은 두 런이 붙은 파일이다.
3. **수집 시작 직전 CLI가 모든 보드를 리셋한다.** `_detect_rx_boards`가 포트마다
   `esptool read_mac`을 돌리는데 esptool은 DTR/RTS로 칩을 부트로더에 넣었다 hard reset 한다.
   TX가 꽂혀 있으면 TX도 리셋되어 `tx_seq`가 0으로 되감긴다 — cross-RX 정렬 키가 끊긴다.
4. **오탐 프레임이 검증 없이 저장된다.** raw CSI 안의 우연한 `0x53 0x43`을 magic으로 오인한
   레코드가 실제로 있다 (`20260523/session_1` 첫 줄: `channel=159`, `rssi=+11dBm`,
   `timestamp_us`가 u64 초과). 유일한 검증이 `raw_len > 4096`뿐이었다.
5. **`csi_amp[:52]` 중 12개가 항상 0이다.** LLTF 64 서브캐리어에서 인덱스 0(DC)과 27~37
   (가드)이 상시 0인 것을 실측 확인. 현재 코드는 이 12개를 모델 입력에 넣고 실제 데이터인
   인덱스 52~63을 버린다 → **feature의 23%가 상수 0, 유효 톤의 23%가 유실.**
6. **위상이 수집 시점에 영구 폐기된다.** raw int8 I/Q를 `sqrt(I²+Q²)` float으로 바꿔 저장하고
   원본을 버린다. 덤으로 레코드가 1243B로 부풀어 실정보량(160B)의 8.4배.
7. **다중 세션 학습 경로가 없다.** `LSTM.py`는 세션 1개를 단일 라벨로 학습 — `y`가 전부 같은
   값이라 3-class 학습이 성립하지 않는다.

## 작업 로그

### 1. 시리얼 프레임 v3 — 상태: 완료 (이후 작업 13에서 v4로)

- **문제**: 프레임 검증이 magic 2바이트 + `raw_len > 4096` 뿐이라 raw CSI 안의 우연한
  `0x53 0x43`이 헤더로 오인됐다. `20260523/session_1` 첫 줄에 `channel=159`, `rssi=+11dBm`,
  `timestamp_us`가 u64를 넘는 레코드가 남아 있다. 또 진폭 float 저장이 위상을 버리고 파일을
  8배로 부풀렸다.
- **가설**: CRC32를 넣으면 오탐이 결정적으로 걸러지고, raw I/Q를 그대로 저장하면 위상 보존과
  용량 절감을 동시에 얻는다.
- **시도**: `csi_frame_header_t`를 32B v2 → **40B v3**으로 확장.
  `frame_type`(`reserved0` 자리), `boot_id`(`reserved1` 자리), `agc_gain`/`fft_gain`,
  `crc32` 추가. CRC는 zlib 호환 reflected CRC-32를 16엔트리 니블 테이블로 직접 구현
  (`esp_rom_crc32_le`는 IDF 버전마다 pre/post inversion 관례가 달라 호스트 `zlib.crc32`와
  맞추기 까다롭다). `uart_writer_task`의 부분 write를 재전송 루프로 고치고,
  `POC_DUMP_CSV` 블록(60여 줄)을 삭제했다.
- **기대값**: 빌드 통과, 프레임 168B, 오탐 프레임이 CRC에서 걸림.
- **실제 결과**: `idf.py build` 통과 (bin 0xb6f70, 파티션 29% 여유).
  프레임 168B = 헤더 40B + raw 128B. pty 가상 보드에서 오탐 magic 주입 시
  `crc_fail`/`resync`로 잡히고 데이터 파일에는 들어가지 않음을 확인.
- **다음 조치**: 실보드에서 `partial` 카운터가 0인지 확인 → 작업 9에서 0 확인.

### 2. `agc_gain` / `fft_gain` 헤더 추가 — 상태: 완료

- **문제**: AGC가 게인을 바꾸면 raw 진폭이 통째로 계단식으로 뛴다. 모델이 그걸 움직임으로
  오인할 수 있는데, 기존 v2 헤더에는 게인 정보가 없어 사후 보정이 불가능했다.
- **시도**: `esp_csi_gain_ctrl_get_rx_gain(&info->rx_ctrl, ...)`를 콜백에서 호출해 헤더에 실음
  (rx_ctrl 필드 추출뿐이라 콜백 부하 없음). 호스트에 `csi_store.gain_scale()` 추가.
- **실제 결과**: 헤더가 38B가 되어 4바이트 정렬이 깨지길래 `reserved` u16을 넣어 40B로 맞췄다.
  `measure_csi_hz.py`가 세션 내 `agc_levels`(고유 게인 값 수)를 출력하도록 했다 — 1이면 게인이
  안 바뀐 것이라 보정이 불필요하다.
- **다음 조치**: 실보드 세션에서 `agc_levels`가 몇인지 보고, 2 이상이면 보정을 넣을지 결정
  → 작업 13에서 결론: 변하긴 하는데 **보정은 오히려 해롭다**.

### 3. IDENT 프레임 → esptool 리셋 제거 — 상태: 완료 (pty 검증)

- **문제**: `_detect_rx_boards`가 수집 직전 포트마다 `esptool read_mac`을 돌렸다. esptool은
  DTR/RTS로 칩을 부트로더에 넣었다 hard reset 하므로 **TX가 꽂혀 있으면 TX도 리셋되어
  `tx_seq`가 0으로 되감긴다** — cross-RX 정렬 키가 세션 중간에 끊긴다. 게다가 포트 이름이
  재연결마다 바뀌어 매번 프로브가 필요했다.
- **가설**: 보드가 스트림으로 자기 정체를 알리면 호스트가 포트를 건드릴 이유가 없다.
- **시도**: RX가 부팅 직후 + 2초마다 `frame_type=1` IDENT 프레임 송출 (payload = eFuse base
  MAC 6B + 펌웨어 문자열 10B). reader가 이 MAC을 `device_registry.csv`에서 찾아 `device_id`
  결정. CLI는 포트 목록만 넘기고, IDENT가 안 오는 포트는 reader가 exit 2로 빠진다.
- **함정**: MAC은 반드시 `esp_efuse_mac_get_default()`여야 한다. RX는 `esp_wifi_set_mac`으로
  STA MAC을 `1a:00:00:00:00:00`(esp-csi의 association-free 트릭)으로 덮어쓰므로,
  `esp_read_mac(ESP_MAC_WIFI_STA)`을 쓰면 모든 보드가 같은 MAC을 보고한다.
- **실제 결과**: pty 가상 보드가 RX101 MAC으로 IDENT를 보내자 reader가
  `IDENT: E8:F6:0A:8A:E4:F8 → RX101 (RX101, fw=meshsense)`로 자동 식별. IDENT 이전에 도착한
  CSI 프레임은 메모리에 버퍼링했다 식별 후 flush하므로 앞부분 손실이 없다.
- **다음 조치**: 실보드에서 TX·RX를 모두 꽂고 수집을 돌려, TX 시리얼에 리셋 로그가 없는지 확인.

### 4. 세션 레이아웃·라벨 SSOT — 상태: 완료

- **문제**: reader가 `open("a")`로 파일을 열고 경로가 `session_<id>`뿐이라, `session_meta.yaml`의
  `session_id` 갱신을 잊으면 **기존 파일에 조용히 append**됐다. 실제로
  `20260615/session_21/device_101.jsonl`은 100번째 줄에서 `seq 158 → 0`으로 되감기고,
  `20260523/session_15`는 `sample_count` 192와 128이 섞여 있다. 라벨은 아예 기록되지 않았다.
- **시도**: 세션 경로를 `raw/<YYYYMMDD>/<HHMMSS>_<label>_s<session_id>/`로 바꾸고 `.csi` 파일을
  `open("xb")`(배타적 생성)로 연다. `session.json` 매니페스트에 라벨·시각·RX별 품질통계를 기록.
  CLI가 수집 시작 시 라벨을 묻고(기본값은 `session_meta.yaml`의 `experiment.label_target`)
  `session_meta.yaml`을 세션에 스냅샷한다. reader는 종료 시 `device_<id>.stats.json`을 남기고
  CLI가 이를 매니페스트로 합친다(동시 쓰기 회피).
- **실제 결과**: 같은 라벨로 1초 간격 재수집 → `233229_static_s21` / `233230_static_s21`로
  분리 생성. 파일 충돌 시 append가 아니라 exit 4로 즉시 중단.
- **부수 발견**: 현재 `session_meta.yaml`의 `label_target`은 `"mask"`로 3-class 체계와 맞지 않는다.
  CLI가 유효 라벨이 아니면 기본값 없이 물어보도록 처리했다.

### 5. `csi_store.py` 공용 I/O — 상태: 완료

- **문제**: 프레임 규격이 C와 Python 두 곳에 손으로 미러링돼 있었고, reader의 진폭 계산이
  서브캐리어당 `struct.unpack_from` 2회를 도는 파이썬 루프였다(100Hz × 64 SC × 2 = 12,800 unpack/s).
- **시도**: numpy structured dtype 하나로 프레임을 정의하고 `np.frombuffer`로 파일 전체를 한 번에
  파싱. 진폭·복소 CSI·게인 보정·검증·재동기화(`FrameSplitter`)를 모두 여기로 모았다.
  C 쪽에는 `offsetof` static assert를 6개 걸어 한쪽만 고치면 빌드가 깨지게 했다.
- **실제 결과**: `python scripts/csi_store.py` 셀프테스트 통과(구조체 크기·CRC 왕복·재동기화).
  reader는 이제 프레임을 **변환 없이 그대로** 파일에 쓴다 — 저장 경로에 변환 코드가 없다.

### 6. reader 견고화 — 상태: 완료 (pty 검증)

- **문제**: `ser.timeout=1`을 설정해놓고 타임아웃을 `continue`로 삼켜서, 보드가 죽거나 USB가
  빠져도 reader가 **에러 없이 영원히 대기**했다. CLI는 조기 종료만 감시하므로 지정 시간 동안
  빈 파일을 만들며 정상처럼 보였다. flush도 500프레임(≈5초)에 한 번뿐이었다.
- **시도**: 종료 코드를 의미별로 분리(0 정상 / 2 IDENT 미수신 / 3 스트림 정지 / 4 파일 충돌).
  `--stall-timeout`(기본 3초) 무프레임이면 중단. `find_magic`의 1바이트 read 루프를
  청크 read + 버퍼 내 `bytes.find`로 교체. flush 주기 1초.
- **실제 결과**: pty로 4가지 경로를 모두 재현해 rc=0/2/3/4 확인.
- **막힌 지점**: pty가 `IOSSIOSPEED`(921600 커스텀 baud)와 `TIOCMBIC`(DTR) ioctl을 지원하지 않아
  reader가 열자마자 죽었다. baud는 테스트에서 115200으로 낮췄고, **DTR/RTS 설정은 코드에서
  `try/except OSError`로 감쌌다** — 이건 테스트 편의가 아니라 실제로 옳다. ESP32-S3의
  USB-Serial-JTAG는 네이티브 CDC라 모뎀 제어선이 없을 수 있고, 없으면 토글 위험도 없다.

### 7. 서브캐리어 인덱스 정정 — 상태: 완료 (측정 근거 확보)

- **문제**: `Preprocessing.py`가 `amp[:52]`로 앞 52개를 잘랐는데, LLTF 64 SC 중 0(DC)과
  27~37(가드)은 상시 0이다.
- **시도**: `csi_store.LLTF_DATA_IDX = [1..26] + [38..63]` (52개) 로 선별. 상수는 한 곳에만 둔다.
- **기대값**: 상수 0 feature가 사라지고 텐서 shape는 그대로.
- **실제 결과**: 동일 데이터에서 **구 방식 상수 0 컬럼 12/52 → 신 방식 0/52**.

### 10. DTR/RTS 를 누르는 것이 오히려 보드를 리셋시킴 — 상태: 완료

### 11. 호스트가 없는 동안 쌓인 묵은 프레임이 수집 앞부분을 오염 — 상태: 완료

- **문제**: DTR 수정 후 `boot_changes=0` 은 됐는데 `seq_gap=4134`, 보드 타임스탬프 span 이
  60초 수집인데 **106초**로 나왔다.
- **가설**: 보드는 호스트가 없어도 CSI 를 계속 링버퍼에 쌓는다. FreeRTOS ringbuf 는 가득
  차면 **새 것을 버리므로**, 방치하는 동안 버퍼가 옛 프레임으로 고정된다. 수집을 시작하면
  그 옛 프레임이 먼저 흘러나온다.
- **시도 1**: (a) 펌웨어 — 가득 차면 가장 오래된 항목을 꺼내 버리고 새 프레임을 넣는
  keep-newest 로 변경. (b) reader — 포트 open 직후 **새 바이트가 200ms 끊길 때까지** 읽고 버림.
- **실제 결과**: 백로그는 사라졌지만(`seq_gap=0`), **살아 있는 100Hz 스트림은 200ms 를 절대
  쉬지 않으므로** 매 수집마다 상한 3초를 꽉 채워 버렸다. 실측: 백로그 없는 상태에서도
  328프레임 / 3.01초 폐기.
- **시도 2 — 도착 속도로 판별**: "백로그는 USB 속도로 쏟아지니 도착 Hz 가 높다".
  **실패**: `ser.read()` 는 청크 단위라 한 청크에서 나온 20여 프레임이 전부 같은 벽시계
  타임스탬프를 갖는다 → 순간 속도가 무한대로 계산되어 종료 조건이 걸리지 않았다.
- **시도 3 — 보드 시계 대 벽시계 진행 비율**: 백로그를 비우는 동안에는 보드 시계가
  벽시계보다 훨씬 빨리 흐른다(프레임당 10ms씩 진행하는데 벽시계는 거의 안 감).
  비율이 2 아래로 떨어지면 따라잡은 것.
  **부분 실패**: 기준점을 고정했더니 다 비운 뒤에도 누적 비율이 천천히 떨어져 3초를 채웠다.
- **최종**: 0.3초 **슬라이딩 윈도**로 현재 비율만 본다. 실측:
  | 상황 | 폐기 | 소요 |
  |---|---|---|
  | 25초 방치 후 (백로그 있음) | 472프레임 | 0.53s |
  | 곧바로 재수집 (백로그 없음) | 48프레임 | 0.38s |
  둘 다 `hz≈99.3  seq_gap=0  tx_cov=0.993`.
- **부수 수정**: 백로그를 비우다 IDENT 를 함께 버리면 보드 식별이 다음 IDENT(2초 뒤)까지
  미뤄진다 — 비우는 중에도 IDENT 는 붙잡아 두고 본 수집 시작 시 바로 쓴다.

### 12. `ESP_LOG` 가 USB 로 나오지 않아 펌웨어 진단이 보이지 않음 — 상태: 완료

- **문제**: `ringbuf_drop`/`partial` 을 확인하려고 5초 로그를 찾았는데, 호스트에서 17초를
  캡처해도 로그 텍스트가 **0건**이었다.
- **원인**: 이 프로젝트는 콘솔 primary 가 GPIO43 UART 이고(`CONFIG_ESP_CONSOLE_UART_CUSTOM`)
  USB-Serial-JTAG 드라이버를 앱이 직접 설치해 쓴다. 즉 5초 로그는 물리 핀으로만 나간다.
  **문서의 "ESP_LOG 가 바이너리 스트림에 끼어든다"는 제약은 실제로는 존재하지 않았고,
  대신 진단을 볼 방법이 아예 없었다.**
- **시도**: IDENT 프레임 payload 를 16B → 32B 로 늘려 진단 카운터 4개(u32)를 실었다.
- **실제 결과**: reader 출력과 `session.json` 에 `fw_csi_cb` / `fw_uart_sent` /
  `fw_ringbuf_drop` / `fw_uart_partial` 이 그대로 들어온다. 부수 효과로
  `resync` 가 0 이 됐다 — 로그가 스트림을 오염시키지 않는다는 게 수치로 확인됐다.

### 13. gain 보정 — 상태: **되돌림** (헤더 필드는 유지, 기본 적용은 끔)

- **문제**: AGC 가 게인을 바꾸면 raw 진폭이 계단식으로 뛴다. 실측상 45초에 AGC 가 483회,
  FFT gain 이 8~23단계로 바뀐다. 모델이 이걸 움직임으로 오인할 수 있다.
- **시도 1 — 직접 만든 근사식**: `2^-((fft-fft0)+(agc-agc0)/4)`.
  **실제 결과**: 시간축 std 가 0.636 → **8.355** 로 13배 악화. 즉시 폐기.
- **시도 2 — 벤더 API**: `esp_csi_gain_ctrl` 의 소스를 보고 Python 으로 이식하려 했으나
  **소스 없이 정적 라이브러리(.a)로만 배포**된다. 그래서 보드에서 계산해
  `gain_comp`(f32) 를 헤더에 싣도록 프레임을 v3 → **v4**(헤더 44B)로 올렸다.
  **실제 결과**: 배율 범위는 0.794~1.189 로 정상인데,
  | 지표 | 보정 전 | 보정 후 |
  |---|---|---|
  | 시간축 std 평균 | 0.636 | 1.280 |
  | 변동계수 | 0.0483 | 0.0966 |
  | AGC 변화 483곳의 평균 진폭 점프 | 0.58 | 0.59 |
- **해석**: AGC 변화 지점의 진폭 점프가 0.58 로, 평균 진폭 13의 4% 에 불과해 일반
  프레임간 변동과 구분되지 않는다 — **보정할 계단이 애초에 없다.**
  `manu_scale=false` 로 하드웨어가 이미 스케일을 맞추는 것으로 보인다. 보정을 켜면 없는
  계단을 만드느라 분산만 2배가 된다.
- **다음 조치**: `amplitude(compensate=False)` 가 기본. **필드는 헤더에 계속 저장한다** —
  수신기가 움직이거나 RSSI 가 크게 흔들리는 조건에서는 결론이 달라질 수 있고,
  그때 재검토하려면 데이터가 남아 있어야 한다.

### 14. `session_id` 자동 순번 + 세션 메타 브라우저 폼 — 상태: 완료

### 15. TX 재부팅 감지 — 상태: 완료

- **계기**: USB 포트가 2개뿐이라 RX 2대를 연결하고 **TX 는 외부 전원에만 꽂아둘** 수 있는지
  물음. 펌웨어상 TX 는 호스트 입출력이 전혀 없어 전원만으로 동작한다 — 답은 "된다".
  다만 그렇게 두면 **TX 재부팅을 알아챌 방법이 필요해진다** (보조배터리 자동 차단 등).
- **문제**: `tx_seq` 역행 감지가 어디에도 없었다. 더 나쁜 건 `Preprocessing.load_buffers` 가
  `tx_seq` 로 **정렬**한다는 점이다 — 재부팅하면 이후 프레임이 세션 앞쪽으로 끌려가
  시간 순서가 뒤집히고, 그 사이 수천 스텝이 선형 보간으로 채워진다.
- **재현**: tx_seq `5000..5199` → 재부팅 → `0..199` 인 세션을 만들어 현재 코드에 넣어 보니,
  정렬 후 첫 프레임이 원래 200번째 프레임이었다. 즉 **48초 분량이 통째로 가짜 데이터가
  되는데 경고가 하나도 안 뜬다.**
- **시도**: 3단계에 감지를 넣었다 — reader(`tx_back` + 경고), `measure_csi_hz`(`tx_back` +
  경고, `tx_cov` 무효화), `Preprocessing`(정렬로 덮지 말고 **거부**).
- **실제 결과** (pty 로 TX 재부팅 재현):
  ```
  reader        : [경고] TX 재부팅으로 보입니다 (tx_seq 5299 → 0) ... tx_back=1
  measure       : tx_back=1 tx_cov=0.000  [경고] TX 재부팅 감지 — 재수집하세요
  Preprocessing : rc=1  ValueError: 수집 중 TX 가 재부팅했습니다 (tx_seq 5299 → 0, 1회)
  build_dataset : [건너뜀] 003258_static_s1: ...
  ```
  정상 세션에서는 `tx_back=0` 으로 오탐 없음 (합성 6세션 + 실보드 30초 확인).
- **부수 확인**: TX 가 아예 죽으면 RX 에 CSI 가 안 들어와 reader 가 3초 안에 `rc=3` 으로
  끝난다 — 별도 감시 장치가 필요 없다.

### 16. RX 2대 동시 수집 검증 — 상태: 완료 (2026-08-26)

- **구성**: TX1 은 외부 전원(USB 포트 절약), 노트북에는 RX101·RX103 만 연결. 두 보드 모두
  최신 펌웨어로 재플래시 (RX 펌웨어는 보드 구분 없이 동일 바이너리).
- **실제 결과** (60초):
  ```
  device_101.csi: n=5944 hz=99.91 gaps=0 seq_gap=0 tx_back=0 tx_cov=0.999 rssi_med=-28 agc_levels=7
  device_103.csi: n=5880 hz=98.99 gaps=0 seq_gap=0 tx_back=0 tx_cov=0.990 rssi_med=-11 agc_levels=1
  cross-RX 공통 tx_seq: 5870 / 최소 RX 5880 = 99.8%
  ```
  두 reader 모두 `crc_fail=0 invalid=0 resync=0`, 펌웨어 `partial=0`.
  IDENT 로 각각 RX101 / RX103 자동 식별 — 포트 순서와 무관하게 맞았다.
- **후처리**: `aligned shape (2, 5934, 52)` → `X (188, 300, 104)`. RX 2대 = 104 feature 확인.
- **두 보드가 서로 다른 채널을 보는지 확인**: 공통 `tx_seq` 구간에서 두 RX 의 평균 진폭
  상관이 **−0.062** (거의 무상관). 워터폴에서도 널(null) 서브캐리어 위치가 RX101 은 27번,
  RX103 은 25번 부근으로 다르다 — 같은 자극을 서로 다른 경로로 받고 있다는 뜻이고,
  RX 를 여러 대 두는 의미가 데이터로 확인됐다.
- **관찰**: RX103 의 `rssi_med=-11` 은 다소 강하다(`agc_levels=1` = 게인 고정).
  [troubleshooting/01-csi-rate.md](../troubleshooting/01-csi-rate.md) §11 에 RSSI 포화
  가설 기록이 있으니, 실제 수집에서는 보드 간 거리를 더 확보하는 편이 좋다.
  (이번 측정에서는 `tx_cov=0.990` 으로 문제 없었다.)

### 17. RX 는 호스트 연결이 필수 — 측정으로 확인 + 내 측정 오류 정정

- **질문**: TX 처럼 RX 도 컴퓨터에 연결 안 된 상태로 둬도 되는가?
- **측정** (RX103, 포트를 15초 닫아 "호스트가 안 읽는" 상태 재현):
  ```
  Δcsi_cb=1192  Δseq=1195  Δringbuf_drop=670   (15.04초)
  ```
  보드는 계속 CSI 를 받지만(~80Hz) 링버퍼(64KB ≈ 4초)를 넘는 것은 전부 버려진다.
  SD 카드도, 플래시 저장도, 무선 업링크도 없다 → **RX 는 호스트 연결이 필수.**
  TX 와 정반대다 (TX 는 송신만 하므로 전원만 있으면 된다).
- **내 측정이 한 번 틀렸다 — 기록해 둔다.** 처음에 "호스트 없을 때 콜백이 881Hz 로
  폭증한다"는 수치를 얻고 이상 현상으로 의심했다. 원인은 펌웨어가 아니라 **내 측정 스크립트**
  였다: 포트를 열자마자 첫 IDENT 를 읽었는데 그게 **백로그에 남아 있던 오래된 IDENT**라
  카운터 스냅샷 시점이 실제보다 한참 과거였고, 델타가 그만큼 부풀었다.
  `Δcsi_cb ≈ Δseq` 를 교차 검증하는 방식으로 다시 재니 두 조건 모두 ~100Hz 로 정상이었다.
  (백로그 프레임 자체도 분석해 `tx_seq` 가 1씩 증가하는 정상 TX 프레임임을 확인했다 —
  rate/channel/sig_len 이 전부 동일.)
- **같은 함정이 reader 에도 있어 고쳤다**: 백로그를 비우다 건진 IDENT 를 펌웨어 카운터의
  **기준점**으로 쓰고 있었다. 그 IDENT 는 최대 링버퍼 깊이(~4초)만큼 과거의 스냅샷이라
  세션 델타에 수집 전 구간이 섞인다. 이제 식별에는 쓰되 기준점은 **본 수집 시작 후 첫
  IDENT** 로 잡는다. 수정 후 실측: `frames=2960` 에 `csi_cb=2799 ringbuf_drop=0`
  (이전에는 `ringbuf_drop=40~85` 가 섞여 들어왔다).
- **교훈**: 이 파이프라인에서 라이브 스트림을 임시로 들여다볼 때는 **반드시 백로그를 먼저
  비워야 한다.** 수집 경로(`csi_serial_reader.py`)는 그렇게 하지만, 애드혹 진단 스크립트는
  쉽게 잊는다.

### 18. 클래스 분리 가능성 진단 도구 — 상태: 완료

- **왜**: 수십 세션을 찍고 나서야 "이 배치로는 안 갈린다"를 알면 늦다. 특히 `empty` vs
  `static` 이 어렵다 — `action` 은 시간축 진폭 변동이 크지만, 정지한 사람은 다중경로를
  바꿀 뿐 시간에 따라 흔들지 않는다. 파일럿 몇 세션으로 먼저 판단할 수단이 필요했다.
- **시도**: `scripts/check_separability.py` — PyTorch 없이 numpy 통계만. 윈도별 특징 5종
  (변동계수 평균/최대, 프레임간 변화율, 고주파 비율, 서브캐리어 분산) →
  **세션 단위 leave-one-out** 최근접 중심 분류 + 쌍별 판정 + PNG.
- **검증**: 합성 데이터 두 벌로 양방향 확인 — 클래스별 변동이 **다른** 데이터(갈려야 함)와
  **동일한** 데이터(갈리면 안 됨).

#### 여기서 함정 두 개를 잡았다

**(1) 쓸모없는 특징이 유클리드 거리에서 동등한 표를 행사해 판정을 뒤집었다.**
분리 가능한 데이터인데 LOSO 정확도가 정확히 우연 수준(0.333)이고 empty↔static 이 완전히
맞바뀌었다. 원인: `서브캐리어 분산` 은 방 배치가 만든 **세션 고유 지문**이라 같은 클래스의
다른 세션끼리도 값이 널뛰는데, 5차원 거리에서 유효 특징 3개와 동등한 비중을 가졌다.
→ 특징별 LOSO 정확도와 **세션지문 지표**(같은 클래스 안 세션 간 흩어짐 / 클래스 간 흩어짐)를
계산해, 세션지문이 1 이상이거나 단독 LOSO 가 우연 수준인 특징을 자동으로 뺀다.
수정 후 정확도 1.000, 노이즈 특징 2개가 `⚠세션특징` 으로 정확히 표시된다.

**(2) AUC 가 거짓말을 한다.** 세 클래스가 **통계적으로 완전히 동일한** 합성 데이터에서도
`action vs empty` AUC 가 **1.000** 으로 나왔다. 모든 세션의 윈도를 한데 모아 계산하기 때문에,
세션마다 다른 기저 채널이 클래스 차이처럼 보인 것이다. 같은 데이터에서 LOSO 는 0.583 으로
정직하게 "사실상 구분 불가" 를 냈다.
→ **판정 기준을 쌍별 2-class LOSO 정확도로 바꿨다.** AUC 는 "참고 — 부풀려진 값" 으로만 표시하고,
그 사실을 출력에 명시한다.

- **부수**: matplotlib 한글 폰트를 자동으로 잡도록 했다 (AppleGothic 등). 없으면 조용히 기본값.

### 19. 브라우저 제어판 (GUI) — 상태: 완료

- **왜**: CLI·유틸 사용이 익숙하지 않은 사용자도 수집을 돌릴 수 있어야 한다.
- **시도**: `scripts/meshsense_gui.py` — 표준 라이브러리 `http.server` 만 쓰고 **127.0.0.1
  에만 바인딩**(보드를 굽고 데이터를 지우는 화면이라 외부에 열 이유가 없다).
  탭 5개: 보드 / 수집 / 세션 / 진단·데이터셋 / 실험 정보.
  무거운 작업은 백그라운드 프로세스 하나로 직렬 실행하고 로그를 실시간으로 흘린다
  (플래시 중 수집을 시작하면 포트가 충돌하므로 동시 실행을 막는다).
- **보드 식별은 esptool 이 아니라 IDENT 로 한다** — 확인만으로 보드가 리셋되지 않는다.
  이를 위해 `csi_serial_reader.py --identify` 를 추가했다 (JSON 출력 후 종료).
- **실보드 검증**: 제어판에서 20초 수집 실행 →
  `RX101 2015프레임 100.0Hz / RX103 1963프레임 97.4Hz, crc_fail=0 seq_gap=0`,
  워터폴 PNG 자동 생성, 세션 목록·품질 표시·순번 자동 증가(22→23) 확인.
- **막힌 지점 3개**:
  1. 1.2초 폴링마다 화면 전체를 다시 그려 **입력 중이던 폼이 통째로 날아갔다.**
     섹션별 데이터 지문을 비교해 바뀐 섹션만 다시 그리도록 고쳤다.
  2. 같은 이유로 워터폴 이미지가 폴링에 지워졌다 — 선택 상태를 변수로 들고 섹션 안에서 그린다.
  3. 보드 태그가 `RX101 RX101` 로 중복 표시됐다 (`board_name` 에 이미 접두어가 있음).

### 20. 부수 수정 — reader 종료 코드·요약 Hz·워터폴 라벨

- **TX 포트가 rc=3(스트림 정지)로 잡히던 문제**: TX 는 USB 로 아무것도 안 보내는데
  stall timeout(3초)이 ident timeout(6초)보다 먼저 걸렸다. 식별 전에는 stall 검사를
  하지 않도록 고쳐 rc=2(RX 아님)로 정확히 분류된다.
- **요약 Hz 가 낮게 보이던 문제**: 매니페스트가 호스트 wall clock 으로 Hz 를 계산해
  백로그 비우기·기동 시간이 섞였다(78.4Hz). 보드 타임스탬프 기준 `span_s` 를 기록해
  99.7Hz 로 정확해졌다.
- **워터폴 PNG**: colorbar 라벨이 `Amplitude (on-device norm)` 이었는데 USB 경로는
  온디바이스 정규화를 하지 않는다(그건 deprecated 된 AP 경로 얘기). `sqrt(I²+Q²)` 로
  정정하고, RX 1대일 때 제목이 겹치고 x축 라벨이 잘리던 여백 계산을 인치 기준으로 고쳤다.

## 막힌 지점 / 되돌린 것

### 실보드 검증 미완 — **해소됨 (2026-08-26)**

1차 작업 때는 보드를 연결할 수 없어 pty 가상 보드와 합성 세션으로만 검증했다. 그때 남긴
미확인 항목은 전부 실보드로 확인했고, **그 과정에서 가상 보드로는 드러날 수 없었던 문제
3건이 나왔다** (작업 10·11·12). 가상 검증으로는 부족했다는 게 이 스프린트의 교훈이다:

| 1차 때 걱정한 것 | 실제 결과 |
|---|---|
| 100Hz 에서 `crc_fail`/`resync`/`partial` | 전부 0 |
| IDENT MAC 이 registry `sta_mac` 과 일치하는지 | 일치 (`E8:F6:0A:8A:D7:E8` → RX103 자동 매칭) |
| 헤더 확장에 따른 콜백 스택 부하 | 문제 없음 (v4 44B 로도 이상 없음) |
| CRC 계산이 콜백 경로에 주는 부하 | 문제 없음 (`fw_csi_cb` 정상) |
| `agc_gain` 이 세션 중 변하는지 | **변한다** (45초에 483회) — 다만 보정은 불필요, 작업 13 참조 |

**가상 보드로는 못 잡았던 것들**: 포트를 여는 행위 자체가 보드를 리셋시킨 것,
방치 중 쌓인 링버퍼 백로그, `ESP_LOG` 가 USB 로 안 나온다는 사실.

### pty가 커스텀 baud·DTR ioctl을 지원하지 않음 — 결과적으로 진짜 버그의 힌트였다

pty로 reader를 검증하려 했더니 `IOSSIOSPEED`(921600)와 `TIOCMBIC`(DTR)에서
`OSError: [Errno 25] Inappropriate ioctl for device`로 죽었다. baud는 테스트에서 115200으로
낮춰 회피하고, DTR/RTS 설정은 `try/except OSError`로 감쌌다.

그때는 "pty에 모뎀 제어선이 없으니 감싸두자" 정도로 넘겼는데, **실보드에서 확인해 보니
그 DTR 설정 자체가 리셋 원인이었다**(작업 10). 지금은 감싸는 게 아니라 아예 건드리지 않는다.
가상 환경이 거부한 동작이 실제로도 하면 안 되는 동작이었던 셈이다.

### `esp_rom_crc32_le`를 쓰려다 직접 구현으로 선회

ROM CRC 함수는 IDF 버전마다 pre/post inversion 관례가 달라 호스트 `zlib.crc32`와 맞추려면
버전 의존적인 실험이 필요했다. 168B × 100Hz = 16.8KB/s에 니블 테이블 CRC는 무시할 부하라,
호환 관례를 코드로 못박는 쪽을 택했다.

### 기존 수집 데이터는 재수집이 전제

`mac_collector_output/raw/` 아래 기존 세션은 (1) 라벨이 없고 (2) append 오염으로 여러 런이
섞여 있어 학습에 쓸 수 없다. 마이그레이션 스크립트를 만들지 않았다 — 라벨 정보가 애초에
존재하지 않아 복원할 수 없기 때문이다. `csi_store.load_legacy_jsonl()`과
`measure_csi_hz.py`의 JSONL 폴백은 비교·진단 용도로만 남겼다.

### `LSTM.py`는 실행 검증 못 함

PyTorch가 설치되어 있지 않아 문법 검사까지만 했다. 모델 담당이 `pip install torch` 후 확인해야 한다.

### RX 2대 동시 수집(cross-RX `tx_seq` 정렬) — **해소됨 (2026-08-26)**

USB 포트가 2개뿐이라 처음에는 TX + RX 1대 구성이었다. TX 를 외부 전원으로 빼서 RX 2대를
붙이니 **공통 `tx_seq` 99.8%** 로 통과했다 (작업 16). TX 가 호스트 없이 동작한다는 점이
포트 제약을 그대로 풀어 준 셈이다.

### 실보드 검증 세션은 전부 삭제했다

책상 위 정지 장면에서 찍은 것이라 `static` 라벨이 실제 시나리오와 맞지 않는다.
잘못 라벨된 데이터가 데이터셋 루트에 남는 것이 이 스프린트가 없애려던 문제 그 자체라
검증 수치만 이 문서에 남기고 세션은 지웠다. **3-class 실데이터는 사용자가 실제 시나리오를
수행하며 수집해야 한다.**

### 블로커였던 것: 데이터 포맷

저쪽 `preprocess_3rx.py`(825줄) + `LSTM.py`(1225줄) + 테스트(780줄)가 **JSONL
`csi_amp` v2** 를 전제로 했다. 우리 수집은 v4 binary `.csi` 다.

수집 포맷을 되돌리면 실측으로 확인한 손상(오탐 프레임 저장, append 혼입, DTR 리셋,
백로그)이 그대로 돌아온다. 그래서 **`scripts/export_jsonl.py`(`.csi` → JSONL v1)** 를
만들어 저쪽 파이프라인을 무수정으로 돌렸다. 검증:

```
export_jsonl  : 3세션 × 3RX × 27500프레임 → 82500 records/세션 (7.5초)
preprocess_3rx: train 2세션 1814 windows / test 1세션 907 windows, 제외된 세션 없음
```

### 병합 중 발견한 것

- **라벨 어휘가 달랐다.** 저쪽은 `motion`, 우리는 `action`. 저쪽이 공식 설계 문서에
  세션 배정까지 확정해 두었으므로 `csi_store.LABELS` 를 `motion` 으로 맞췄다.
  수집 데이터가 아직 없어 마이그레이션 비용이 없다.
- **저쪽은 `features_per_rx=64`** 로 64개를 다 쓴다. LLTF 의 DC·가드 12개가 상시 0이라
  3-RX 192 feature 중 **36개(19%)가 상수 0**이다. `data-schema.md` 와
  `postprocessing.md` 에 명시했다.
- **저쪽 라벨이 `LABEL_SESSION_RANGES` 로 코드에 하드코딩**돼 있다. 우리 `session.json` 이
  그 자리를 메운다 — `export_jsonl.py --print-labels` 가 배정을 그대로 출력한다.
  실제로 합성 세션 10/11/12 를 넣었더니 저쪽 하드코딩 범위(empty=1~10, static=11~20)에
  걸려 session 12(motion)가 static 으로 분류됐다. 하드코딩의 위험이 그대로 드러난 사례다.

### 내가 만들었다가 폐기한 것

`model_train/model/build_dataset.py` 를 지웠다. 저쪽 `preprocess_3rx.py` 가 같은 일을
더 엄밀하게 한다 — 손상 record 제거, `tx_seq` 단조성 검증, RX 조합별 교집합, 수신 mask,

`check_separability.py` 는 그 의존을 끊고 `csi_store` 만으로 자립시켰다.

## 실시간 경로 1-RX 검증 (2026-09-02)

TX(외부 전원) + RX(업링크, USB 데이터 미사용) + SINK(USB) 3보드로 무선 경로를 실측했다.
결과와 설계는 [realtime-uplink.md](../realtime-uplink.md). 요지: **99.58Hz, 손실 0%,
업링크 실패 0, 업링크가 CSI 수신을 방해하지 않음.**

### 여기서도 세 번 틀렸다

**(1) 백로그를 또 안 비웠다.** 첫 측정이 51Hz·46% 손실로 나와 업링크가 절반을 흘린다고
의심했다. 원인은 애드혹 스크립트가 싱크의 백로그를 먼저 읽은 것 — 작업 17 에서 똑같이
당하고 문서에까지 적어둔 함정이다. 비우고 재측정하니 99.5Hz·손실 0%.

**(2) ring buffer 가 4바이트 정렬 크기를 돌려준다.** 172바이트 프레임에 `len=176` 이
와서, 그대로 보내면 프레임마다 4바이트가 붙는다. 프레임 길이는 헤더의 `total_len` 이
정본이므로 그것을 쓰도록 RX·SINK 양쪽을 고쳤다.

**(3) 그런데 (2)를 고쳐도 간격이 176 이었다.** 176바이트를 통째로 뜯어보니 남는 4바이트가
`40616` — 다음 프레임의 `tx_seq` 값이었다. **TX 의 자극 broadcast(4바이트 카운터)를
싱크가 함께 받아 그대로 흘려보내고 있었다.** 같은 채널에 우리 업링크만 오는 게 아니라는
당연한 사실을 놓쳤다. 싱크가 프레임 서명(magic + version)으로 걸러내도록 고치니
`resync` 가 프레임당 1회 → 0 이 됐다.

세 번 다 "추측하지 말고 원시 바이트를 본다"로 풀렸다. 특히 (3)은 카운터만 보고 있었으면
영영 못 찾았을 것이다 — 데이터 자체는 `crc_fail=0`, `seq_gap=0` 으로 멀쩡했기 때문이다.

## 논문 준비 — 보드 없이 (2026-09-02)

순서: ①수집 프로토콜 ②출처 기록 ③라벨 배관 ④서브캐리어(합의 대기) ⑤ablation 하네스 ⑥다중 RX demux.
"수집 전에 정해야 복구 불가능한 것"을 앞에 뒀다.

### ⑤ ablation 하네스 (`scripts/ablation.py`)

RX 대수 / 윈도 길이 / `amp52`·`amp64`·`amp52+phase` 를 같은 베이스라인으로 비교하고
`--split-by session|date|placement|subject` 로 조건 단위 분할을 지원한다. 합성 데이터
(2 날짜 × 2 피험자 × 3 클래스 × RX 3대)로 세 분할 모두 동작 확인.

- **정직성 확인**: 합성 위상은 순수 잡음인데 `amp52+phase` 가 amp52 보다 낮게(1.000→0.916)
  나왔다. 잡음 특징을 넣으면 나빠진다는 걸 하네스가 감추지 않는다.
- **알려진 성질**: 그룹이 2개뿐이면 세션지문 필터가 공격적이라 특징이 1개만 남는다.
  파일럿 규모에서는 정상, 조건이 늘면 안정된다.

### ⑥ 다중 RX demux

헤더 `reserved` → `rx_id`, reader 를 RX별 `RxStream` 으로 재구성. pty 로 RX 2대 교대
스트림이 `device_101/103.csi` 로 분리되고 각각 seq 연속임을 확인. USB 직결 회귀 없음.
**재작성 중 실수 하나** — `--device-id` override 가 프레임이 와야 파일을 열게 되어 충돌
테스트가 rc 2 로 나왔다. 명시적 override 는 시작 즉시 열도록 되돌렸다 (rc 4).
실보드 다중 RX 는 미검증.

### 조건 필드

세션 메타에 `condition.placement_id` / `condition.subject_id` 추가. 프로토콜의 조건 단위
분할과 ablation `--split-by placement|subject` 의 키다.

## 남은 일 / 다음 스프린트

**실시간 경로 — 1-RX 손실 0, 2-RX 는 약한 링크 ~7% 손실 확인.** 완화(싱크 rx 버퍼·송신 분산·프레임 축소)가 다음 과제.

**서브캐리어 52 vs 64 결정** — 모델 담당 합의 필요. 제안: 기본 52, 64 는 ablation 항목으로 보고.

```
TX(csi_send_poc) ──ESP-NOW 10ms──▶ RX × N ──ESP-NOW 업링크──▶ SINK 1대 ──USB──▶ Mac
```

선결 과제:
1. RX가 송신을 하게 되므로 **RX마다 STA MAC을 달리 줘야 한다.** 현재 RX는 자기 MAC을 TX와 같은
   `1a:00:00:00:00:00`으로 설정하고 그 MAC의 프레임만 CSI로 통과시키므로, 그대로 두면 RX가
   서로의 업링크를 CSI로 잡아 자기오염된다.
2. 업링크 에어타임 실측 — RX 3대 × 100Hz × 164B @ MCS0. CSI 콜백 트리거율이 떨어지는지
   5초 카운터로 확인. 떨어지면 진폭 uint8 양자화 또는 2샘플 묶음 전송으로 완화.
