# 실시간 무선 경로 (ESP-NOW 업링크 + SINK)

> 설계와 현재 상태는 [realtime-uplink.md](../realtime-uplink.md).

## 2026-09-02 — 역할별 MAC 분리 (선결 과제)

- **문제**: 모든 보드가 STA MAC `1a:00:00:00:00:00` 을 썼다(esp-csi 의 association-free 트릭).
  RX 가 송신을 시작하면 서로의 업링크를 CSI 로 잡아 자기오염된다.
- **해결**: TX `..:00`(CSI 필터 기준) / RX `..:<CSI_RX_ID>` / SINK `..:ff`. RX 의 CSI 필터는
  TX MAC 에만 걸려 있어 업링크·ACK 는 CSI 로 안 잡힌다.
- **재발 방지**: `CLAUDE.md` — 역할별 MAC 을 같게 하지 말 것.

## 2026-09-02 — 세 번째 보드가 인식되지 않음

- **증상**: 3보드를 꽂았는데 `/dev/cu.usbmodem*` 에 2개만.
- **원인**: (사용자 측 연결 문제 — 데이터선 없는 충전 케이블 또는 허브 전력.) TX 를 외부
  전원으로 빼고 RX 2대만 연결하는 것으로 해결.
- **부수 확인**: TX 는 외부 전원에서 정상 송신 (RX 콜백 ~100Hz 로 확인).

## 2026-09-02 — 첫 측정 51Hz·46% 손실 → 백로그

[06](06-measurement-pitfalls.md) 참조. 비우고 재면 99.5Hz·손실 0%.

## 2026-09-02 — 프레임마다 4B 덧붙음 (두 원인이 겹침)

1. ring buffer 4B 정렬 패딩 — RX·SINK 양쪽 수정.
2. 고쳐도 그대로 → TX 자극 broadcast 가 싱크를 거쳐 새어 나옴 — 프레임 서명 필터.

상세는 [02](02-serial-stream.md) 2026-09-02 두 항목. 데이터는 `crc_fail=0 seq_gap=0` 으로
멀쩡했기 때문에 카운터만 봤으면 못 찾았을 문제.

## 2026-09-02 — 결과

TX(외부 전원) + RX(업링크) + SINK, 60초: `hz=99.58 seq_gap=0 tx_cov=0.996`,
`uplink_ok=5804 fail=0 ringbuf_drop=0`, reader `resync=0`. 업링크가 CSI 수신을 방해하지 않음.

## 2026-09-03 — 2-RX 동시 업링크에서 약한 링크에 ~7% 손실 (실보드)

- **구성**: TX(외부) + RX103(외부, 업링크) + RX102(USB 전원, 업링크 rx_id=2) → SINK RX101 → Mac.
- **증상**: 세 번 연속 같은 패턴 — RX102 `seq_gap=0` 99.8Hz, **RX103 `seq_gap≈360~410` 93Hz**
  (약 7%). host demux 자체는 정상 (`device_102/103.csi` 분리, cross-RX 99.5%).
- **어디서 잃었나 (싱크 상태 프레임 추가 후)**: RX103 `uplink_fail=0 ringbuf_drop=0`,
  싱크 `drop=0 usb_timeout=0`, host `crc_fail=0 invalid=0`. 그런데 RX 두 대 `sent` 합 −
  싱크 `recv` ≈ **400 = RX103 의 seq_gap**. 즉 RX 는 ACK 를 받아 성공으로 셌는데 싱크
  `recv_cb` 에는 안 온 프레임이 있다 → **싱크 Wi-Fi 수신 경로(MAC-ACK 이후, 콜백 이전)**.
  같은 RX 에서 `DUP=11` — ACK 유실 후 재전송 — 링크가 marginal 하다는 신호.
- **결정적 실험**: RX102 를 USB 직결로 되돌려 업링크를 RX103 하나만 남기니
  **RX103 손실 0** (`seq_gap=0`, 99.66Hz), 싱크 `recv=5808` = RX103 `sent=5808` 정확히 일치.
- **결론**: 손실은 RX103 보드나 위치의 고정 문제가 아니라 **동시 업링크 2개 + TX broadcast
  (`foreign≈96Hz`) 가 싱크 수신에 겹칠 때** 발생하며 약한 링크가 먼저 무너진다.
  1-RX 업링크는 손실 0.
- **위치 교체 실험 (같은 날, 포트 사정으로 자연히 실행됨)**: RX102 를 외부 전원으로,
  RX103 을 USB(Mac 옆, 싱크 근처)로 바꿔 다시 60초 → 이번엔 **RX102 가 7.3% 손실
  (`seq_gap=432`), RX103 은 0.** 손실이 **보드가 아니라 위치(싱크에서 먼 쪽)** 를 따라간다.
  두 RX 다 `fail=0`, 싱크 `drop=0 usb_timeout=0`, RX sent 합 − 싱크 recv ≈ 410 ≈ seq_gap.
  즉 동시 업링크 경합에서 **링크 마진이 작은 쪽**이 ACK 는 받되 싱크 수신 콜백까지 못 오는
  프레임을 낸다. 양쪽 rx_id 태그(1·2)로 demux 도 실보드에서 확인 (cross-RX 99.6%).
- **완화 후보** (측정 순서대로): ~~싱크 rx buffer 증가~~ → RX 송신 시점 분산(RX 마다
  위상 오프셋) → 진폭 uint8 양자화로 프레임 축소 → 업링크 속도 MCS 상향.
  어느 것이든 **RX 2대 동시 + seq_gap 으로 판정**한다.

## 2026-09-03 — 완화 1: 싱크 rx 버퍼 증가 — **효과 없음 (기각)**

- **시도**: `CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM` 10 → 25 (Kconfig 최대), dynamic 은 이미
  최대 128. 같은 배치로 60초.
- **막힌 지점**: 처음에 32/256 을 넣었더니 Kconfig 범위(static [2,25], dynamic [0,128]) 밖이라
  **조용히 기본값으로 리셋**되어 dynamic 이 32 가 됐고 빌드도 실패해 빈 세션이 생겼다.
  범위 밖 값은 경고 한 줄만 내고 무시된다 — `sdkconfig.h` 를 확인해야 한다.
- **결과**: RX102 `seq_gap=456` (7.6%), RX103 0, 싱크 `drop=0`. **버퍼 수는 원인이 아니다.**
  값은 해가 없으니 25 로 둔다.
- **해석**: 하드웨어 rx 버퍼가 포화되지 않는데도 ACK 된 프레임이 콜백에 안 온다 —
  ESP-NOW 수신 경로 안쪽(드라이버 큐/ESP-NOW 처리)이거나, 약한 링크의 재전송 처리와 얽힌
  문제. 다음 레버는 **송신 시점 분산** (두 RX 가 TX 자극 직후 동시에 쏘는 것을 피한다).

## 2026-09-03 — 완화 2: 송신 시점 분산 — **효과 있음 (채택)**

- **시도**: RX 펌웨어에 `CSI_UPLINK_OFFSET_MS`(CMake, 기본 0). 프레임 **캡처 시각** 기준
  `rx_id × OFFSET` 뒤에 보낸다 — 캡처 시각 기준이라 백로그로 늦게 꺼낸 프레임은 즉시 전송,
  지연이 누적되지 않는다. RX103(rx_id=1)만 4ms 로 재플래시, RX102 는 오프셋 0 그대로.
- **결과** (같은 배치, 60초 × 5회, RX103 오프셋만 바꿈, RX102 는 항상 0):
  | RX103 오프셋 | RX102(먼 쪽) 손실 | RX103 손실 | RX103 `csi_cb` / RX102 | RX103 tx_cov |
  |---|---|---|---|---|
  | 4ms (busy-wait) | **0.0%** (`seq_gap=1`) | 0 | 5638/5759 (−2.1%) | 0.972 |
  | 4ms (busy-wait, 재현) | **0.0%** (0) | 0 | 5670/5770 (−1.7%) | 0.978 |
  | 4ms (esp_timer) | **0.07%** (4) | 0 | 5648/5764 (−2.0%) | 0.974 |
  | 0ms (대조) | 5.8% (348) | 0 | 5716/5776 (−1.0%) | 0.985 |
  | 2ms | 1.05% (63) | 0 | 5748/5784 (−0.6%) | 0.990 |
  싱크 `recv` 는 매번 RX `sent` 합과 일치(drop=0, usb_timeout=0).
- **해석**: 두 RX 가 같은 TX 자극(10ms 주기) 직후 거의 동시에 unicast 를 쏘면 싱크에서
  겹치고, 링크 마진이 작은 쪽이 진다. 2ms 로는 절반만 갈라지고 4ms 면 완전히 갈라진다 —
  RX102 의 송신+ACK(+재전송) 창이 캡처 후 2~4ms 까지 이어진다는 뜻.
  ACK 는 받았는데 콜백에 안 오던 현상은 결국 **동시 도착 처리**의 문제였다.
- **부작용**: 오프셋을 준 RX103 의 CSI 캡처(`csi_cb`)가 RX102 보다 1~2% 적다. 대조(0ms)에서도
  −1% 라 절반은 배치(RSSI −39 vs −31), 나머지 ~1% 가 오프셋 송신의 비용으로 보인다.
  busy-wait 를 esp_timer one-shot 으로 바꿔도 같아서 **CPU 점유가 아니라 송신 시점 자체**의
  영향이다. 7% 손실 대비 무시할 수준이라 채택.
- **구현**: RX tick 이 10ms 라 `vTaskDelay` 로는 ms 를 못 맞춘다. 처음엔 `esp_rom_delay_us`
  busy-wait, 채택하면서 `esp_timer` one-shot + `xTaskNotifyGive` 로 교체(상한 20ms).
- **RX 3대**: rx_id 1·2·3 × 4ms = 4/8/12ms 로 10ms 주기를 넘는다. 2ms 가 절반만 갈라졌으니
  3ms(3/6/9)가 경계일 수 있다 — 실측 필요. 안 되면 프레임 축소(진폭 양자화)로 송신 창을 줄인다.

## 미검증

- RX 3대 동시 업링크. 2대에서 이미 약한 링크 7% 손실이라 완화 없이는 늘리지 않는다.
- 싱크의 RX 겸용.
