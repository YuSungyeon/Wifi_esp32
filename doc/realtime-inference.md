## 1. 목적과 범위

방 안의 상태를 `empty` / `static` / `motion` 중 하나로 **실시간 표시하고 기록한다.**
1차 목표는 논문 발표용 시연이지만, 설계 기준은 **상시 모니터링 서비스**다 — 몇 초 빠른
반응보다 **오탐이 적고 장시간 안정적인 것**을 우선한다.

| 항목 | 결정 |
|---|---|
| 실행 위치 | Mac 호스트 (SINK → USB 경로 그대로). 소형 PC 이식은 나중 과제 |
| 출력 상태 | `empty` / `static` / `motion` + **`deciding`(판단 보류)** |
| 기록 단위 | 상태가 바뀔 때만 이벤트 한 줄 |
| 범위 밖 | 사람 수 세기, 위치 추정, 보드 위 추론, 여러 방 동시 감시 |

## 2. 모델 둘, 판정 규칙이 그 위에 선다

상태를 내는 **3-class 모델**과 움직임 여부만 내는 **1단계 모델**을 함께 쓴다. 둘 다 진폭이고
담당자의 구조(`SharedEncoder`)·입력 변환(`amplitude_input`)을 그대로 쓴다. 각각 seed 3개의
softmax 평균이다.

| 항목 | 상태 모델 | 1단계 |
|---|---|---|
| 체크포인트 | `amp60/model_amp1500_all74.pt` | `amp60/model_motion3s.pt` |
| 창 | **1500 frame (15초)** | 300 frame (3초) |
| 출력 | `empty`/`static`/`motion` | `rest`/`motion` |
| 입력 | 진폭, RX 101/102/103 × raw 톤 `[38..63, 2..26]` = 153열 (공통) | |
| 파라미터 | 4,814 × seed 3 | 4,781 × seed 3 |
| 학습 | 74세션 (9/16·17·19·20) | 45세션 (9/16·17·19) |
| 봉인 평가 | **없음** ↓ | 9/20 단발 — 세션 30/30 · 창 0.9661 |

판단 간격은 둘 다 0.3초다. 엔진이 체크포인트의 `window_frames` 를 읽으므로 창을 바꾸면
코드 수정 없이 따라간다(`realtime/engine.py` `MODEL`·`STAGE1`).

**기본 모델에는 봉인 평가가 없다.** `all74` 는 가진 세션을 전부 학습에 넣은 것이라 남은
평가 날짜가 없다(9/10 빈 방 6세션은 `load_raw_amplitude` 가 공통 구간 부족으로 거부한다).
성능 근거는 **같은 창·같은 학습기로 날짜를 갈라 학습한 형제 체크포인트**에서 가져온다.

| 창 | 9/16·17 15세션 학습 → 9/19+20 | 9/19+20 59세션 학습 → 9/16·17 |
|---|---|---|
| 10초 | 59/59 · 창 0.938 | 12/15 · 창 0.753 |
| **15초** | **59/59 · 창 0.948** | **12/15 · 창 0.773** |
| 30초 | 59/59 · 창 0.964 | 13/15 · 창 0.828 |

**세션 단위로는 10·15·30초가 같고, 창 정답률만 창이 길수록 높다.** 실시간은 창 단위로
판단하므로 창 정답률이 낮은 것을 감수하는 대신 **반응이 빨라지는 쪽**(15초)을 골랐다. 그
교환의 실측은 §4 에 있다. 담당자 배포 체크포인트(`robust/model.pt`, 진폭 30초, 9/19+20 학습)도
`--model` 로 그대로 쓸 수 있다.

### 2단계(진폭 3초 + 위상 60초) 는 왜 쓰지 않았나

파일럿 15세션에서는 두 질문의 잘 되는 조건이 반대로 나왔고(사이클 12 움직임 0.987 /
사이클 11 위상 60초 정지 판정 우세), 그래서 2단계 구성을 설계했다. 이후 60세션이 확보되며
전제가 바뀌었다.

| 비교 (서로의 날짜로 교차 평가) | 세션 정답 |
|---|---:|
| 진폭 30초 단일 모델 — 60세션 학습 → 15세션 평가 | 12/15 |
| 위상 60초 — 15세션 학습 → 60세션 평가 | 58/60 |
| 위상 60초 — 60세션 학습 → 15세션 평가 | 14/15 |

위상 쪽이 조금 낫지만 시험 세션이 15개라 2개 차이는 우연과 구분되지 않는다. 반면 진폭
모델은 입력 계약·테스트·추론 진입점이 갖춰진 배포 산출물이고, 위상 모델은 저장된 가중치조차
없는 실험 코드다. 그래서 **실시간 경로는 단일 모델로 가고, 위상은 모델 담당과 협의할 근거
자료로 남긴다.** 2단계 구성의 실험 기록은 위 보고서에 있다.

### 1단계(움직임 여부)는 되살렸다 — 다만 상태 판단이 아니라 **화면용**이다 (2026-10-12)

위 결론은 상태 판단에 그대로 유효하다. 바뀐 것은 **표시**다. 파일럿의 두 측정을 다시 보면
2단계 구성의 두 절반은 가치가 반대였다.

| 파일럿 | 과제 | 입력 | macro-F1 | 세션 |
|---|---|---|---:|---:|
| 사이클 12 | 움직임 / 그 외 | 진폭 **3초** | **0.987** | 13/13 |
| 사이클 13 | empty / static 전용 | 위상 60초 | 0.852 | 8/9 |
| 사이클 11 | (비교) 3-class 모델의 empty·static 부분만 | 위상 60초 | **0.877** | 9/9 |

**1단계는 분리하면 이득, 2단계는 손해다.** 전용 empty/static 모델은 motion 세션이 빠져 학습
데이터가 3분의 2로 줄고, 움직임도 "사람이 있다"는 단서를 가르친다. 그래서 **1단계만** 만들었다.

`model_train/amp60/model_motion3s.pt` — 진폭 3초, 이진(`rest`/`motion`), 학습 9/16·17·19
45세션, **봉인 9/20 단발 평가**:

| | |
|---|---:|
| 세션 | 30/30 (재현율 rest 1.000 · motion 1.000) |
| 창 정답률 | 0.9661 |
| rest 창 p_motion | 평균 0.051 · 중앙값 0.044 · 95%ile 0.077 |
| motion 창 p_motion | 평균 0.834 · 중앙값 0.909 · 95%ile 0.967 |

| 기준 | 연속 창 | 덮는 시간 | 움직임 창 비율 | rest 오경보 (1.64시간) |
|---:|---:|---:|---:|---:|
| 0.70 | 3 | 3.6초 | 0.838 | 4.3회/시간 |
| 0.70 | 10 | 5.7초 | 0.838 | 1.2회/시간 |
| 0.90 | 3 | 3.6초 | 0.549 | **0회** |

**2026-10-13 부터 상태 판단에도 쓴다 — 게이트로.** 처음에는 화면 표시 전용이었다. 창 3초와
상태 모델의 시간 축이 달라 섞으려면 기준값을 다시 잡아야 했고, 그 근거가 없었기 때문이다.
합성 전환 시퀀스(§4)가 생기면서 운영점을 고를 수 있게 됐다.

규칙은 하나다 — **1단계가 연속 3창(3.6초) 동안 `p_motion ≥ 0.9` 이면 `motion` 을 후보로
먼저 낸다**(`realtime/engine.py` `_motion_now()`, `stage1_gate=(0.9, 3)`). 상태 모델이 15초
창을 채우기를 기다리지 않고 입실·보행에 먼저 반응하게 하는 장치다. 기준 0.9·연속 3창은 위
표에서 **rest 1.64시간 오경보 0회**인 운영점이다. `--no-gate` 로 끌 수 있다.

게이트는 `motion` **한 방향으로만** 작동한다. 빈 방·정지 판정은 여전히 상태 모델이 내린다 —
1단계는 "지금 움직이는가"만 알고 사람이 있는지 없는지는 모르기 때문이다.

"움직임 창 비율 0.838"은 놓침률이 아니다 — motion 세션 300초 내내 사람이 움직이지 않으므로
멈춘 구간을 rest 로 보는 것은 맞는 동작이다. `model_train/amp60/stage1_eval.py` 로 다시 잴 수 있다.

1단계는 화면의 **활동량 띠**로도 그대로 보인다(§8). 게이트가 왜 걸렸는지 사람이 눈으로
확인할 수 있어야 하기 때문이다.

### 앙상블은 쓰지 않는다 (2026-10-12 측정)

서로 다른 모델의 세션 평균 확률을 평균해 봤다(`model_train/analysis/ensemble_test.py`,
학습 불필요, 날짜 잠금 검사 포함).

| 평가 | 결과 |
|---|---|
| 배포 진폭(30초) + 위상 60세션(60초) → 9/16·17 15세션 | 12/15, 14/15 → 합쳐도 **14/15** |
| 위상 v1(60초5Hz) + v3(60초10Hz) + v2(90초10Hz) → 9/19 30세션 | 셋 다 29/30, **모든 조합 29/30** |

이득이 없을 뿐 아니라 **오류가 겹친다.** 창 길이가 2~3배 다른 위상 모델 셋이 똑같은 한
세션(9/19 s12)에서만 틀리고, 진폭·위상 쌍도 더 나은 모델의 유일한 오답(s33)을 공유한다.
오답이 모델 분산이 아니라 **세션 자체**에서 나오므로 평균·투표로는 고쳐지지 않는다.
특징 수준 결합(진폭+위상 한 입력)은 이미 나빠진다고 측정돼 있었다(파일럿 사이클 8).

**정확도는 결합이 아니라 데이터로 올려야 한다.** 평가 4건에서 어떤 조합도 최고 단일 모델을
넘지 못했다. 약한 둘을 합치면 최고 단일 모델과 같아지는 경우는 있었다(9/16·17).

### 위상 입력 채택 논의는 "차이 없음" 으로 닫힌다 (2026-10-12)

§2 는 오랫동안 "위상 쪽이 조금 낫지만 시험 세션이 15개라 2개 차이는 우연과 구분되지 않는다"
로 남아 있었다. 같은 학습기로 **양방향을 채우자 그 2개 차이가 방향에 따라 뒤집힌다.**

| 학습 → 평가 | 진폭 30초 | 위상 |
|---|---|---|
| 9/16·17 15세션 → 9/19+20 60세션 | **59/60 · 창 0.964** | 58/60 · 0.948 |
| 9/19+20 60세션 → 9/16·17 15세션 | 13/15 · 0.828 | **14/15 · 0.877** |
| 같은 창(30초)끼리 → 9/19 | **0.954** | 0.923 |

**입력 종류는 차이를 만들지 않는다.** 같은 창에서는 오히려 진폭이 낫고, 위상은 창을 60~90초로
늘려야 따라온다 — 지배 변수는 창 길이라는 §5 의 결론과 같다. 배포 모델도 특별히 약하지 않다
(같은 조건에서 우리 진폭 13/15, 배포 12/15). **실시간 경로를 위상으로 바꿀 근거는 없다.**
상세 표는 [amp60 README](../model_train/amp60/README.md).

**대신 드러난 것**: 배치 5개짜리 15세션이 같은 캠페인 30세션과 맞먹고, 배치 3개짜리 60세션은
배치 5개인 15세션을 0.828 로밖에 못 맞힌다. **조건 다양성이 세션 수를 이긴다** — §7 수집
계획에서 세션을 늘리기보다 배치·방·사람을 늘리는 쪽이 낫다는 뜻이다.

## 3. 데이터 흐름

```text
보드 → SINK → USB → ① csi_serial_reader.py (현행 그대로, .csi 저장)
                        │
                        ▼
                     ② 실시간 판단 프로그램 (신규)
                        · 저장 중인 .csi 를 tail 로 따라 읽는다
                        · 3-RX 를 tx_seq 격자로 정렬 (공식 전처리와 같은 규칙)
                        · 최근 W초 링버퍼 유지
                        · 0.3초마다 상태 모델 + 1단계 → 게이트 → 판정 규칙
                        ▼
                     ③ 출력: 상태 전환 이벤트 파일 + 제어판(GUI) 현재 상태 표시
```

**수집 코드는 고치지 않는다.** 판단 프로그램이 `.csi` 를 뒤따라 읽는 이유:

1. **원본이 남는다** — 오탐이 난 순간의 원시 데이터를 다시 볼 수 있다.
2. **재생(replay)이 곧 시험대다** — 같은 코드에 녹화 파일을 넣으면 오프라인 평가가 된다.
   반응 지연·오탐률 측정과 규칙 조정을 보드 없이, 발열 없이 반복할 수 있다.
3. 수집 경로는 "손대면 안 되는 것"(CLAUDE.md)이 많아 변경 비용이 크다.

대가는 파일을 거치는 1초 미만의 추가 지연이다. 수십 초 단위 판단에서는 무시할 수 있다.

**입력 계약**: 판단 프로그램은 `.csi` 의 raw I/Q 를 직접 읽는다(위상이 필요하므로).
JSONL(`csi_amp`, 진폭만)과 공식 전처리 계약은 바꾸지 않는다.

### 윈도는 거의 전부 겹친다

윈도 길이와 무관하게 **0.3초(30 frame)마다** 새 윈도를 만든다. 30초 윈도는 이웃과 99%,
60초 윈도는 99.5% 겹친다. 이웃 판단이 서로 비슷하므로 규칙에서 몇 개를 모아 흔들림을
거르기 쉽다. 반대로 **창 개수는 독립 표본이 아니다** — 평가는 세션·이벤트 단위로 한다.

## 4. 판정 규칙 (상태 기계)

설계의 뼈대는 물리적 제약이다: **빈 방 ↔ 정지 전환은 반드시 움직임을 거친다.** 사람이
들어오거나 나가려면 움직여야 하기 때문이다. 그래서 빈 방·정지 판정은 움직임이 끝난 뒤
한 번 내리고, 다음 움직임 전까지 쉽게 뒤집지 않는다. 이것이 장시간 오탐을 막는 핵심이다.

```text
        움직임 감지
   ┌──────────────────────────────────────────┐
   ▼                                          │
[motion] ──조용해짐──▶ [deciding] ──W초 동안 움직임 없음──┐
   ▲                        ▲                             │
   │                        └── 확신도 < 기준 ─────────────┤
   │                                                       ▼
   └──────── 움직임 감지 ◀──────────────── [empty] 또는 [static]
```

모델은 0.3초마다 3-class 확률을 낸다. 상태 기계는 그 위에서 **확신 기준**과 **유지 시간**만
건다(`realtime/state.py`). 1단계 게이트는 그 앞단에 있다(§2).

| 규칙 | 조건 | 값 |
|---|---|---|
| ① 확신 기준 | 최대 확률이 기준 미만이면 상태를 바꾸지 않고 `deciding` | **0.60** |
| ② motion 유지 | 후보가 `motion` 이면 짧게 본다 — 입실·활동에 바로 반응 | 1초 |
| ③ empty·static 유지 | 후보가 `empty`/`static` 이면 오래 본다 — 깜빡임·오탐 억제 | **5초** |
| ④ empty↔static 직접 전환 | 움직임을 거치지 않은 전환은 특히 더 오래. 사람이 들고 나려면 반드시 움직인다 | **10초** |
| ⑤ RX 저하 | RX 2대면 기준을 올려 계속 판단, 1대 이하면 `suspended` 로 멈추고 마지막 판단을 표시 | 0.85 |
| ⑥ 1단계 게이트 | 연속 3창(3.6초) `p_motion ≥ 0.9` 이면 `motion` 후보를 먼저 낸다 | 0.9 · 3창 |

**①③④ 는 2026-10-13 에 합성 전환 시퀀스로 다시 잡은 값이다**(이전: 0.70 · 15초 · 60초).
창이 30초에서 15초로 짧아져 판단이 덜 흔들리는 만큼 유지 시간을 줄일 수 있었다. 이 값들은
`realtime/evaluate_transitions.py` 의 인자로 그대로 바꿔 가며 다시 잴 수 있다.

**판단을 건너뛴 창은 후보 유지 시간을 지우지 않는다.** 공백으로 창이 안 나오는 것을 "확신
없음" 으로 넘기면 유지 시간이 공백마다 처음부터 다시 쌓여 상태가 영영 안 바뀐다. RX 끊김만
별도로 상태 기계에 알린다(`realtime/engine.py` `step()`).

### 전환 반응 — 합성 시퀀스 실측 (2026-10-18 재측정)

상태가 바뀌는 대본을 녹화에서 이어 붙여(`scripts/make_demo_session.py --plan state:sec --date`)
재생하고, **화면에 보인 상태가 정답과 같은 시간의 비율**을 잰다. `deciding` 은 틀린 것으로
센다 — 사람이 화면에서 보는 기준이다. 대본 T1 은 `빈 방 2분 → 보행 1분 → 정지 3분 →
보행 1분 → 빈 방 2분` (9분)이고, 날짜마다 그 날 세션에서 떠 왔다.

| 원본 날짜 | 시간 정확도 | 창 이후 | 빈 방 | 움직임 | 정지 |
|---|---:|---:|---:|---:|---:|
| 9/16 | **68.6%** | 70.6% | 86% | 87% | **40%** |
| 9/17 | 84.7% | 87.1% | 82% | 91% | 92% |
| 9/19 | 86.8% | 89.2% | 89% | 84% | 93% |
| 9/20 | 86.7% | 89.3% | 85% | 90% | 94% |
| **평균** | **81.7%** | | | | |

| 전환 | 지연 (초) |
|---|---|
| 빈 방 → 움직임 | 6.3 · 6.6 · 7.8 · 9.9 |
| 움직임 → 정지 | 10.2 · 12.0 · 15.3 · 17.7 |
| 정지 → 움직임 | 4.5 · 5.4 · 8.4 · 9.9 |
| **움직임 → 빈 방** | 20.1 · 25.8 · 29.1 · **36.6** |

**읽는 법 세 가지.**

1. **움직임이 시작되는 전환은 5~10초**다. 1단계 게이트가 상태 모델을 기다리지 않고 먼저
   `motion` 을 내기 때문이다. 30초 창 시절의 "30초 대본 2/5" 와 비교하면 다른 물건이다.
2. **사람이 나간 것을 아는 데는 20~37초**가 걸린다. 가장 느린 전환이고, 이것이 §1 의
   "오탐이 적은 쪽을 우선" 과 맞바꾼 값이다. 빈 방은 움직임이 멈춘 뒤 창이 다 차야 보인다.
3. **9/16 이 혼자 68.6% 로 낮고 정지 판정이 40% 다.** 9/16 은 배치 A·B 두 가지가 섞인
   날이고 세션이 7개뿐이라 학습에서 차지하는 비중도 작다. 평균만 인용하면 이 날이 묻힌다.

**합성의 한계는 그대로다.** 이어 붙인 경계는 사람이 실제로 움직여 생긴 변화가 아니라
불연속이다. 실제 지연은 이보다 나을 수도, 나쁠 수도 있다 — §6-② 로만 확정된다.

### 모델별 최소 유지 시간 (2026-10-12 실측, 네 모델)

> 아래 표는 **상태 모델 하나만** 썼을 때의 값이고, 당시 실시간 기본이던 30초 창 기준이다.
> 지금 기본은 진폭 15초 + 1단계 게이트이며 전환 실측은 위 절에 있다.

| 모델 | 창 | 움직임이 몇 초 이어져야 잡히나 | 전환 지연 | 30초 대본 |
|---|---|---:|---:|---:|
| 담당자 배포 진폭 | 30초 | **30초** | 3~27초 | 2/5 |
| 위상 30초 | 30초 | 미감지 | 12~24초 | 2/5 |
| 위상 60초 5Hz | 60초 | **20초** | 33초 | 1/5 |
| 위상 60초 10Hz | 60초 | **45초** | 33~36초 | 1/5 |

정지·빈 방의 유지 시간은 **측정하지 못했다** — 대조군(같은 클래스의 다른 세션을 끼움)이 먼저
반응해 합성 경계를 잰 값이 된다. 상세는
[phase60 README](../model_train/phase60/README.md) 의 "반응성" 절에 있다.

**창 길이가 반응성을 정한다.** 30초 창이면 진폭이든 위상이든 30초 대본에서 2/5, 60초 창이면
둘 다 1/5이다. 입력(진폭·위상)이 아니라 창이 지배한다.

### 짧은 움직임은 보고되지 않는다 (2026-10-02 실측)

정지 세션 가운데에 움직임 구간을 길이를 바꿔가며 끼워 넣고 배포 모델의 출력을 쟀다
(`model_train/phase60/transition_test.py`).

| 끼워 넣은 움직임 | 움직임 확률 최대 | 상태 기계 판정 |
|---|---:|---|
| 1 · 2 · 3 · 5 · 10 · 15 · 20초 | 0.11 ~ 0.13 | **정지** (반응 없음) |
| 30초 (창 전체) | 0.946 | 움직임 — 단 3초 동안만 |

**1초부터 20초까지 출력이 전부 같다.** 0.11 은 그 정지 세션의 자연 변동 수준이며, 끼워 넣은
움직임이 출력에 아무 영향도 주지 못했다는 뜻이다. 창의 3분의 2(20초)를 채워도 움직이지 않았다.

모델이 창 안의 신호를 **시간 평균·표준편차로 요약**하기 때문이다. 비례해서 반응하지 않고
창을 거의 다 채워야 뒤집힌다. 따라서 위 표의 "움직임 약 1초"는 **움직임이 계속 이어질 때**의
값이고, 20초쯤 걷다 앉는 사람은 `motion` 으로 한 번도 보고되지 않는다.

이 한계는 창 길이가 정한다. 짧은 사건을 잡으려면 짧은 창 모델이 따로 필요하다 — §2 의
1단계(진폭 3초)가 정확히 그 역할이다.

**이 절은 2026-10-13 이후로는 상태 판단에 더 이상 그대로 적용되지 않는다.** 1단계 게이트가
들어오면서 **3.6초 이상 이어지는 움직임은 상태 모델과 무관하게 `motion` 으로 보고된다**(§2·§4).
위 표는 **상태 모델 하나만 썼을 때**의 한계이며, 게이트를 끄면(`--no-gate`) 그대로 돌아온다.
남는 한계는 **3.6초 미만의 움직임**과, 움직임이 끝난 뒤 빈 방·정지를 가리는 데 걸리는
시간이다(§4 의 20~37초).

합성 시퀀스의 한계: 다른 세션에서 잘라 붙인 것이라 사람이 실제로 움직여 생기는 연속적인
변화와 다르다. 진짜 전환은 이보다 잘 잡힐 수 있다. 그러나 **창 길이로 인한 희석**은 그대로
드러난다.

**이벤트 기록**: 상태가 바뀔 때마다 `{시각, 이전 상태, 새 상태, 확신도, 근거 윈도 구간}`
한 줄. 이 기록이 반응 지연·오탐률 계산의 유일한 입력이다.

## 5. 윈도 길이 — 왜 15초인가

**2026-10-13 에 30초에서 15초로 바꿨다.** 그 전까지는 담당자 배포 체크포인트(30초)를 그대로
썼고, 창 길이는 모델 담당이 60세션 안에서 비교해 고른 값이었다.

| 창 | 창 F1 (9/19 development, 같은 특징·같은 선형 모델) |
|---|---:|
| 3초 | 0.914 |
| 10초 | 0.977 |
| 30초 | **0.997** |

우리 파일럿 실험도 독립적으로 같은 방향이었다 — 10초 → 30초에서 macro-F1 0.754 → 0.833,
60초에서 정지 판정이 더 올랐다(사이클 7·9·11). 창이 길수록 정지 상태 판정이 좋아지고
움직임 반응이 느려지는 교환이 있다.

**바꾼 이유는 그 교환의 값을 실제로 쟀기 때문이다.** §2 의 표대로 10·15·30초는 **세션 단위
정답이 같고**(59/59, 12~13/15) 창 정답률만 다르다(0.94 / 0.95 / 0.96). 즉 창을 줄여 잃는
것은 **창 하나하나의 정확도 0.016** 이고, 얻는 것은 **창이 차는 시간 15초**다. 전환이 잦은
실시간에서는 후자가 크다 — §4 의 전환 지연이 그 결과다.

창을 바꾸려면 모델을 다시 학습해야 한다. 엔진은 체크포인트의 `window_frames` 를 그대로 읽으므로
코드 수정 없이 따라간다. 10초 모델(`model_amp1000_all74.pt`)도 저장소에 있어 `--model` 로
바로 비교할 수 있다.

|---|---|---|---|
| ① | 새 날짜 holdout | 모델·규칙을 **전부 고정한 뒤** 새 날·새 배치 세션으로 1회만 평가 | 상태별 정답률, 세션 정답 |
| ② | 전환 반응 지연 | 대본대로 상태를 바꾸고(§7) 운영자가 전환 시점을 표시 | 전환 종류별 지연 중앙값·최대, 전환 중 오상태 시간 |
| ②′ | (대리) 합성 전환 | 녹화를 대본대로 이어 붙여 재생 — 보드 불필요 | **완료**(§4). 경계가 불연속이라 ② 를 대신하지 못한다 |
| ③ | 장시간 오탐 | 빈 방 수 시간 + 책상 정지 1시간 | 시간당 거짓 `사람 있음` / 거짓 `empty` 이벤트 수 |
| ④ | 다른 피험자 | 최소 2명 추가, 사람마다 기본 세션 | ①과 같은 지표를 사람별로 |
| ⑤ | RX 한 대 손실 | 기존 데이터에서 RX 를 한 대씩 빼고 재평가(3가지) — 보드 불필요 | 저하 폭, 특히 취약한 보드 위치 |

모델 자체의 교차 날짜 평가는 끝났다(§2). ①~⑤ 는 **실시간 경로 전체**(정렬 → 창 → 상태 기계)를
사람이 상태를 바꾸는 상황에서 재는 것이며, 단일 상태 5분 세션으로는 대신할 수 없다.

**진행 상황 (2026-10-18)**

| # | 상태 |
|---|---|
| ① 새 날짜 holdout | **미완** — 기본 모델(`all74`)이 가진 날짜를 전부 학습에 썼다(§2) |
| ② 전환 반응 지연 | **미완** — 실제 전환 세션 2건을 10/14 에 찍었으나 **정답이 없다**(아래) |
| ②′ 합성 전환 | **완료** — §4 |
| ③ 장시간 오탐 | 미완 |
| ④ 다른 피험자 | 미완 — 피험자 1명 |
| ⑤ RX 한 대 손실 | 미완 (보드 불필요, 언제든 가능) |

**② 는 왜 아직 미완인가.** 10/14 에 실시간 측정으로 `live` 세션 2건(528초·547초, RX 3대)을
찍었고 상태 전환 이벤트가 각각 17·15줄 기록됐다. 그러나 **`realtime_marks.jsonl` 도 세션
메모도 비어 있다** — 운영자가 언제 무엇을 했는지가 남지 않아, 기록된 전환이 맞는지 틀렸는지
판정할 기준이 없다. 지금 이 세션들로 할 수 있는 것은 "실시간 경로가 실보드에서 9분 동안
끊기지 않고 돌았다" 까지다.

`realtime/evaluate_transitions.py --truth-plan <상태:초> …` 가 대본 오프셋으로 정답을 만들어
주므로, **운영자가 따른 대본을 세션 메모에 적기만 하면** 이미 찍은 세션으로도 ② 를 낼 수 있다.

**holdout 봉인 원칙**: 평가용 데이터는 규칙 조정·모델 학습 어디에도 쓰지 않는다.
한 번 결과를 본 데이터는 더 이상 시험지가 아니다.

**전환 시점 기준 시각**: `.csi` 프레임에는 호스트 시각이 없다. 세션 매니페스트의
`started_at_unix_us` 와 100Hz `tx_seq` 로 환산하며 오차는 ±0.1초 수준이다 — 초 단위
지연 측정에는 충분하다.

## 7. 다음 수집 계획

1. **전환 세션 대본** (10분 예시): `empty` 2분 → 입실·보행 1분 → 착석 정지 3분 →
   기립·보행 1분 → 퇴실 후 `empty` 3분. 전환 시점마다 제어판의 **전환 표시** 버튼을 누른다.
   **버튼을 누르지 않았다면 대본이라도 세션 메모에 적는다** — 10/14 세션 2건이 정답 없이
   남은 이유가 이것이다(§6). 둘 다 없으면 그 세션은 ② 에 쓸 수 없다.
2. **전환 세션은 두 묶음**: 첫 묶음은 §4 규칙값 조정용, 다른 날 묶음은 봉인 평가용.
   **§4 상수는 이미 합성 시퀀스로 조정됐으므로**, 처음 찍는 실제 묶음은 조정용으로 쓰고
   봉인용은 그 뒤 다른 날에 찍는다.
3. **기본 세션**: 클래스 3종 × 배치 2개 — holdout 평가용.
4. **장시간**: 빈 방 야간 녹화(3-RX 기준 약 190MB/시간) + 주간 책상 작업 1시간.
5. **다른 피험자**: 섭외되는 대로 추가.

수집 절차·품질 판정은 [수집 프로토콜](collection-protocol.md) §7 을 따른다.

## 8. 화면 구성 (CLI·GUI 시안 확정 2026-09-28)

공통 원칙: **지금 상태가 가장 잘 보이고, 나머지는 문제가 생겼을 때만 찾게 한다.**
CLI 는 화면 공간 배분으로, GUI 는 글자 크기로 서열을 만든다. 상태 전환 이벤트는 화면과
무관하게 항상 파일에 기록된다 — 화면은 사람용이고, 지연·오탐률 계산은 파일로 한다.

### CLI (`--plain` 이면 한 줄 갱신 모드)

24행 기준 배분: 제목 1행 · **상태 블록 9행(40%)** · 이력 4행 · 상태줄 1행. 상태 블록은
왼쪽 위에 상태 한 단어만 두고 나머지를 비운다 — 여백이 강조 장치다. 아스키 큰 글자는 쓰지 않는다.

```text
┌─ MeshSense 실시간 ──────────────────────── 14:23:51 ─┐
│                                                      │
│      움직임                                          │
│                                                      │
│      2분 14초째                                      │
│      확신  ████████████████████░░░░░  87%            │
│                                                      │
├──────────────────────────────────────────────────────┤
│  14:21:37   빈 방  → 움직임     1.2초만에            │
├──────────────────────────────────────────────────────┤
│  99.8Hz  RX3  정상  s47 18분        [m]전환 [q]종료  │
└──────────────────────────────────────────────────────┘
```

활동량 줄(`활동`)은 확신 막대 바로 아래에 온다 — 1단계가 본 **최근 60초**를 24칸으로 접고,
칸마다 **최대값**을 쓴다. 평균을 쓰면 3초짜리 움직임이 묻혀 띠를 넣은 뜻이 없어진다. 값이
낮으면 공백에 가까워 아무 일 없을 때 화면이 조용하다. 1단계 체크포인트가 없으면 줄만 빠진다.

```text
│      정지                                            │
│      2분 14초째                                      │
│      확신  █████████████████████░░░  87%             │
│      활동  ▁▁▁▁▁▁▁▁▁▁▁▁▁ ███ ▁▁ ▁▁▁  최근 60초       │
```

- `deciding` 은 같은 자리에서 유지 시간 옆에 **남은 시간**을 함께 보인다.
- 화면이 좁아지면 **이력 → 테두리 순으로 버리고 여백은 마지막까지 남긴다.** 12행 미만이면
  한 줄 갱신 모드로 자동 전환한다.

### GUI — 새 **실시간** 탭 (탭 순서 맨 앞)

| 크기 | 요소 |
|---|---|
| 3.6rem 굵게·상태색 | 상태 단어 |
| 1.05rem | 유지 시간(굵게) + 시작 시각(흐리게) |
| 막대 + 숫자 | 확신도. 막대 위 세로선이 **판단 기준선**(0.7, 저하 모드 0.85) |
| 막대 아래 띠 | **활동량** — 1단계(창 3초)의 최근 3분, 칸마다 최대값. 상태색 주황, 높이로만 세기를 보인다. "상태 판단에는 쓰지 않습니다"를 띠 옆에 적는다 |
| 보통 카드 | **최근 60분** 상태 띠, 상태 변화 목록 |
| 0.8rem 흐리게 | 품질 태그·수집률·RX 대수·녹화 세션·모델 날짜 (한 줄) |

- 버튼은 `실시간 측정`(또는 측정 중이면 `종료`) · `판단 정지` · `전환 표시` 셋이다.
  `실시간 측정` 은 `live` 수집과 판단을 함께 시작한다(§9).
- **`전환 표시` 는 장식이 아니다.** 이 버튼이 §6-② 의 유일한 정답 입력이다 — 누르지 않고 찍은
  세션은 나중에 지연을 잴 수 없다.
- 제외: 모델 확률 전체, RX별 상세 수집률, 서브캐리어 파형, 하루 요약 — 다른 탭이나
  기록 파일에 있다.

**색 체계**: 빈 방 회색 · 정지 파랑 · 움직임 주황 · 판단 중 황토(빗금). 이 색이 상태 글자,
카드 왼쪽 6px 띠, 60분 띠, 변화 목록의 점에 **같은 뜻으로** 쓰인다. 카드 배경 전체를 칠하지
않는다 — 상태가 바뀔 때마다 화면이 통째로 뒤집히면 오래 켜 두기 어렵다. 빈 방일 때 화면이
가장 조용한 것이 의도다. 다크 모드는 상태색을 밝은 계열로 따로 둔다. 갱신되는 숫자에는
고정폭(tabular) 숫자를 쓴다.

**최근 60분 띠**: 상태 하나가 수십 분 이어지는 것이 정상이라 10분 창에는 변화가 거의 담기지
않는다. 60분을 기본으로 하고, 폭이 좁아 1분 미만 구간이 뭉개지면 최소 2px 로 그려 존재만
드러낸다.

### 신호 저하 시 동작

판단을 멈추는 대신 **기준을 높여 계속한다.** 모델 구조가 서브캐리어 시계열을 공유 가중치로
처리하고 통계로 풀링하므로 입력 시계열 수가 줄어도 계산은 성립한다 — 다만 2-RX 입력으로
학습·평가한 적이 없어 성능 저하 폭은 §6-⑤ 로 측정한다.

| 상황 | 동작 | 표시 |
|---|---|---|
| RX 3대 | 정상 판단 | 평소 화면 |
| RX 2대 | 계속 판단, 확신 기준 0.7 → 0.85 | 확신 막대 아래 한 줄 "RX 2대 · 저하 모드" |
| RX 1대 이하 또는 TX 끊김 | 판단 정지 | 원인 + **마지막 판단과 그 시각** |

`csi_store.LABELS` 에 넣지 않고 세션 이름으로만 허용하며, 학습·평가·내보내기에서 자동으로
빠진다(`csi_session.SESSION_LABELS`). 수집이 먼저 끝나는 경우는 스트림 정지뿐이라, 그때는
실시간 화면도 내리고 이유를 보인다.

세션 디렉터리에 남는 파일: `realtime_status.json`(현재 상태, 원자적 교체),
`realtime_events.jsonl`(상태 전환), `realtime_marks.jsonl`(운영자 전환 표시).

## 10. 문자 알림 (조건 → SMS)

> **상태: HISTORICAL — 2026-10-27 제거.** 알림은 이제 집 상태 서비스 클라우드가 판단하고 보낸다
> ([계획](plans/2026-10-23-home-service.md) §3.3·§3.5). 클라우드는 집 기기가 죽은 것까지 알 수 있고,
> 로컬과 클라우드가 둘 다 켜져 있으면 같은 상황에 문자가 두 통 갔다. 엔진은 이제 상태를 클라우드로
> **보내기만** 한다(`realtime.home.Sender`). `realtime/sms.py`·제어판 문자 알림 카드·`/api/sms` 는 지웠다.
> 아래는 그 설계의 기록이다 — `suspended` 가 `absent` 를 울리는 문제(§10.3)와 올라가는 모서리
> 규칙(§10.4)은 클라우드 설계로 옮겨 갔다.

**당시 상태: CURRENT** (2026-10-21). 실시간 판단이 도는 동안 조건을 지켜보다가 맞으면 SMS 를 보낸다.
발송은 [SOLAPI](https://solapi.com) Python SDK (`pip install solapi`).

### 10.1 어디서 도는가

**판단 엔진 안**이다 — `Engine.step()` 이 판단을 끝낸 뒤 `realtime.sms.Watcher.check()` 를 부른다.
제어판에서 상태 파일을 보고 검사하면 **브라우저를 닫는 순간 감시가 멈춘다.** 그건 알림이 아니다.
제어판은 설정을 고치고 기록을 보여 줄 뿐, 조건을 재지 않는다.

설정은 **판단마다 다시 읽는다.** 측정 중에 `알림 끄기` 를 눌렀는데도 문자가 계속 가면 끌
방법이 없다. 엔진은 이미 판단마다 `realtime_status.json` 을 쓰므로 작은 읽기 하나가 더
느는 것뿐이다.

### 10.2 규칙은 두 가지뿐

| `kind` | 조건이 참인 때 | 쓰는 곳 |
|---|---|---|
| `hold` | 그 상태가 **N분 내리 계속**됐다 | `suspended` 10분 → 보드가 죽은 것 |
| `absent` | **N분 동안 그 상태가 한 번도 안 나왔다** | `motion` 30분 → 안부 확인 |

둘은 같지 않다. `hold(static, 30)` 은 중간에 `empty` 로 한 번만 튀어도 처음부터 다시 쌓지만,
`absent(motion, 30)` 은 `static`·`empty` 를 오가도 성립한다. 사람이 자다 깨다 하는 것을 잡으려면
뒤쪽이다.

**"나타나면" 은 따로 없다** — `hold(X, 0)` 이 즉시 알림이다. 종류를 셋으로 늘리지 않는다.

`state` 로 쓸 수 있는 값은 `csi_store.LABELS` 셋(`empty`·`static`·`motion`)과 `suspended`
(RX 끊김)다. `deciding` 은 시작 직후 잠깐이라 규칙 대상이 아니다.

### 10.3 `suspended` 는 `absent` 시계를 되돌린다

RX 가 끊긴 동안은 **아무것도 관측하지 못한다.** 그 구간을 "움직임이 없었다" 로 세면,
보드가 죽은 날 `absent(motion, 30)` 이 울려 *사람에게 문제가 생겼다*고 말하게 된다 —
가장 나쁜 오보다. 그래서 `suspended` 인 동안은 모든 상태를 "방금 봤다" 로 쳐서 `absent` 시계를
되돌린다. 끊김 자체는 `hold(suspended, N)` 규칙이 맡는다.

**그래서 `suspended` 규칙이 없으면 알림 전체가 의미를 잃는다.** 보드가 죽어도 화면은 조용하고,
조용한 것이 정상으로 보인다. 알림을 처음 켤 때 `hold(suspended, 10)` 을 기본으로 하나 넣는다
(지울 수는 있다).

### 10.4 언제 보내고 언제 안 보내는가

- **올라가는 모서리에서 한 번.** 조건이 거짓→참이 될 때 보낸다. 참인 동안은 조용하다.
  이것이 없으면 `stride` 마다(0.3초) 한 통씩 나간다.
- **조건이 거짓이 되면 다시 무장한다.** 움직임이 생겼다가 또 30분 없어지면 그때 한 통 더.
- `repeat_min > 0` 이면 참이 이어지는 동안 그 간격으로 다시 보낸다. 기본 0(안 보냄).
- **하루 상한** `daily_cap`(기본 20). 정상 운용은 하루 1~2통이므로 20통을 치면 규칙이 잘못된
  것이다. 상한에 걸리면 발송을 멈추고 기록에 `capped` 로 남긴다.
- `dry_run` 이면 **보내지 않고 기록만** 한다. 30분 규칙이 제대로 걸리는지는 반나절을 기다려야
  알 수 있고, 규칙이 틀렸으면 그 확인에 요금이 든다.

### 10.5 설정과 기록 — 저장소에 들어가지 않는다

`mac_collector/solapi.json` **(`.gitignore`)**. `block_order.json` 과 같은 자리·같은 방식이다.

```json
{
  "enabled": false, "dry_run": false, "daily_cap": 20,
  "api_key": "", "api_secret": "", "from": "", "to": [],
  "rules": [{"id": "sus", "on": true, "kind": "hold",
             "state": "suspended", "minutes": 10, "repeat_min": 0}]
}
```

기록은 `mac_collector/sms_log.jsonl` — **세션 폴더가 아니다.** 하루 상한을 세려면 실행을
넘어 남아야 하고, 제어판도 "오늘 몇 통" 을 그 파일에서 읽는다. 한 줄은
`{wall, rule, text, to, ok, status, session}` 이고 `status` 는
`sent`·`dry`·`capped`·`error: …` 중 하나다. **실패를 조용히 묻지 않는다** — 문자가 안 왔을 때
"조건이 안 맞았나, 발송이 깨졌나" 를 이 파일에서 가른다.

### 10.6 문자 내용

규칙에서 만든다. 사람이 쓰지 않는다 — 단문(SMS)은 90바이트(한글 45자)라 직접 쓰면 넘쳐
장문으로 바뀌고 요금이 달라진다.

```text
[MeshSense] 움직임 없음 30분
10/21 14:32
```

### 10.7 아직 아닌 것

시간대 제한(밤에는 안 보내기), 조건 조합(A 이고 B), 카카오톡·이메일 경로, 수신 거부 처리.
넷 다 지금 쓸 데가 없다. `solapi` 가 없으면 규칙은 돌고 기록만 남으며 제어판이 설치하라고 적는다.

  담당자 배포 체크포인트(`robust/model.pt`)도 `new-date deployment validation pending` 이다.
- **장시간 운영을 재 본 적이 없다.** 가장 긴 연속 실행이 9분(10/14 live 세션)이다.
  시간당 오탐은 §6-③ 전까지 알 수 없다.
- **피험자 1명·단일 방**이다. 방 일반화는 주장하지 않는다.
- **모델 구조와 입력 변환은 담당자 것을 그대로 쓴다.** 실시간 경로는 체크포인트의 입력
  계약(창·톤 순서·클래스)을 읽어 따라가며, 전처리나 모델 구조를 자체적으로 바꾸지 않는다.
  다만 **기본 체크포인트는 더 이상 담당자 배포본이 아니다** — 창 15초가 필요해 우리 학습기로
  만든 `A-ours` 체크포인트다(§2·§5). 담당자와 맞출 사안이다.
- **9/19 s12 는 학습·평가 목록에서 빠져 있다** — `static` 라벨이지만 300초 내내 산발적
  움직임이 있어 프로토콜 정의를 벗어난다. `train_sessions.EXCLUDED_SESSIONS` 가 단일
  소스이고 데이터와 `session.json` 은 그대로다
  ([트러블슈팅 04](troubleshooting/04-session-labels.md) 2026-10-12).
