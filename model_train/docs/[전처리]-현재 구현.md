> 입력 계약: [JSONL record schema](../../doc/data-schema.md)

형태를 보존한 참고 자료다. 6절도 공식 설계를 이해하기 위해 남긴 기존 설명이며
설계 기준이 아니다. 현재 공식 전처리는 [`preprocess_3rx.py`](../preprocessing/preprocess_3rx.py),
공식 학습은 [`LSTM.py`](../lstm/LSTM.py)를 사용한다. 구형 `Preprocessing.py`는
파일을 import하는 순간 전처리를 실행하므로 공식 학습 코드에서 import하지 않는다.

## 1. 현재 설정

| 변수 | 현재 값 | 의미 |
|---|---:|---|
| `SESSION_DIR` | `.../20260525/session_2` | 읽을 session 경로. source에 고정 |
| `RX_IDS` | `[102]` | 사용할 RX ID 목록 |
| `F_S` | `100` | TX sequence 한 칸을 10ms로 보는 가정 |
| `WINDOW_SECONDS` | `3.0` | window 길이(초) |
| `STRIDE_SECONDS` | `0.3` | 다음 window까지 이동할 시간(초) |
| `WINDOW` | `300` | 한 window의 시간 sample 수 |
| `STRIDE` | `30` | window 사이의 sample 간격 |
| `SESSION_SECONDS` | `300` | 사용할 최대 session 길이(초) |
| `MAX_SESSION_SAMPLES` | `30000` | 사용할 최대 sequence 수 |
| `N_SUB` | `52` | 한 RX에서 사용할 amplitude 수 |
| `LABEL_NAME`, `LABEL`, `SPLIT` | `empty`, `0`, `train` | 현재는 source에 고정 |

현재 `RX_IDS` 길이를 `R`이라고 하면 현재는 `R=1`이다. 아래의 `T`는 보간 뒤
공통 sequence grid 길이, `N`은 최종 window 개수다.

## 2. 입력 JSONL record

전처리에 실제 사용하는 필드는 다음과 같다.

```json
{
  "device_id": 102,
  "tx_seq": 4871,
  "csi_amp": [/* amplitude 값 64개 */]
}
```

| field | Python 변환 | 전처리에서 쓰는 이유 |
|---|---|---|
| `device_id` | `int` | RX별 buffer의 key |
| `tx_seq` | `int` | TX가 공유하는 frame 순번. RX 정렬 기준 |
| `csi_amp` | `np.ndarray`, `float64`, `(64,)` 기대 | CSI amplitude 입력 |

코드는 `csi_amp[:52]`만 사용한다. 즉 입력 배열이 최소 52개라는 전제가 있으며,
길이 검증이나 유효 subcarrier 선택은 아직 구현하지 않았다.

## 3. 변수 흐름과 shape

```text
JSONL line
  → raw_json_lines
  → buffers[device_id]
  → rx_arrays[device_id]
  → seq_grid
  → aligned
  → windows
  → X, y
```

### 3.1 `raw_json_lines`

모든 `*.jsonl` 파일의 비어 있지 않은 줄을 문자열로 모은 list다.

```text
raw_json_lines: list[str], 길이 M
raw_json_lines[0]: '{"device_id": 102, "tx_seq": 4871, ...}'
```

`M`은 session 안의 모든 RX record 수의 합이다. 이 단계에서는 JSONL 전체 줄과
CSI amplitude가 메모리에 남으므로 긴 session에는 메모리 사용량이 커질 수 있다.

### 3.2 `buffers`

각 JSON 문자열을 파싱해 RX별 list로 나눈 값이다.

```text
buffers: defaultdict(list)
buffers[102]: list[tuple[int, np.ndarray]]
buffers[102][i]: (tx_seq, amp)

tx_seq: int
amp: float64 array, shape (64,) 기대
```

각 RX list는 `tx_seq` 오름차순으로 정렬된다. 현재 코드에는 중복 `tx_seq`나
순서 역전 record를 제거·검증하는 처리가 없다.

### 3.3 `rx_arrays`

`to_array()`가 각 RX buffer를 NumPy 배열 두 개로 바꾼 결과다.

```text
rx_arrays: dict[int, tuple[np.ndarray, np.ndarray]]
rx_arrays[102] = (seq, amp)

seq: float64 array, shape (T_102,)
amp: float64 array, shape (T_102, 52)
```

여기서 `T_102`는 RX 102가 저장한 record 수다. `amp`의 두 번째 축은
`csi_amp[:52]`이므로 52다.

### 3.4 `start_seq`, `end_seq`, `seq_grid`

선택한 RX가 모두 존재하는 sequence 범위를 구한다.

```text
start_seq = 선택한 RX들의 첫 seq 중 가장 큰 값
end_seq   = 선택한 RX들의 마지막 seq 중 가장 작은 값
end_seq   = min(end_seq, start_seq + 29999)

seq_grid: float64 array, shape (T,)
seq_grid = [start_seq, start_seq + 1, ..., end_seq]
```

코드는 TX가 목표 100Hz로 `tx_seq`를 하나씩 증가시킨다고 가정한다. 따라서
`seq_grid`의 한 칸을 10ms로 간주한다.

현재는 `RX_IDS=[102]` 하나만 선택하므로 “여러 RX가 함께 가진 범위” 계산은
실제로 RX 102의 첫·마지막 sequence 범위를 다시 사용하는 것과 같다. 다중 RX로
바꿀 때에만 `max(first seq)`와 `min(last seq)`가 공통 구간을 만든다.

### 3.5 `aligned`

`resample_to_grid()`는 RX 하나의 amplitude를 `seq_grid`에 맞춘다.

```text
resample_to_grid(...): float64 array, shape (T, 52)
aligned: float64 array, shape (R, T, 52)

현재 R=1:
aligned.shape == (1, T, 52)
```

각 subcarrier마다 `np.interp(seq_grid, seq, amp[:, k])`를 사용한다. 중간
`tx_seq`가 빠진 경우 앞뒤 amplitude를 직선으로 연결해 값을 만든다.

이 방식은 TX 100Hz를 가정한 PoC 처리다. 실제 RX 수신 시각을 복원하지 않으며,
긴 누락 구간이나 빠른 움직임을 선형 값으로 바꿀 수 있다. `np.interp`에 넣는
`seq`는 증가해야 하지만, 현재 코드는 중복·비단조 sequence를 검증하지 않는다.

### 3.6 `windows`

`aligned`에서 300개 sequence씩 잘라 만든 list다.

```text
처음 slice:            (R, 300, 52)
transpose 후:          (300, R, 52)
reshape 후 window 하나: (300, R * 52)

현재 R=1: window 하나의 shape = (300, 52)
windows: list[np.ndarray], 길이 N
```

window 시작 위치는 `0, 30, 60, ...`이다. `T >= 300`일 때 window 수는 다음과
같다.

```text
N = floor((T - 300) / 30) + 1
```

`T < 300`이면 코드가 warning을 출력하지만, 이후 `np.stack(windows)`는 빈 list
때문에 실패한다. 현재는 충분한 길이의 session을 전제로 한다.

### 3.7 최종 `X`, `y`

```text
X: float64 array, shape (N, 300, R * 52)
y: int64 array,   shape (N,)

현재 R=1:
X: (N, 300, 52)
y: (N,)
```

축의 의미:

| 배열 | axis 0 | axis 1 | axis 2 |
|---|---|---|---|
| `X` | window 번호 | 3초 안의 시간 sample 300개 | RX별 amplitude feature |
| `y` | window 번호별 class 번호 | 없음 | 없음 |

현재 `y`의 모든 원소는 `LABEL=0`이다. 예를 들어 `N=4`면 `y=[0, 0, 0, 0]`이다.

### 3.8 Shape를 표로 이해하기

현재 단일 RX 기준으로는 `X`를 **3초짜리 표를 여러 장 쌓은 것**으로 생각하면
된다.

#### Record 하나

한 번 수신한 CSI record에는 amplitude 64개가 있다.

```text
csi_amp = [a0, a1, a2, ..., a63]
shape = (64,)
```

현재 코드는 앞의 52개만 사용한다.

```text
[a0, a1, ..., a51]
shape = (52,)
```

즉, 한 시점은 숫자 52개짜리 한 줄이다.

#### 시간순으로 쌓은 RX 하나의 표

```text
시간         sub0  sub1  sub2  ... sub51
tx_seq 100     10    21    15  ...    32
tx_seq 101     11    20    17  ...    31
tx_seq 102     13    22    16  ...    30
...            ...   ...   ... ...   ...
```

RX 하나의 전체 데이터는 다음 shape다.

```text
(T, 52)

T  = 전체 시간 sample 수
52 = 한 시점의 amplitude feature 수
```

예를 들어 5분을 100Hz로 사용하면 최대 `(30000,52)`다.

#### RX 축을 추가한 `aligned`

여러 RX를 처리할 수 있도록 RX 축을 앞에 둔다.

```text
aligned.shape = (R, T, 52)

R  = RX 개수
T  = 시간 sample 수
52 = RX 하나의 amplitude feature 수
```

현재는 `RX_IDS=[102]`이므로 `(1,T,52)`다.

```text
aligned
└── RX 102 표: (T, 52)
```

RX가 세 개라면 표가 세 장이다.

```text
aligned
├── RX 101 표: (T, 52)
├── RX 102 표: (T, 52)
└── RX 103 표: (T, 52)
```

#### 3초 window 하나

100Hz에서 3초는 시간 sample 300개다.

```text
(R, T, 52)
   ↓ 시간축에서 300개를 자름
(R, 300, 52)
```

현재 RX 하나의 window는 다음과 같은 표다.

```text
             amplitude 52개
          ┌─────────────────┐
시간 1    │  ... 52개 ...   │
시간 2    │  ... 52개 ...   │
시간 3    │  ... 52개 ...   │
...       │                 │
시간 300  │  ... 52개 ...   │
          └─────────────────┘

shape = (300, 52)
```

RX가 세 개면 같은 시각의 RX별 feature를 옆으로 붙인다.

```text
       RX101 52개   RX102 52개   RX103 52개
시간  ┌───────────┬───────────┬───────────┐
  1   │           │           │           │
  2   │           │           │           │
 ...  │           │           │           │
 300  │           │           │           │
      └───────────┴───────────┴───────────┘

52 × 3 RX = 156 features
window shape = (300, 156)
```

#### Window 여러 개를 쌓은 최종 `X`

3초짜리 window가 `N`개 만들어지면 다음과 같다.

```text
X.shape = (N, 300, R × 52)

현재 RX 1개: X.shape = (N, 300, 52)
향후 RX 3개: X.shape = (N, 300, 156)
```

각 축은 다음 순서다.

```text
X[window 번호][3초 안의 시간][CSI feature]
```

구체적인 index 예시:

```python
X[0]          # 첫 번째 3초 window, shape (300, 52)
X[0][10]      # 첫 window의 11번째 시각, shape (52,)
X[0][10][5]   # 해당 시각의 6번째 amplitude 값, 숫자 하나
```

라벨은 window마다 하나다. Window가 100개라면:

```text
X: (100, 300, 52)
y: (100,)
```

가장 짧게 정리하면 다음과 같다.

```text
record 하나      = amplitude 52개
3초 window 하나  = 300행 × 52열
전체 dataset X   = 3초 window N개
```

## 4. 실행 경계

폐기된 구형 `LSTM.py`가 다음 import를 실행하면 전처리 파일 전체가 실행됐다.

```python
from Preprocessing import LABEL, LABEL_NAME, SPLIT, X, y
```

따라서 구형 학습을 시작할 때 JSONL loading, 정렬, 보간, window 생성도 함께
실행됐다. 현재 공식 `LSTM.py`에는 이 import가 없으며, 공식 전처리가 저장한
`X.npy`, `y.npy`, `windows.jsonl`을 직접 읽는다.

## 5. 현재 한계와 공식 설계 연결

현재 한계:

- session path, RX ID, label, split이 source에 고정돼 있다.
- metadata reader 함수는 있지만 호출하지 않는다.
- `session_meta.yaml`의 `label_target=motion`은 코드의 `LABEL_MAP`
  (`empty`, `static`, `action`)에 없다.
- `csi_amp[:52]`는 유효 OFDM tone mapping이 아니다.
- 짧은 누락과 긴 누락을 구분하지 않고 같은 선형 보간을 적용한다.
- tensor와 metadata를 파일로 저장하지 않는다.
- 여러 session을 train/validation/test로 나누지 않는다.

다음 변경은 [공식 전처리 설계](%5B전처리%5D-설계.md)에 따라 구현한다.

1. CLI/config로 session과 RX 목록 입력
2. 중복·비단조 `tx_seq` 검증과 누락 정책 정의
3. 64개 feature 사용 정책과 subcarrier mapping version
4. session metadata 기반 label/split 검증
5. 여러 session을 session 단위로 train/validation/test 분리
6. tensor, label, device order, mapping version 저장

모델의 Tensor 변환과 학습은 [LSTM 모델 설계와 학습](%5B모델%5D-장단기메모리%20설계와%20학습.md)을 참조한다.

## 6. 참고: 공식 설계를 이해하기 위한 기존 설명

> 이 절은 교육용 shape·예시를 보존한 참고 자료다. 전처리의 공식 판정 규칙과
> 임계값은 [전처리-설계.md](%5B전처리%5D-설계.md)가 우선한다.

대상 경로:

```text
mac_collector_output/raw/20260616/
├── session_1  ~ session_10   → empty
├── session_11 ~ session_20   → static
└── session_21 ~ session_30   → motion
```

확인된 구성:

- session 30개가 존재한다.
- 각 session에 `device_101.jsonl`, `device_102.jsonl`, `device_103.jsonl`과
  `session_meta_snapshot.yaml`이 존재한다.
- metadata의 `label_target`은 위 session 범위와 일치한다.
- metadata의 `split_strategy`는 30개 모두 `train`이므로 실제
  train/validation/test 구분으로 사용할 수 없다.
- `session_22/device_102.jsonl`은 약 4KB다. 다른 RX 파일이 대체로
  35~40MB인 것과 비교하면 불완전 수집 가능성이 높다.

### 6.1 Label 계약

이 dataset의 class는 다음으로 고정할 계획이다.

```text
empty  → 0
static → 1
motion → 2
```

현재 코드의 `action → 2`는 dataset metadata의 `motion`과 맞지 않으므로 구현
전에 `motion → 2`로 변경해야 한다. `action`과 `motion`을 같은 class로 암묵적으로
취급하지 않는다.

### 6.2 Session 단위 split

window를 만든 뒤 무작위로 나누면 같은 session의 겹치는 window가 train과 test에
동시에 들어가 data leakage가 생긴다. 따라서 session을 먼저 나눈 다음 각
split 안에서만 window를 만든다.

품질 검사로 session 22를 제외한 뒤의 고정 split 초안:

| split | empty | static | motion | 합계 |
|---|---|---|---|---:|
| train | 1~6 | 11~16 | 21, 23~26 | 17 |
| validation | 7~8 | 17~18 | 27~28 | 6 |
| test | 9~10 | 19~20 | 29~30 | 6 |

empty·static은 6/2/2 session, motion은 5/2/2 session을 사용한다. Train의 class
수 차이는 window 수를 확인한 뒤 train에만 class weight를 적용할지 결정한다.
Validation과 test는 oversampling하지 않는다. Test session은 모델과
hyperparameter를 확정하기 전까지 사용하지 않는다.

#### Class weight란 무엇인가

`session_22`를 제외하면 motion의 train session은 5개이고 empty·static은 각
6개다. 실제로 만든 window 수도 motion이 더 적을 수 있다. 이때 많은 class만
잘 맞춰도 평균 loss가 작아지는 것을 막기 위해, 적은 class를 틀렸을 때의 loss를
더 크게 계산할 수 있다. 이 가중치가 class weight다.

예를 들어 train window 수가 다음과 같다면:

| class | train window 수 | 예시 weight |
|---|---:|---:|
| empty | 12,000 | 1.0 |
| static | 12,000 | 1.0 |
| motion | 8,000 | 1.5 |

motion 정답을 틀린 경우의 loss는 일반 오류보다 1.5배 크게 반영된다. CSI 입력을
바꾸거나 motion record를 복제하는 방법은 아니다. 적용 여부와 정확한 값은 실제
train window 수를 확인한 뒤 validation 결과로 정한다. Validation과 test의
데이터나 평가지표에는 weight를 적용하지 않는다.

현재 metadata snapshot은 수집 당시 기록이므로 수정하지 않는다. 실제 split은
별도의 dataset manifest에 명시한다.

```yaml
dataset: 20260616
class_map:
  empty: 0
  static: 1
  motion: 2
train_sessions: [1, 2, 3, 4, 5, 6, 11, 12, 13, 14, 15, 16, 21, 23, 24, 25, 26]
validation_sessions: [7, 8, 17, 18, 27, 28]
test_sessions: [9, 10, 19, 20, 29, 30]
excluded_sessions:
  22: "device_102 has only 3 records; common interval is 3 frames (< 27000)"
```

이 manifest는 품질 검사 후 고정하며, 이후 실행에서 임의로 다시 섞지 않는다.

#### Manifest란 무엇인가

Manifest는 이 dataset을 어떻게 만들었는지 적어 둔 작은 YAML 구성표다. 코드가
자동으로 추측하게 두지 않고 다음 값을 고정한다.

- 각 session의 class 번호와 train·validation·test 소속
- 제외한 session과 제외 이유
- RX 결합 순서 (`[101,102,103]`)
- 공통 구간 길이, 관측률, 보간 gap, window/stride 같은 전처리 기준

따라서 나중에 전처리나 학습을 다시 실행해도 같은 session과 같은 규칙을 사용해
같은 dataset 구성을 재현할 수 있다. Test 성능을 본 뒤 더 유리한 session으로
바꾸는 일을 막는 기록이기도 하다.

### 6.3 목표 전처리 계약

다음 값은 구현 시 config와 manifest에 기록할 **초기 계획값**이다. 모델 성능을
확인한 뒤 test 결과에 맞춰 바꾸지 않는다. 조정이 필요하면 train·validation만
사용한다.

| 항목 | 계획값 | 의미 |
|---|---:|---|
| RX 순서 | `[101, 102, 103]` | feature를 결합하는 고정 순서 |
| `N_SUB` | `64` | RX 하나에서 우선 사용할 전체 amplitude 수 |
| boot small-seq 기준 | `10` | 역행 뒤 이 값 이하이면 재부팅 후보 |
| boot large-drop 기준 | `100` | 이 이상 `seq`가 감소하면 재부팅 후보 |
| 최소 공통 길이 | `27000 tx_seq` | 목표 5분 수집량의 90% 미만 session 제외 |
| 최소 RX 관측률 | `0.85` | 공통 grid 중 실제 record가 있는 비율 |
| 최대 보간 gap | `5 tx_seq` | 약 50ms 이하의 내부 gap만 보간 |
| window | `300` | 100Hz 기준 3초 |
| stride | `30` | 100Hz 기준 0.3초 |

`seq`는 RX 재부팅과 품질 검사에만 사용한다. 세 RX의 정렬 key는 `tx_seq`이며,
모델 입력은 `csi_amp`에서 만든 amplitude feature다.

### 6.4 목표 전처리 단계

```text
session별 JSONL 로드
  → 이전·현재·다음 record로 단일 손상값 제거
  → seq로 RX 재부팅 segment 분리
  → 정리 후 지속적인 tx_seq 감소가 없는지 검증
  → 3-RX 안정 segment의 가장 긴 tx_seq 교집합 선택
  → session 품질 gate
  → session 단위 split 고정
  → 공통 tx_seq grid와 존재 mask 생성
  → 짧은 내부 gap만 보간
  → 3-RX feature 결합
  → 3초 window 생성
  → train 통계로 normalization
```

#### 6.4.1 입력 검증

각 session에서 `device_101.jsonl`, `device_102.jsonl`, `device_103.jsonl`을
독립적으로 한 줄씩 읽는다. 최소 필드는 다음과 같다.

```text
device_id
seq
timestamp_us
tx_seq
csi_amp
```

필수 field가 없거나 숫자 변환이 실패한 record, `csi_amp`가 64개보다 짧은
record는 사용하지 않고 개수와 이유를 품질 보고서에 기록한다.

20260616 첫 학습에서는 `csi_amp` 64개 전체를 순서 그대로 사용한다. 따라서 RX
하나의 feature 수는 64개이고, RX 3개를 합친 한 시점의 feature 수는 192개다.
`csi_amp[:52]`처럼 앞부분만 자르지 않는다.

64개 중 null/DC/guard 위치를 제외할지, pilot을 별도로 다룰지, ESP32-S3의
`first_word_invalid`가 true인 frame을 어떻게 처리할지는 **차후 결정 사항**이다.
현재 수집 JSONL에는 이 flag가 저장되지 않았으므로, 첫 baseline에서는 임의로
제외·보간하지 않고 64개 전체를 동일하게 입력한다. 이후에는 다음 후보를
train·validation으로 비교해 결정하고, 결정한 mapping과 version을 manifest에
기록한다.

1. 64개 전체 사용(현재 baseline)
2. 물리적으로 활성인 subcarrier만 선택
3. `first_word_invalid`를 새 수집 frame metadata에 저장한 뒤 해당 frame만 처리

#### 6.4.2 RX 재부팅 segment

인접 record에서 다음 조건을 만족하면 새 RX boot 후보로 본다.

```text
current_seq < previous_seq
and
(current_seq <= 10 or previous_seq - current_seq >= 100)
```

일반적인 packet loss는 `seq`가 앞으로 건너뛰므로 이 조건과 다르다. `seq=0`이
JSONL에 반드시 존재한다고 가정하지 않는다. 재부팅 경계를 알린 record는
손상 가능성이 있으므로 학습에서 제외하고, 다음 record부터 새 segment를 만든다.
경계 뒤 record는 `seq`·`timestamp_us`·`tx_seq`가 연속적인지 검증한 뒤 사용한다.

실제 session 17·26 RX 102의 경계 record에는 비정상적으로 큰 `timestamp_us`와
불연속 `tx_seq`가 있었다. 따라서 기존 수집률 도구의 “`seq`와 시각이 함께 감소”
조건을 전처리에 그대로 사용하지 않는다.

작은 예제로 보면 다음과 같다.

| 읽은 순서 | `seq` | 판정 | 처리 |
|---:|---:|---|---|
| 1 | 2998 | 정상 | 기존 segment에 유지 |
| 2 | 2999 | 정상 | 기존 segment에 유지 |
| 3 | 0 | 재부팅 경계 후보 | 경계 record는 제외 |
| 4 | 1 | 새 boot의 정상 record | 새 segment 시작 |
| 5 | 2 | 정상 | 새 segment에 유지 |

반면 `2998 → 3001`은 순번이 앞으로 증가했으므로 재부팅이 아니라 중간에 두 frame을
받지 못한 경우다. 재부팅 검사는 `seq`가 **뒤로 돌아갔는지**를 먼저 본다.

#### 6.4.3 단일 손상 record와 `tx_seq` 검증

현재 운영 절차는 TX를 session마다 재부팅하지 않는다. TX firmware의 송신
counter는 TX를 처음 켜거나 실제로 reset할 때만 0으로 돌아가며, USB 수집 메뉴는
RX reader만 시작하고 TX를 제어하지 않는다.

20260616의 `2,583,125` record를 확인하면 `tx_seq` 감소는 8번 있지만 모두 다음
record에서 감소 전보다 큰 정상 값으로 즉시 복귀한다. 감소한 작은 값부터
`0,1,2,...`처럼 계속되는 실제 TX 재부팅 형태는 0건이다. 따라서 감소 한 번을
바로 TX epoch 경계로 사용하지 않는다.

segment를 만들기 전에 파일 순서의 `이전–현재–다음`을 비교한다.

```text
previous.tx_seq > current.tx_seq
and
next.tx_seq > previous.tx_seq
```

이 형태이면서 현재 `seq` 또는 `tx_seq`가 앞뒤 흐름에서 벗어나면 현재 record만
손상값으로 제외한다. 가운데 값이 비정상적으로 크게 튀는 경우도
`previous.tx_seq < next.tx_seq`인데 current가 그 사이에 없으면 같은 후보로
기록한다. CSI가 정상처럼 보여도 어느 TX frame인지 알 수 없으므로 해당 record의
CSI도 사용하지 않는다.

session 11 RX 103의 실제 예는 다음과 같다.

```text
정상: seq=17456,      tx_seq=617288
손상: seq=3288334404, tx_seq=2411
정상: seq=17459,      tx_seq=617291
```

손상 record를 제거하면 `617289~617290`의 2-frame gap만 남고, session 11의 공통
범위는 `599760~629722`, 총 `29963 frame`이다. 이 세션은 제외하지 않으며 3초
window `989개`를 사용할 수 있다.

단일 손상 record를 제거한 뒤에도 다음처럼 감소한 값이 계속되면 여러 epoch로
분할해 일부만 사용하지 않는다.

```text
50000 → 0 → 1 → 2 → 3
```

이는 예상 밖 TX 재부팅 또는 복구 불가능한 데이터 혼합으로 보고 session 전체를
제외한다. Mac 수신 시각 `received_at_unix_us`는 이 판정에 사용하지 않는다.

#### 6.4.4 세 RX의 공통 구간

세 RX의 안정 segment 조합마다 다음 교집합을 계산한다.

```text
common_start = max(rx101_start, rx102_start, rx103_start)
common_end   = min(rx101_end,   rx102_end,   rx103_end)
```

`common_start <= common_end`인 조합 중 공통 길이가 가장 긴 조합을 선택한다.
재부팅이 여러 번인 session에서 무조건 마지막 segment만 선택하는 것보다 사용
가능한 데이터를 더 보존할 수 있다.

예시 1:

```text
RX101: 200~400
RX102: 210~400
RX103:  50~400
공통:  210~400
```

RX 103은 50부터 가지고 있지만 RX 101은 200 이전, RX 102는 210 이전 데이터가
없다. 따라서 50~209를 공통 데이터로 취급하면 없는 값을 대량으로 만들어 내게
된다. 세 RX가 모두 범위 안에 들어오는 첫 값인 210에서 시작한다.

예시 2:

```text
RX101: 200~400
RX102: 210~410
RX103: 200~600
공통:  210~400
```

RX 103은 600까지 가지고 있지만 RX 101은 400에서 끝난다. 401~600까지 RX 101과
RX 102의 마지막 값을 반복하거나 직선으로 늘리면 실제로 측정하지 않은 움직임을
학습 데이터로 만들게 된다. 세 RX 중 가장 먼저 끝나는 400에서 종료한다.

가장 작은 시작값부터 가장 큰 끝값까지 합집합을 만들지 않는다. 공통 범위 밖은
선형 보간하거나 endpoint 값으로 채우지 않는다. `np.interp`는 입력 범위 밖에서
끝 값을 반복할 수 있으므로 반드시 교집합 내부에서만 호출한다.

RX별 전체 범위와 내부 누락을 눈으로 확인하는 진단 도구는
[RX별 `tx_seq` 범위 시각화](../../doc/postprocessing.md#4-current-rx별-tx_seq-범위-시각화)를
사용한다. 시각화 도구는 공통 범위를 계산하거나 전처리 결과를 보간하거나
session을 자동 제외하지 않는다. 세 RX 교집합은 전처리 구현에서 별도로 계산한다.

#### 6.4.5 Session 품질 gate

선택한 공통 구간에 다음 기준을 적용한다.

```text
세 RX 파일과 안정 segment가 모두 존재
단일 손상 제거 후 지속적인 tx_seq 감소가 없음
common_end - common_start + 1 >= 27000
각 RX 관측률 >= 0.85
```

RX별 관측률은 공통 범위 안의 고유 관측 `tx_seq` 수를 공통 grid 길이로 나눈
값이다. 20260616 데이터를 시각화 도구로 점검하면 session 22는 RX 102 record가
3개뿐이며 세 RX의 공통 구간도 `1364029~1364031`, 총 3 frame에 불과하다. 최소
공통 길이 27,000 frame을 충족하지 못하므로 제외된다. 나머지 29개 session은 이
초기 기준을 통과한다.

품질 검사는 label과 모델 결과를 사용하지 않고 모든 session에 같은 규칙을
적용한다. 통과한 session만 6.2의 train/validation/test manifest에 넣는다.

#### 6.4.6 `tx_seq` grid와 존재 mask

공통 교집합으로 정수 grid를 만든다.

```text
tx_grid = [common_start, common_start + 1, ..., common_end]
T = len(tx_grid)
```

같은 `tx_seq`의 세 RX record를 같은 grid index에 둔다. 중복 `tx_seq`는 정해진
규칙으로 하나만 남기고 중복 수를 보고한다. 정렬 배열과 별도로 실제 관측 여부를
유지한다.

```text
aligned:      float64, shape (3, T, 64)
present_mask: bool,    shape (3, T)
```

교집합은 양 끝의 공통 존재 범위만 보장한다. 내부에는 RX별 누락이 있을 수 있으므로
`present_mask`가 필요하다.

#### 6.4.7 결측값 정책

공통 범위 내부의 연속 누락 길이가 5 frame 이하일 때만 subcarrier별 선형 보간을
허용한다. 100Hz에서 5 frame은 약 50ms다.

```text
내부 gap <= 5 frame  → 선형 보간
내부 gap > 5 frame   → invalid 유지
공통 범위 바깥       → extrapolation 금지
```

긴 gap과 겹치는 3초 window는 제외한다. 보간 전후에도 mask와 보간된 frame 수를
남겨 session·window별 실제 관측률을 추적한다.

예를 들어 공통 grid가 `[210, 211, 212, 213, 214]`인데 RX 102에 212만 없다면
한 frame짜리 내부 gap이다. 211과 213의 측정값 사이를 선형 보간해 212를 만들 수
있다. 반대로 RX 102에 212부터 218까지 7개가 연속으로 없다면 허용 길이 5를
넘으므로 그 구간과 겹치는 window를 버린다.

#### 6.4.8 Feature 결합과 window

RX 순서 `[101,102,103]`을 고정해 feature 축으로 합친다.

```text
(3, T, 64)
  → transpose
(T, 3, 64)
  → reshape
(T, 192)
```

세 RX가 모두 유효하고 긴 gap이 없는 구간만 300 sample씩 자른다. 시작 index는
`0, 30, 60, ...`이며 서로 다른 session을 이어 하나의 window로 만들지 않는다.

```text
window 하나: (300, 192)
X: float32, shape (N, 300, 192)
y: int64,   shape (N,)
```

`seq`와 `timestamp_us`는 최종 feature에 넣지 않는다. `tx_seq`도 모델 feature가
아니며 window의 출처와 정렬 metadata로만 저장한다.

#### 6.4.9 Normalization

Feature별 평균과 표준편차는 train window에서만 계산한다. Validation과 test에는
train 통계를 그대로 적용한다.

```text
train      → mean/std 계산 및 적용
validation → train mean/std 적용
test       → train mean/std 적용
```

### 6.5 작은 데이터로 전체 과정 따라가기

실제 record는 RX마다 amplitude 64개를 쓰지만, 아래 예시에서는 표를 읽기 쉽게
RX마다 amplitude 두 개만 있다고 가정한다.

#### 1단계: 안정 segment의 범위를 구한다

```text
RX101 tx_seq: 200, 201, 202, 203, 204, 205
RX102 tx_seq:      201, 202,      204, 205, 206
RX103 tx_seq: 199, 200, 201, 202, 203, 204
```

각 RX의 시작과 끝만 비교하면 다음과 같다.

```text
common_start = max(200, 201, 199) = 201
common_end   = min(205, 206, 204) = 204
tx_grid      = [201, 202, 203, 204]
```

따라서 199, 200, 205, 206은 일부 RX에 실제 record가 있어도 사용하지 않는다.
그 값들은 세 RX가 함께 관측한 범위 밖에 있기 때문이다.

#### 2단계: 공통 grid에 실제 관측 여부를 표시한다

| RX / `tx_seq` | 201 | 202 | 203 | 204 |
|---|:---:|:---:|:---:|:---:|
| RX 101 | 있음 | 있음 | 있음 | 있음 |
| RX 102 | 있음 | 있음 | 없음 | 있음 |
| RX 103 | 있음 | 있음 | 있음 | 있음 |

이 표가 `present_mask`다. 범위 교집합은 양 끝을 안전하게 정하지만, RX 102의
203처럼 범위 **안쪽**에서 빠진 record까지 없애 주지는 않는다. 그래서 교집합과
mask가 둘 다 필요하다.

#### 3단계: 짧은 내부 gap만 보간한다

RX 102의 203은 앞의 202와 뒤의 204 사이에 있는 한 frame짜리 gap이므로 보간한다.
두 amplitude 중 첫 번째 값이 202에서 20, 204에서 24였다면 203은 22가 된다.

```text
20 ── 22 ── 24
202   203   204
      보간
```

이 값은 실제 측정값이 아니므로 `present_mask`는 여전히 `False`로 유지하고,
별도의 보간 여부도 기록한다. 보간했다고 실제 수신 record로 바꾸어 세면 안 된다.

#### 4단계: 같은 `tx_seq`의 RX feature를 옆으로 붙인다

`tx_seq=201`에서 단순화한 amplitude가 다음과 같다고 가정한다.

```text
RX101: [10, 11]
RX102: [20, 21]
RX103: [30, 31]
```

RX 순서 `[101,102,103]`을 고정해 한 줄로 합치면 다음과 같다.

```text
[10, 11, 20, 21, 30, 31]
```

예시에서는 `2 × 3 = 6`개 feature지만 실제 데이터는 `64 × 3 = 192`개다. 이
작업을 grid의 모든 시각에 적용하면 `(T,192)` 배열이 된다.

#### 5단계: 시간축을 3초씩 자른다

100Hz에서 3초는 300 frame이다. `(T,192)` 배열에서 연속된 300행을 자르면
window 하나가 `(300,192)`이 된다. 다음 window는 30 frame, 즉 0.3초 뒤에서
시작한다.

```text
window 0: tx_grid index   0 ~ 299
window 1: tx_grid index  30 ~ 329
window 2: tx_grid index  60 ~ 359
```

긴 gap이 한 칸이라도 포함된 window는 만들지 않는다. 서로 다른 session의 끝과
시작을 이어서 하나의 window로 만드는 것도 금지한다.

#### 이 예시의 핵심

- `seq`는 RX가 재부팅했는지 검사하는 값이다.
- `tx_seq`는 같은 TX frame을 세 RX 사이에서 맞추는 값이다.
- 교집합은 범위 바깥의 가짜 extrapolation을 막는다.
- `present_mask`는 교집합 안쪽의 실제 누락을 찾는다.
- 짧은 내부 누락만 보간하고 긴 누락이 포함된 window는 제외한다.

### 6.6 Shape 요약

| 단계 | shape | 의미 |
|---|---|---|
| JSONL record의 `csi_amp` | `(64,)` 기대 | reader가 만든 한 frame의 amplitude |
| RX별 선택 feature | `(T_rx,64)` | 첫 baseline은 amplitude 64개 전체 사용 |
| 공통 grid 정렬 | `(3,T,64)` | RX·시간·feature |
| RX feature 결합 | `(T,192)` | 시점마다 3×64 features |
| window 하나 | `(300,192)` | 3초 입력 |
| split별 `X` | `(N_split,300,192)` | 여러 window |
| split별 `y` | `(N_split,)` | class 번호 |

### 6.7 전처리 산출물

전처리 결과는 split별 Tensor와 재현 metadata로 저장할 계획이다.

```text
dataset_20260616/
├── manifest.yaml
├── quality-report.json
├── normalization.npz
├── train.npz
├── validation.npz
└── test.npz
```

`manifest.yaml`에는 class map, split, 제외 session과 이유, RX 순서, 모든 threshold,
subcarrier mapping version을 저장한다. `quality-report.json`에는 session·RX별
record 수, RX boot 경계, 단일 손상 record, 정리 후 남은 `tx_seq` 감소, 선택
segment, 공통 범위, 관측률, gap과 최종 window 수를 저장한다.

각 split 파일에는 최소 다음 값을 둔다.

```text
X:                   (N_split, 300, 192), float32
y:                   (N_split,), int64
session_id:          (N_split,), int
window_start_tx_seq: (N_split,), int
observed_ratio:      (N_split, 3), float32
```

`session_id`와 시작 `tx_seq`를 함께 저장해야 window 단위·session 단위 평가와
train/test 혼입 여부를 검증할 수 있다.

### 6.8 구형 코드의 구현 전 상태

이 절 전체는 당시 **PLANNED**였던 계약을 보존한 내용이다. 구형 `Preprocessing.py`는 단일 session,
`RX_IDS=[102]`, 무제한 `np.interp`, `(N,300,52)` 입력을 사용한다. 반면 PLANNED
계약의 목표 입력은 3-RX·64 feature 기준 `(N,300,192)`이며, 재부팅 segment,
단일 손상 제거, 3-RX 교집합, 품질 gate, mask와 split 저장은 현재 공식
`preprocess_3rx.py`에 구현되어 있다.

### 6.9 이해 확인

아래 답은 접어서 두었다. 먼저 스스로 판단한 뒤 펼쳐 본다.

1. RX 범위가 `100~500`, `120~480`, `90~700`이면 공통 범위는 어디인가?

   <details><summary>정답 보기</summary>

   `120~480`이다. 시작은 가장 늦은 120, 끝은 가장 이른 480을 사용한다.

   </details>

2. 세 RX의 범위가 모두 `100~500`이면 `present_mask`는 필요 없는가?

   <details><summary>정답 보기</summary>

   필요하다. 범위가 같아도 중간의 특정 `tx_seq` record가 일부 RX에서 빠질 수
   있다.

   </details>

3. RX 102에서 `seq`가 `4000 → 4003`으로 바뀌면 재부팅인가?

   <details><summary>정답 보기</summary>

   아니다. 순번이 앞으로 증가했으므로 두 record가 빠진 packet loss 후보다.
   재부팅 후보는 `seq`가 뒤로 돌아갈 때 검사한다.

   </details>

4. 공통 범위 안에서 7 frame 연속 누락이 발견되면 어떻게 하는가?

   <details><summary>정답 보기</summary>

   계획값인 최대 5 frame을 넘으므로 보간하지 않는다. 해당 구간과 겹치는 3초
   window를 제외한다.

   </details>

5. Normalization 평균과 표준편차를 전체 29개 session으로 계산하면 안 되는
   이유는 무엇인가?

   <details><summary>정답 보기</summary>

   Validation·test 분포가 train 변환에 미리 반영되어 data leakage가 생기기
   때문이다. Train session으로만 계산한 통계를 나머지 split에 그대로 적용한다.

   </details>

### 6.10 구현할 핵심 처리 로직

1. 파일 순서의 이전(A)·가운데(B)·다음(C) record를 비교한다. B를 제외했을 때
   A보다 C의 `tx_seq`가 커야 단일 손상 판정을 계속한다.
2. A와 C의 `seq`가 증가하는 같은 RX boot 구간에서는 B의 `seq` 또는 `tx_seq`가
   A와 C 사이를 벗어나면 B를 제거한다.
3. A와 C 사이가 RX 재부팅 경계이고 C의 `seq`가 10 이하라면, B의 `tx_seq`가
   A와 C 사이를 벗어난 경우에만 B를 제거한다. C는 새 RX segment의 시작으로
   남긴다.
4. 단일 손상 제거 뒤에도 인접 `tx_seq` 감소가 남으면 예상 밖 TX 재부팅 또는
   데이터 혼합으로 보고 해당 session을 제외한다.
5. `seq`가 감소하면서 새 값이 10 이하이거나 감소 폭이 100 이상인 지점에서 RX
   boot segment를 나눈다.
6. 선택한 세 RX segment의 시작 `tx_seq` 중 최댓값을 공통 시작으로, 종료
   `tx_seq` 중 최솟값을 공통 끝으로 정한다. 시작이 끝보다 크면 session을
   제외한다.
7. 공통 범위의 모든 정수 `tx_seq`를 grid로 만들고, RX별 실제 CSI를 해당 번호의
   위치에 배치한다. 실제 record가 있었는지는 `present_mask`에 별도로 남긴다.
8. 5 frame 이하의 내부 gap만 보간하고, 더 긴 gap과 겹치는 window는 제외한다.
9. RX 101·102·103 순서로 각 64개 feature를 결합해 시점당 192개 feature를 만든다.
10. session 경계를 넘지 않도록 길이 300, stride 30으로 3초 window를 생성한다.
