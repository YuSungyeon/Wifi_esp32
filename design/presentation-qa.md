# 1부 — 하드웨어·통신·데이터 규격

## Q1. 왜 ESP32-S3 를 썼나

### 한 줄 답

**Wi-Fi 칩이면서 CSI 를 API 로 꺼내 주는 보드**가 필요했고, 거기에 네이티브 USB 와
ESP-NOW 까지 갖춘 것이 ESP32-S3 였다. 셋 중 하나라도 빠지면 이 구조가 성립하지 않는다.

### 자세히

**① CSI 를 밖으로 내준다 — 이게 전제 조건이다**

CSI(채널 상태 정보)는 수신 칩이 복조하면서 내부적으로 항상 계산하는 값이다
(`H[k] ≈ Y[k] / X[k]`). 문제는 **대부분의 Wi-Fi 칩이 이걸 펌웨어 밖으로 안 내보낸다**는
것이다. ESP-IDF 는 `esp_wifi_set_csi_config()` 와 콜백으로 서브캐리어별 raw I/Q 를
그대로 준다. 이게 없으면 프로젝트 자체가 불가능하다.

> 노트북 Wi-Fi 칩으로 같은 걸 하려면 Intel 5300 용 패치 드라이버나 Nexmon 같은 펌웨어
> 해킹이 필요하다. — *문서엔 없음, 말로 보탤 것*

**② CSI 구성을 우리가 고를 수 있다**

`lltf_en` / `htltf_en` 을 따로 켜고 끌 수 있다. HT20 에서도 둘 다 켜면 LLTF(64) +
HT-LTF(64) 를 이어붙여 raw 256바이트(=128 SC)가 나오는데, **LLTF 만 남겨 64 SC 로
고정**했다. 모델 입력 shape 가 매번 같아야 하기 때문이다.

**③ 네이티브 USB-Serial-JTAG 가 들어 있다**

ESP32-S3 의 USB-C 는 외부 UART 브리지 칩(CP2102 등)이 아니라 **칩 안에 있는 USB** 다.
100Hz × 172바이트 ≈ 17KB/s 를 브리지 없이 그대로 흘린다.

부작용도 이것 때문에 생겼고 문서에 남아 있다 — **DTR/RTS 를 건드리면 보드가 리셋된다.**
브리지 칩용 관례대로 `dtr=False, rts=False` 를 눌러두면 오히려 리셋이 걸린다
(실측: 손대면 12초에 2회 재부팅, 손대지 않으면 0회).

**④ ESP-NOW 를 쓸 수 있다** → Q2

**⑤ 보드 5대가 전부 같은 하드웨어다**

TX 1 · RX 3 · SINK 1, 역할은 셋이지만 보드는 **모두 같은 ESP32-S3**다. 역할은 빌드
플래그로만 가른다(`CSI_UPLINK_ENABLED`, `CSI_RX_ID`). 고장 나면 아무거나 바꿔 꽂으면 된다.

**⑥ TX 는 전원만 있으면 된다**

TX 펌웨어에는 host 입출력 코드가 아예 없다. USB 포트가 모자라면 충전기에 꽂아 두면 된다.
방 안에 보드를 흩어 놓는 구조라 이게 중요하다.

### 받아칠 거리 — "보드가 약해서 느린 것 아닌가"

아니다. 초기 AP 경로에서 22Hz 천장에 막혔지만, **같은 보드로 토폴로지만 바꾸니 97.5Hz**
가 나왔다. 22Hz 는 ESP32-S3 의 한계가 아니라 구조의 한계였다.

### 근거

| 내용 | 위치 |
|---|---|
| CSI 설정(`lltf_en`/`htltf_en`), LLTF only + HT20 = 128바이트 | `doc/firmware.md` §4 |
| HT20/HT40 과 서브캐리어 수, HT40 을 안 쓰는 이유 | `doc/firmware.md` §2.1 |
| 네이티브 USB-Serial-JTAG, DTR/RTS 리셋 실측 | `doc/firmware.md` §9 |

| 22Hz 는 보드 한계가 아니었다 | `doc/troubleshooting/01-csi-rate.md` 2026-05-22 |

## Q2. ESP-NOW 가 뭐고 왜 그걸 썼나

### 한 줄 답

ESP-NOW 는 **AP 접속 없이 MAC 주소로 바로 주고받는 Espressif 독자 프로토콜**이다.
AP 경로로는 **22Hz 가 천장**이었는데 ESP-NOW 로 바꾸니 **97.5Hz** 가 나와서 썼다.

### ESP-NOW 가 뭔가

Wi-Fi 의 **물리계층(802.11)은 그대로 쓰되, 그 위의 것을 전부 건너뛴다.**

```text
일반 Wi-Fi:  AP 검색 → 인증 → association → DHCP → IP → UDP/TCP → 데이터
ESP-NOW:     채널만 맞추고 → MAC 주소로 바로 프레임
```

연결(association)이라는 상태가 없다. 그래서 끊길 것도, 재접속할 것도, IP 설정도 없다.

우리 설정:

| 항목 | 값 |
|---|---|
| Wi-Fi mode | STA (단, **association 없음**) |
| channel / bandwidth | 11 / HT20 고정 |
| rate | MCS0 LGI |
| 암호화 / power save | 없음 / 끔 |
| TX 송신 | broadcast peer `ff:ff:ff:ff:ff:ff` 로 4바이트 카운터, 10ms 마다 |

> "STA 인데 association 이 없다"는 말이 헷갈리면: STA 는 **라디오의 역할**이고
> association 은 **AP 에 접속하는 절차**다. 라디오만 STA 로 켜고 접속은 안 한 상태다.

### 왜 썼나 — 다섯 가지

**① CSI 는 "프레임을 받아야" 나온다**

채널을 측정하려면 누군가 규칙적으로 전파를 쏴 줘야 한다. ESP-NOW 는 그 자극을
**100Hz 로, 매번 똑같은 PHY 설정(HT20 MCS0 LGI)으로** 쏠 수 있다. 설정이 고정이라
CSI 의 모양도 매번 같다.

**② AP 경로는 실제로 막혔다 (이게 가장 센 근거)**

처음엔 SoftAP + UDP 로 만들었다. 결과는 **17~22Hz 천장**이었고, 원인은 확정됐다 —
AP/STA association + **DTIM 게이팅** + 자극·데이터 채널 공유. 코드와 설정 옵션을 전부
시도했지만 트리거율 5~10% 가 한계였다. ESP-NOW/USB 로 바꾼 뒤 **97.5Hz**.

움직임을 잡으려면 초당 수십~100회는 재야 하는데, 22Hz 로는 애초에 안 된다.

**③ broadcast 라 RX 를 몇 대든 늘릴 수 있다**

TX 는 **수신자를 모른다.** 같은 프레임을 RX 3대가 동시에 받아 각자 CSI 를 잰다 —
한 사건을 세 각도에서 보는 셈이다. 수신자 목록이나 IP 설정이 없으니 RX 를 더 놔도
TX 를 안 고친다.

**④ 보낸 번호표가 그대로 정렬 키가 된다**

TX 가 보내는 payload 는 4바이트 카운터 하나다. 이게 RX 헤더의 **`tx_seq`** 가 된다.
보드마다 시계가 달라 `seq`·`timestamp_us` 로는 3대를 못 맞추는데, "같은 전파를 받았다"
는 사실로 맞추는 것이다.

**⑤ 전원만 꽂으면 돈다**

접속 절차가 없으니 부팅하자마자 동작한다. 공유기도, 비밀번호도, IP 도 필요 없다.
집에서 따라 하기 쉬운 구조다.

### 대가 — 공짜는 아니었다

| 대가 | 어떻게 풀었나 |
|---|---|
| **맥북이 ESP-NOW 를 못 받는다** (Espressif 독자 규격이라 일반 Wi-Fi 클라이언트가 해석 못 함) | **싱크 보드 1대**를 둔다. RX 들이 싱크로 무선 업링크하고, 싱크만 USB 로 Mac 에 붙는다. 보드는 **TX 1 + RX 3 + SINK 1 = 5대**. 싱크가 RX 를 겸해 4대로 줄이는 것은 **아직 안 했다**(`남은 일`) |
| 같은 채널에 **TX 자극 broadcast 도 섞여 들어온다** | 싱크가 **프레임 서명(magic + version)** 으로 우리 프레임만 통과시킨다 → Q3 |
| RX 가 송신하는 동안 못 듣는다 (반이중) | 100Hz × ~300µs ≈ 3% 인데 실측상 구분되지 않음 (콜백 ~99Hz 유지) |
| RX 끼리 송신이 겹친다 | `CSI_UPLINK_OFFSET_MS` 로 송신 시점을 분산 (2-RX 손실 7.6% → 0.0%) |
| RX 가 서로를 CSI 로 잡는 자기오염 | **역할별 MAC** — RX 의 CSI 필터를 TX MAC(`1a:…:00`)에만 걸어 둔다 |

### 근거

| 내용 | 위치 |
|---|---|
| ESP-NOW 설정값, association 없는 STA 의 의미, TX 송신 loop | `doc/firmware.md` §2, §2.2, §3 |
| AP 경로 22Hz 천장 → ESP-NOW 97.5Hz | `doc/troubleshooting/01-csi-rate.md` |
| ESP-NOW/USB 단일 경로 채택 결정 | `doc/adr-poc-only.md` |
| 맥북이 못 받음 · 싱크가 필요한 이유 · N+1 | `doc/realtime-uplink.md` |
| 역할별 MAC, 송신 오프셋, 에어타임 | `doc/realtime-uplink.md` |

## Q2b. 왜 100Hz 로 수집했나 (TX 자극 주기)

### 한 줄 답

**모델이 100Hz 를 필요로 한 게 아니다.** 모델 입력은 0.1초 평균, 즉 **10Hz** 다. 100Hz 는
⑴ 시스템이 정상인지 재는 계기판이고, ⑵ 나중에 깎아 쓸 여유이고, ⑶ **수집은 다시 할 수
없기 때문에** 남겨 둔 원본 해상도다.

### 먼저 정직하게 — 모델은 10Hz 만 쓴다

전처리가 100Hz 를 0.1초 평균으로 깎는다(30초 창 = 300칸). 그리고 **더 촘촘히 줘도
좋아지지 않았다** — 위상 모델 30초 창 실험에서 10Hz 0.9233, 20Hz 0.9216 이었다(진폭
모델에서 같은 비교를 한 기록은 없다). 100Hz 로 받는 것은 모델의 요구가 아니다. 이걸 먼저
인정하고 아래 셋을 말하는 편이 낫다.

### 그럼 왜 100Hz 인가 — 세 가지

**① 수집률이 곧 "시스템이 정상인가" 의 계기판이다.**
이 프로젝트에서 가장 오래 붙잡은 문제가 수집률이었다. AP+UDP 경로는 **17~22Hz 천장**이었고,
11단계를 실측해 원인을 확정한 뒤 토폴로지를 갈아서 97.5Hz → 99.5Hz 가 됐다. TX 가 **정확히**
100Hz 로 때려 주면 RX 쪽 숫자가 그대로 건강 지표가 된다 — 지금도 측정을 시작하면 Hz 를
먼저 본다. 떨어지면 뭔가 고장났다는 뜻이다(보드 리셋, 간섭, 콜백 블로킹). 100 이 둥근 수라
**"몇 % 빠졌나" 가 머리로 계산되는 것**도 의외로 큰 이점이다.

**② 깎을 수 있는 방향으로 틀렸다.**
10칸을 평균하면 칩 노이즈가 줄어든다. 그리고 100Hz 원본에서 프레임 몇 개가 비어도 0.1초
칸은 남은 샘플로 채워진다 — **10Hz 로 받았다면 한 프레임 손실이 칸 하나를 통째로 비운다.**
보간 정책이 "최대 5 frame 까지만" 인 것도 100Hz 라서 성립한다: 5프레임이 **50ms** 짜리
구멍이기 때문이다. 20Hz 였다면 같은 5프레임이 250ms 가 된다.

**③ 수집은 다시 할 수 없다.**
창 3·10·15·30·60·90초 비교, 0.1초 평균, 5/10/20Hz 다운샘플, 호흡 대역 스펙트럼 — 이
실험 전부가 **이미 저장된 raw 를 다시 돌려서** 나왔다. 같은 사람·같은 방·같은 날을 다시
찍을 수는 없다. 촘촘히 남겨 두는 비용은 디스크뿐이고, 모자라게 남기면 **그 실험 자체가
불가능**해진다.

나이퀴스트로 따지면 호흡은 0.2~0.5Hz, 사람 움직임은 수 Hz 다. 100Hz 는 분명히 과분하다.
**과분한 쪽이 되돌릴 수 있는 방향**이라서 과분하게 뒀다.

### 비용은 얼마였나

| 항목 | 값 |
|---|---|
| RX 한 대 대역폭 | 172B × 100Hz = **17.2KB/s** |
| 3대 × 5분 세션 용량 | 약 **15MB** (`.csi` 바이너리) |
| 반이중 에어타임 | 100Hz × ~300µs ≈ **3%** |
| CRC-32 부하 | 니블 테이블이라 무시할 수준 (실측 `crc_fail=0`) |

과분하게 받아도 쌌다. 참고로 정규화한 JSONL 로 저장하던 때는 같은 세션이 **120.9MB** 였고,
바이너리 v4 로 바꾸면서 **15.1MB** 로 8배 줄었다 — 100Hz 를 유지할 수 있었던 이유 중 하나다.

### 100Hz 는 어떻게 만드나 (물으면)

```c
usleep(1000 * 1000 / 100);   // 10ms 대기
```

그리고 **`CONFIG_FREERTOS_HZ=1000` 이 필수다.** 기본값 100 이면 tick 이 10ms 라
`usleep(10000)` 이 tick 경계로 반올림돼 **실효 50Hz** 가 된다. 삭제 금지 항목이고
`sdkconfig.defaults` 주석에 근거를 남겨 뒀다.

### 받아칠 거리 — "더 올릴 수 있었나"

**올려 본 측정은 없다.** 100Hz 에서 손실 0% 가 나오고 모델이 10Hz 로 충분했으니 올릴
이유가 없었다. 다만 반대 방향으로 단서가 있다 — 콜백 안에서 CSV 를 찍던 시절 921600 baud
처리 한계에 걸려 **~46Hz 까지 떨어졌다.** 즉 올릴 때 먼저 막히는 곳은 무선이 아니라
**호스트로 내보내는 길**이다. (상한 실측: 문서엔 없음 — 말로 보탤 것)

|---|---|
| 22Hz 천장 11단계 실측 → 97.5Hz → 100Hz 손실 0% | `doc/troubleshooting/01-csi-rate.md` |
| `usleep(10ms)`, `CONFIG_FREERTOS_HZ=1000` 없으면 50Hz | `doc/firmware.md` §110·§362 · `CLAUDE.md` |

## Q2c. 왜 채널 11 을 썼나

### 한 줄 답

중요한 것은 **"11" 이 아니라 "고정"** 이다. CSI 는 채널마다 주파수 응답이 달라서 채널이
움직이면 측정값의 의미가 바뀐다. 11 을 고른 것은 **2.4GHz 비중첩 채널 1·6·11 중 하나**이고,
esp-csi 예제가 쓰던 값(상수 이름이 `CONFIG_LESS_INTERFERENCE_CHANNEL`)을 그대로 이어받았다.

### 왜 "고정" 이 먼저인가

`H[k]` 는 **그 주파수에서의** 채널 응답이다. 채널이 1 → 11 로 바뀌면 중심 주파수가
2412MHz → 2462MHz 로 옮겨 가고, 같은 방·같은 사람인데도 톤별 값이 달라진다. 그래서

- TX·RX·SINK **세 펌웨어가 같은 채널에 못 박혀** 있다. 하나만 달라도 CSI 가 아예 안 잡힌다.
- **association 을 하지 않는 이유 중 하나도 이것이다.** AP 에 붙으면 AP 가 채널을 옮길 때
  (DFS·간섭 회피·재부팅) 끌려간다. STA-only 로 채널을 직접 박으면 아무도 못 옮긴다.
- 학습 자료 전부가 채널 11 에서 나왔다. **다른 채널로 옮겨도 모델이 먹히는지는 시험하지
  않았다** — 이건 열린 질문으로 남겨 두는 게 정확하다.

### 왜 하필 11 인가 — 1·6·11

2.4GHz 채널은 5MHz 간격으로 번호가 붙지만 한 채널이 **20MHz 를 쓴다.** 그래서 번호가 5 이상
떨어져야 겹치지 않고, 비중첩 조합은 사실상 **1 · 6 · 11 세 개뿐**이다. 7번이나 9번을 쓰면
옆에 있는 1번·6번·11번 AP 들과 **부분 중첩**해서, 서로 양보도 못 하면서 간섭만 받는다.

11 은 그 셋 중 **밴드 끝**이다. 1 과 6 은 양쪽에서 이웃을 받지만 11 위쪽(12·13)은 국내
공유기가 기본값으로 거의 쓰지 않아 한쪽만 이웃이 있다. 다만 **이 비교를 우리가 측정한
기록은 없다** — 1·6 과 비교해 11 이 깨끗했다고 말할 근거는 저장소에 없다.

### 왜 5GHz 가 아닌가

**ESP32-S3 는 2.4GHz 전용이다.** 선택의 여지가 없다. 덤으로 이쪽이 유리한 면도 있다 —
2.4GHz 가 벽 투과와 회절에 더 강해서, 방 하나를 훑는 용도에는 맞는 쪽이다.

### 간섭이 실제로 문제가 됐나

채널 11 에서 **~99.5Hz · 손실 0% · `crc_fail=0`** 이 나온다. 이 채널에서 간섭 때문에 막힌
적은 없다.

반대 방향으로 재미있는 기록이 하나 있다. AP 경로를 디버깅하던 중 `channel_filter` 를 끄자
CSI 콜백이 **182~763Hz 로 폭증**했다 — 주변 2.4GHz 트래픽이 전부 잡힌 것이다. 밴드가 붐비는
것은 사실이고, 그래서 **고정 채널 + MAC 필터**가 둘 다 필요하다. 채널만 고정해도 남의
프레임은 들어온다.

### 바꾸려면 (물으면)

| 파일 | 상수 |
|---|---|
| `esp32s3_csi_send_poc/main/app_main.c` | `CONFIG_LESS_INTERFERENCE_CHANNEL 11` |
| `esp32s3_csi_recv_poc/main/app_main.c` | `CONFIG_LESS_INTERFERENCE_CHANNEL 11` |
| `esp32s3_csi_sink/main/app_main.c` | `SINK_CHANNEL 11` |

**세 군데를 함께 고쳐 다시 구워야 한다.** 하나라도 남으면 그 보드만 조용해진다. 그리고
자료를 다시 모아야 한다 — 위에 적은 대로 채널 간 전이는 검증하지 않았다.

### 근거

| 내용 | 문서·코드 |
|---|---|
| channel 11 · HT20 · STA-only(association 없음) 고정 | `doc/firmware.md` §13·§22 · `doc/architecture.md` §172 |
| 상수 이름과 세 펌웨어의 정의 위치 | 위 표의 `app_main.c` 세 곳 |
| 채널 11 에서 99.5Hz·손실 0%, `channel_filter` off 시 182~763Hz 폭증 | `doc/troubleshooting/01-csi-rate.md` |
| 1·6·11 비중첩, 11 을 고른 비교 측정 | **문서엔 없음** — 일반 무선 상식 + upstream 기본값. 말로 보탤 것 |

## Q2d. 왜 HT20 을 썼나 (왜 HT40 이 아닌가)

### 한 줄 답

넓은 대역폭이 주는 것은 **속도**인데, 우리는 데이터를 빨리 보내려는 게 아니다. HT40 은
서브캐리어를 **64 → 128 개로 두 배**로 늘려 모델 입력 shape 를 흔들고, 전파를 두 배로
차지하고, 옆 채널과 겹칠 확률도 올린다. 얻을 것이 없고 치를 것만 있었다.

### 대역폭이 CSI 에서 뜻하는 것

일반 Wi-Fi 에서 대역폭은 "차선 수" 다 — 넓으면 빠르다. **CSI 관점에서는 "몇 개의 주파수
성분을 재는가" 다.**

| 대역폭 | OFDM 서브캐리어 | raw CSI 크기 |
|---|---:|---|
| **HT20** | **64** | **128 bytes** (I/Q pair 64개) |
| HT40 | 128 | 256~384 bytes |

### 서브캐리어가 많으면 좋은 거 아닌가 — 아니다

여기가 질문의 핵심이고, 숫자로 답할 수 있다.

- **64개도 이미 남는다.** 유효 LLTF 톤은 52개(`[1..26]+[38..63]`)뿐이고, 거기서도 이웃 톤은
  값이 거의 같아서 모델은 **3칸 간격으로 RX 당 17톤만** 쓴다. 128개를 받아도 "더 촘촘하게
  남는" 쪽이다.
- **비용은 정직하게 두 배다.** 프레임이 172B → 300B 급, 디스크·에어타임·USB 처리 전부 두 배.
  100Hz 를 유지하려는 설계(Q2b)와 정면으로 부딪친다.
- **얻는 것은 주파수 해상도**(multipath 지연 분해능)인데, 사람의 있음·없음·움직임을 가르는
  데 그 해상도를 쓰지 않았다.

### "HT20 이라서 64개" 가 아니다 — 좋은 이야깃거리

**처음에는 HT40 이었다.** 지금 구조의 첫 커밋(`38fe40a`, 2026-05-23)은 TX/RX 모두
`WIFI_BW_HT40` 였고, **같은 날** `237dd75`("ht40 -> 20")에서 HT20 으로 바꿨다. 그때
`htltf_en` 도 함께 껐는데, 이유가 중요하다.

> ESP32-S3 는 **HT20 에서도** `lltf_en` 과 `htltf_en` 을 둘 다 켜면 LLTF(64) + HT-LTF(64)
> 를 이어붙여 **raw 256 bytes(=128 SC)** 를 낸다.

즉 64개로 고정하려면 **HT20 과 LLTF-only 두 가지를 같이** 걸어야 한다. 대역폭만 좁혀서는
안 된다. Q1 에서 "ESP32-S3 는 두 훈련 구간을 따로 켤 수 있어서 64 SC 를 고정할 수 있다" 고
말한 지점이 바로 여기다.

| 훈련 구간 | 설정 |
|---|---|
| LLTF | `true` — CSI 계산에 사용 |
| HT-LTF | `false` |
| STBC HT-LTF | `false` |
| LTF merge | `false` |

### LLTF-only 는 "정보를 많이 모으려는" 설정이 아니다

문서에 못 박아 둔 표현이 정확하다 — **RX 간 데이터 shape 와 의미를 단순하고 일정하게
유지하기 위한** 조건이다. RX 3대의 shape 가 같아야 `tx_seq` 로 묶어 하나의 배열로 쌓을 수
있다. 한 대만 256B 를 내보내면 그 세션은 쓸 수 없다.

같은 이유로 ESP-NOW rate 도 **MCS0 LGI** 로 못 박았다 — 빠른 속도보다 **일정한 CSI shape 와
안정적인 반복 송신**이 먼저다.

### 받아칠 거리 — "HT40 이면 정확도가 올랐을 수도 있지 않나"

**비교 실험은 하지 않았다**(문서엔 없음). 다만 방향은 짚을 수 있다.

- 창 길이가 지배적 변수였다 — 3초 0.914 → 30초 0.997. **시간을 늘리는 쪽이 컸다.**
- RX 별로 톤을 나눠 쓰게 하자 배치 지문을 외워 **오히려 무너졌다**(사람 있음/없음 24/30).
  톤 정보를 더 주는 방향이 일반화에 유리하다는 증거가 없다.
- 톤 축에서는 오히려 **줄이는 쪽**(52 → 17톤, 증강으로 39톤만 무작위 사용)이 효과를 봤다.

### 바꾸려면

HT20 과 LLTF 설정은 **firmware 만 고치는 작업이 아니다.** `raw_len`·frame contract·모델
입력 shape 가 함께 바뀌므로 `doc/data-schema.md` 와 reader·후처리 문서를 같이 고쳐야 한다.

사족 하나 — 소스에 ESP32-C5/C6/C61 분기에 `WIFI_BW_HT40` 설정이 **아직 남아 있다.** 이
프로젝트가 빌드하는 대상은 S3 라서 그 분기는 실행되지 않는다. 코드를 보고 질문하면 이걸
묻는 것이다.

### 근거

| 내용 | 문서 |
|---|---|
| HT20/HT40 차이, 서브캐리어 수, "그래서 HT20 으로 고정한다" | `doc/firmware.md` §2.1 |
| `38fe40a` → `237dd75`("ht40 -> 20"), HT20+둘 다 켜면 256B | 같은 문서 §2.1 |
| LLTF-only 는 shape 일정 유지용, 변경 시 함께 고칠 문서 | 같은 문서 §4 (CSI 설정) |
| HT20 MCS0 LGI 고정 이유 | 같은 문서 §3-5 |
| 창 길이 지배적, RX별 분리 시 붕괴 | `doc/sprint/2026-08-collection-hardening.md` (2026-10-02) |
| HT20 vs HT40 정확도 비교 | **문서엔 없음** — 안 했다. 그대로 말할 것 |

## Q3. 데이터는 어떻게 보내나 — 경로

### 한 줄 답

**학습용은 USB 직결, 실시간은 무선으로 싱크를 거쳐** Mac 으로 온다. 두 경로에
**똑같은 프레임**이 흐르고, 싱크는 내용을 해석하지 않고 그대로 넘긴다.

### 두 경로

```text
학습 수집:  TX ──자극──▶ RX ──USB──▶ Mac
실시간:    TX ──자극──▶ RX × 3 ──ESP-NOW 업링크──▶ SINK ──USB──▶ Mac
           (전원만)      (전원만)                   (유일한 USB 연결)
```

RX 는 host 연결이 없으면 데이터를 버린다(링버퍼 4초치). 그래서 실시간으로 방 안에
흩어 놓으려면 무선 업링크가 필요하다.

**싱크는 프레임을 뜯어보지 않는다.** RX 가 만든 v4 프레임이 CRC 까지 그대로 Mac 에
도착한다. 덕분에

- host 파서가 **USB 직결과 완전히 같다** (`scripts/csi_store.py` 하나)
- 수집 도구를 그대로 쓴다 — reader 는 싱크 포트를 RX 인 것처럼 읽는다
- **프레임 규격이 바뀌어도 싱크는 고칠 게 없다**

### 보드 위에서는

CSI 콜백 안에서는 **아무것도 하지 않는다.** 프레임을 만들어 64KB 링버퍼에 넣고 즉시
빠져나온다. 콜백 안에서 동기 I/O 를 하면 Wi-Fi 드라이버 태스크가 막혀 ~50Hz 로 붕괴한다.
실제로 겪은 일이라 `CLAUDE.md` 의 "손대면 안 되는 것" 맨 위에 있다.

링버퍼는 **가득 차면 가장 오래된 것을 버린다**(keep-newest). 기본 동작은 반대라서, 그대로
두면 host 가 없는 동안 묵은 프레임이 버퍼를 점유해 수집을 시작한 순간 수십 초 전 데이터가
먼저 나온다(46초 방치 시 `tx_seq` 격자에 4134스텝 구멍).

**보드는 진폭 계산도, 정규화도 하지 않는다.** raw I/Q 바이트를 그대로 보내고 호스트가
처리한다. 저장 단계에 변환이 없어 변환 버그가 낄 자리가 없고, 위상 정보가 보존된다.

### 근거

| 내용 | 위치 |
|---|---|
| 두 경로, 싱크가 해석하지 않음, 수집 도구 재사용 | `doc/realtime-uplink.md` |
| 콜백 안 동기 I/O 금지, 보드 정규화 금지 | `CLAUDE.md` "손대면 안 되는 것" |
| 링버퍼 keep-newest, 백로그 비우기 | `doc/firmware.md` §9 |
| `.csi` 는 변환 없이 그대로 저장 | `doc/data-schema.md` §2 |

## Q4. 데이터의 형태는 — 프레임 규격

### 한 줄 답

**리틀엔디언 바이너리, 44바이트 헤더 + payload.** CSI 프레임은 payload 가 128바이트라
한 장에 **172바이트**다.

```text
[44바이트 헤더][payload]
     ↑              ↑
 메타데이터      CSI = 128B = 64 서브캐리어 × (I, Q) 각 int8
```

### 헤더 44바이트 (주요 필드)

| offset | type | 필드 | 뜻 |
|---:|---|---|---|
| 0 | `uint16` | `magic` | `0x4353` — 프레임 시작 표식 → Q5 |
| 2 | `uint8` | `version` | `4` — 규격 판 번호 → Q5 |
| 3 | `uint8` | `frame_type` | `0`=CSI · `1`=IDENT · `2`=SINK_STATUS |
| 4 | `uint16` | `total_len` | `44 + raw_len` — **길이의 정본** |
| 6 | `uint16` | `raw_len` | CSI=`128`, IDENT=`32`, SINK_STATUS=`48` |
| 8 | `uint32` | `seq` | RX 부팅부터 증가 — **보드마다 따로** |
| 12 | `uint64` | `timestamp_us` | RX 자기 타이머 — **보드마다 따로** |
| 20 | `int8` | `rssi` | 수신 세기 (dBm) |
| 26 | `uint16` | `boot_id` | 부팅마다 새 값 — 재부팅과 `seq` 되감김 구분 |
| 28 | `uint32` | `tx_seq` | **TX 가 보낸 번호표 — 3대를 맞추는 키** |
| 34 | `uint16` | `rx_id` | 싱크가 여러 RX 를 한 줄로 넘길 때 host 가 이걸로 가른다 |
| 40 | `uint32` | `crc32` | 전체 검사값 (zlib 호환) |

### 꼭 짚을 것 셋

**① `seq`·`timestamp_us` 로는 3대를 못 맞춘다**

보드마다 독립이다. 부팅 시점도 다르고 시계도 다르다. 그래서 정렬에는 반드시
**`tx_seq`**(TX 가 보낸 공통 번호표)를 쓴다. 두 RX 가 같은 `tx_seq` 를 들고 있으면
**같은 전파를 받은 것**이다.

`tx_seq` 를 정렬로 정리해서도 안 된다 — 역행은 TX 재부팅이라는 **사건**이고, 정렬하면
시간이 뒤집힌다.

**② 길이는 `total_len` 이 정본이다**

ESP-IDF 링버퍼(NOSPLIT)는 4바이트 정렬된 크기를 돌려준다. 그 값을 그대로 쓰면 실제
프레임보다 길 수 있다. 헤더가 말하는 길이를 쓴다.

**③ 프레임은 세 종류다**

| `frame_type` | 내용 | 왜 |
|---|---|---|
| `0` CSI | 측정값 128B | 본체 |
| `1` IDENT | MAC 6B + 펌웨어 문자열 + 진단 카운터 4개 | **보드를 리셋하지 않고 식별**하려고. esptool 로 포트를 프로브하면 보드가 리셋돼 `tx_seq` 가 끊긴다 |
| `2` SINK_STATUS | 싱크 MAC + 카운터 8개 | "RX 는 보냈다는데 host 엔 안 왔다" 가 싱크 드롭인지 USB 타임아웃인지 가른다 |

> 콘솔이 GPIO43 UART 로 나가 있어 `ESP_LOG` 가 USB 로 안 나온다(17초 캡처에 로그 0건).
> 그래서 진단 카운터를 **프레임에 실어** 보낸다.

### 저장되는 형태

```text
mac_collector_output/raw/<날짜>/<시각>_<라벨>_s<세션>/
    device_<id>.csi      ← 44B 헤더 + raw I/Q 프레임의 연속, 변환 없음
    session.json         ← 라벨 정본 + 코드 출처(git commit) + RX별 품질 통계
```

`.csi` 는 **배타적 생성**이라 append 되지 않는다. 옛 레이아웃은 append 였고, 실제로
여러 run 이 한 파일에 섞여 데이터를 오염시켰다(`20260615/session_21` 은 100번째 줄에서
`seq 158→0` 으로 되감긴다).

### 근거

## Q5. 매직(사인)은 뭐고, 버전을 담는다는 건 무슨 뜻인가

### 한 줄 답

**매직은 "여기서부터 한 프레임"을 알리는 표식**이고, **버전은 "이 바이트들을 어떤 규격으로
읽어야 하는지" 알리는 판 번호**다. 둘 다 **잘못 읽는 것을 막으려고** 있다.

### 매직 `0x4353` — 프레임의 시작 표식

**값의 정체**

```text
0x43 = ASCII 'C'
0x53 = ASCII 'S'       →  0x4353 = "CS" = CSI
리틀엔디언이라 선로에는 0x53 0x43 ('S' 'C') 순서로 나간다
```

**왜 필요한가**

USB 는 **바이트가 줄줄이 흘러오는 통로**일 뿐이다. "여기부터 한 프레임" 이라는 경계가
없다. 중간부터 포트를 열면(=항상 그렇다) 프레임 한가운데 들어와 있다. 그래서 매직을
찾아 **거기서부터** 읽기 시작한다. 깨지면 다음 매직을 찾아 다시 맞춘다(resync).

**싱크에서도 쓴다**

같은 채널에는 RX 업링크만 오는 게 아니다. TX 의 자극 broadcast(4바이트 카운터)도 같이
들어온다. 그대로 흘려보내면 프레임 사이에 4바이트가 끼어 host 가 **매 프레임 재동기화**
한다. 싱크는 **매직 + 버전**으로 우리 프레임만 통과시키고 나머지는 `foreign` 으로 센다.

**매직만으로는 부족하다 — CRC 가 생긴 이유**

payload 는 raw I/Q 바이트(int8)라 **아무 값이나 나올 수 있다.** 측정값 안에 우연히
`0x53 0x43` 이 나타나면 그 자리를 프레임 시작으로 오인한다. 가정이 아니라 **실제로
그렇게 저장된 레코드가 있다**:

```text
20260523/session_1 첫 줄:  channel = 159   (실제로는 11)
                           rssi    = +11dBm (양수일 수 없다)
                           timestamp_us 가 u64 범위 초과
```

v2 는 매직 2바이트와 `raw_len` 상한만 검사했다. **길이·범위 검사만으로는 못 막는다.**
그래서 v4 에서 **CRC-32(zlib 호환)** 를 넣었다 — 헤더의 `crc32` 를 0으로 둔 상태의
헤더+payload 전체를 계산해 비교한다. 우연히 일치할 확률은 사실상 0 이다.

### 버전 `4` — 규격의 판 번호

**무슨 뜻인가**

"이 44바이트를 **어떤 순서로, 어떤 크기로** 읽어야 하는가" 를 가리키는 번호다.
바이너리에는 필드 이름이 없다. 그냥 바이트가 붙어 있을 뿐이고, 몇 번째 바이트가 무엇인지는
**읽는 쪽과 쓰는 쪽이 같은 표를 보고 있다는 약속**으로만 성립한다. 버전은 그 약속의 이름이다.

**왜 필요한가 — 보드와 Mac 은 따로 업데이트된다**

보드 5대를 다시 플래시하는 것과 Mac 의 파서를 고치는 건 별개의 작업이다. 둘이 어긋나면,

```text
보드는 v3 로 보내는데 Mac 이 v4 로 읽는다
  → 필드가 한 칸씩 밀린다
  → 그런데 숫자로는 멀쩡해 보인다  ← 이게 제일 위험하다
```

조용히 틀린 데이터가 쌓인다. 버전을 보고 **모르는 판이면 읽지 않고 버린다.**

**실제로 올라온 번호다**

v2 → v4. v2 는 매직 + 길이만 검사했고, v4 에서 CRC-32 와 `boot_id`·`rx_id`·`gain_comp`
같은 필드가 들어왔다. 지금 `.csi` 와 `session.json` 에는 `frame_version: 4` 가 박혀 있어,
나중에도 그 세션이 어느 규격으로 찍혔는지 알 수 있다.

### 셋이 한 벌이다 — 세 겹 검사

```text
매직    → 여기가 프레임 시작인가?       (위치)
버전    → 내가 아는 규격인가?           (해석)
CRC-32  → 내용이 안 깨졌나?             (무결성)
```

셋을 다 통과해야 저장한다. 실측으로 `crc_fail=0`, `invalid=0`.

### 규격을 바꾸려면

문서를 먼저 고치고, **RX 펌웨어(C)와 Python 파서를 같은 변경에서** 고친다.
C 쪽에 `offsetof` static assert 가 걸려 있어 **한쪽만 고치면 빌드가 깨진다** — 어긋난
채로 데이터를 찍을 수 없게 막아 둔 것이다.

### 근거

| 내용 | 위치 |
|---|---|
| 매직·버전·CRC 계약, CRC 가 필요한 이유, 오염된 실제 레코드 | `doc/data-schema.md` §1 |
| 싱크의 프레임 서명 필터, `foreign` 카운터 | `doc/realtime-uplink.md` |
| `offsetof` static assert, 규격 변경 절차 | `doc/data-schema.md` §2, §5 |

## Q6. 왜 카메라가 아니고 Wi-Fi 인가

### 한 줄 답

**영상을 남기지 않고, 몸에 아무것도 차지 않고, 가만히 있는 사람도 보이는** 조합이
필요했다. 네 가지 수단을 놓고 보면 그 셋을 동시에 만족하는 것은 전파뿐이다.

### 자세히

| 수단 | 왜 안 됐나 |
|---|---|
| 카메라 | 가장 정확하다. 그리고 **영상이 유출되는 것이 가장 무섭다.** 집 안, 그중에서도 화장실·침실에 둘 수 있는 물건이 아니다 |
| 웨어러블 (워치·목걸이) | 차고 있을 때만 된다. **쓰러진 뒤에 버튼을 누를 수 있는 사람은 도움이 덜 급한 사람이다** |
| PIR 인체감지 센서 | 값싸고 흔하다. 그런데 **움직임의 변화만** 본다. 가만히 누워 있는 사람은 PIR 에게 빈 방과 똑같다 — 우리가 잡으려는 바로 그 상황을 못 본다 |
| mmWave 레이더 | 된다 — 상용 제품도 있다. 방마다 전용 하드웨어를 새로 달아야 하고, 우리는 **이미 있는 Wi-Fi 로 되는지** 를 보려 했다 |
| **Wi-Fi CSI** | 이미 집에 깔려 있는 전파를 쓴다. 벽을 통과하고, 조명·소리와 무관하고, **저장되는 것이 영상이 아니다** |

마지막 줄이 핵심이다. 우리가 디스크에 쓰는 것은 int8 64쌍 — 사람이 보아도 숫자다.
유출돼도 나오는 것은 `빈 방 / 정지 / 움직임` 세 글자와 시각뿐이다.

### 받아칠 거리 — "Wi-Fi 로도 사생활이 털리지 않나"

연구 수준에서는 CSI 로 자세·호흡·심지어 타이핑까지 추정한 사례가 있다. **우리가 만든
것은 그게 아니다.** 입력은 톤별 상대 진폭 51개 시계열이고, 출력 어휘는 세 가지
(`csi_store.LABELS`)다. 신원 식별·자세 복원은 범위 밖이고 주장하지 않는다. 이 구분을
먼저 말하는 편이 낫다 — 질문자가 노리는 지점이다.

## Q7. CSI 로 사람을 어떻게 구분하나 — 원리

### 한 줄 답

**보낸 신호를 알고 있으니, 받은 신호와 비교하면 그 사이 공기가 한 일이 남는다.**
사람이 그 공기 안에 있으면 그 "한 일" 이 달라지고, 움직이면 흔들린다.

### 자세히

보낸 신호를 `X[k]`, 받은 신호를 `Y[k]` 라 하면 채널은

```text
H[k] ≈ Y[k] / X[k]          k = 0 .. 63  (서브캐리어 번호)
```

OFDM 은 한 번 보낼 때 주파수를 64칸으로 쪼개 쓴다. 그래서 **한 프레임이 올 때마다
64개의 독립적인 측정**이 생긴다. 이게 CSI 가 RSSI(신호 세기 한 숫자)보다 훨씬 쓸모 있는
이유다 — 64칸은 각각 다른 경로 조합에 다르게 반응한다.

세 상태가 다르게 보이는 방식:

| 상태 | `H` 가 어떻게 보이나 |
|---|---|
| 빈 방 | 거의 변하지 않는다. 가구와 벽은 가만히 있다 |
| 정지 | 평균 모양이 빈 방과 다르다(사람 몸이 경로를 하나 바꿨다). 그리고 **아주 조금 흔들린다** — 호흡·무게 이동 |
| 움직임 | 크게 흔들린다. 몸이 움직이면 경로 길이가 계속 바뀐다 |

그래서 핵심 단서는 절대값이 아니라 **변화량**이다. "지금 이 톤이 평소 대비 얼마나
다른가" 가 입력이 된 이유(Q8)가 여기다.

### 정직하게 — 호흡을 봤다고 말하지는 않는다

30초 창이 3초보다 훨씬 잘 맞는 것은 측정됐다(창 F1 0.914 → 0.997). 긴 창이 호흡
주기를 담아서 그렇다는 **물리적 원인 검증은 하지 않았다.** 정규화·구조·학습 방식도
같이 바뀌었기 때문에 창 길이 하나의 효과로 돌릴 수 없다.

### 근거

| 내용 | 문서 |
|---|---|
| LLTF 64 서브캐리어, 유효 톤 `[1..26]+[38..63]` | `doc/data-schema.md` · `CLAUDE.md` |
| 창 길이별 F1, "원인 검증 수행하지 않았다" | `robust-three-class-report.md` §4 |

## Q8. 모델에 무엇을 넣나 — 전처리

### 한 줄 답

보드는 **raw I/Q 만** 보낸다. 호스트가 진폭으로 바꾸고, **상대 변화**로 바꿔서 넣는다 —
절대 세기는 버린다.

### 자세히

```text
3대의 .csi → tx_seq 로 정렬 → 세 RX 공통 구간 → 짧은 누락만 보간(≤5 frame)
  → 100Hz 를 0.1초 평균 (30초 = 300칸)
  → 톤별 윈도 평균(+0.5)으로 나눔 → 윈도 안에서 중심화 → ×3 → ±20 제한
  → RX 3 × 17톤 = 51개 시계열 × 300칸
```

**왜 나누는가(상대값).** 절대 진폭은 RX 가 TX 에서 몇 미터 떨어졌는지, 안테나가 어디를
보는지, 그 칩의 게인이 어떤지에 따라 그냥 달라진다. 윈도 평균으로 나누면 그 전부가
약분되고 **"이 톤이 평소 대비 지금 얼마나 다른가"** 만 남는다. 방이나 배치가 바뀌어도
덜 흔들리게 만드는 장치다. 학습 증강으로 RX 게인을 0.8~1.2 배 섞은 것도 같은 목적이다.

**왜 51톤인가.** 유효 LLTF 톤은 52개(`[1..26]+[38..63]`, DC 와 가드는 상시 0)다. 거기서
raw 인덱스 `[38..63, 2..26]` 51개를 쓰고, RX 당 3칸 간격으로 17톤만 고른다. 이웃 톤은
거의 같은 값이라 전부 넣어도 정보가 늘지 않는다.

**왜 보드가 아니라 호스트에서 하는가.** 두 가지다.

- CSI 콜백 안에서 계산하면 **Wi-Fi 드라이버 태스크가 막혀 수집률이 ~50Hz 로 붕괴**한다.
  실제로 겪은 일이고 금지 사항으로 적혀 있다.
- 전처리를 바꿀 때마다 **펌웨어를 다시 구워 보드 5대에 넣을 이유가 없다.** raw 를 그대로
  남겨 두면 저장된 자료로 전처리만 다시 돌릴 수 있다.

### 근거

| 내용 | 문서 |
|---|---|
| tx_seq 정렬·공통 구간·보간 ≤5 frame | `model_train/docs/preprocessing/design.md` §1~2 |
| 0.1초 평균, 나누고 중심화, ×3·±20, 51톤/17톤 | `robust-three-class-report.md` §5 |
| 콜백 동기 I/O 금지, 보드 정규화 금지 | `CLAUDE.md` "손대면 안 되는 것" |

## Q9. 모델 구조는 어떻게 되나

### 한 줄 답

**톤마다 똑같은 1D Conv** 를 돌려 시간 모양을 뽑고, 통계로 모아 3분류한다.
파라미터는 **모델당 4,731개** — 일부러 작게 만들었다.

### 자세히

| 단계 | 내용 |
|---|---|
| 입력 | 51개 시계열 × 300칸 (RX 3 × 17톤, 30초) |
| 톤 공유 Conv | 8 → 16 → 16 채널, kernel 5/5/3, stride 1, bias 없음, 각 뒤 BatchNorm+ReLU |
| 풀링 | 앞 두 묶음 뒤 AvgPool1d(2, 2) — 시간 300 → 150 → 75 |
| 모으기 | 시간축 통계 → 톤축 통계 → 분류 head (3클래스) |
| 앙상블 | seed 0/1/2 의 **softmax 확률 평균** |
| 학습 | AdamW 1e-3, weight decay 0.01, label smoothing 0.1, dropout 0.3, 15 epoch 고정 |
| 증강 | RX 게인 0.8~1.2, 51톤 중 **무작위 39톤만** 사용 |

**"톤 공유" 가 설계의 핵심이다.** 톤 번호마다 따로 가중치를 두면 모델은 "38번 톤이 이런
값이면 정지" 처럼 **그 방 그 배치 전용 암기**를 한다. 같은 필터를 모든 톤에 돌리면
배울 수 있는 것은 **"어느 톤에서든 이런 모양으로 흔들리면 움직임"** 뿐이다. 증강에서
톤 39개만 무작위로 쓰는 것도 특정 톤 조합에 기대지 못하게 하려는 같은 장치다.

**왜 이렇게 작은가.** 학습에 쓴 것이 60세션·윈도 1,124개다. 모델이 자료보다 표현력이
크면 외운다. 4,731개는 그 규모에 맞춘 값이고, 덤으로 **노트북 CPU 에서 0.3초 간격
추론**이 된다 — 실시간 경로가 GPU 없이 도는 이유다.

### 받아칠 거리 — "왜 LSTM/Transformer 가 아닌가"

저장소에 LSTM·1D-CNN 경로가 남아 있다(`model_train/lstm/`, `cnn1d/`). 자료 60세션
규모에서 더 큰 모델이 이기지 못했고, 통계 특징 + 선형 모델도 날짜 교차 session F1
0.93 을 냈다. **자료가 모델 크기를 정했다**는 쪽이 정직한 답이다.

### 근거

## Q10. 정확도는 얼마인가 — 숫자가 여러 개인 이유

### 한 줄 답

**세 가지 다른 질문에 세 가지 답**이다. 97% 는 같은 자료 안, 83.6% 는 처음 보는 날짜,

### 자세히

| 숫자 | 무엇을 쟀나 | 조건 |
|---|---|---|
| 창 **97.3%** / 세션 **30/30** | 날짜를 갈라 학습·평가 (9/19 ↔ 9/20) | **같은 2일 자료 안**. 가장 후한 숫자 |

## Q11. 모델이 확률을 내는데 왜 규칙을 또 두나 — 상태 기계

### 한 줄 답

모델은 **0.3초마다** 의견을 낸다. 사람의 상태는 0.3초마다 바뀌지 않는다. 그 사이를
**확신 기준과 유지 시간**으로 메운다.

### 설계의 뼈대는 물리다

**빈 방 ↔ 정지 전환은 반드시 움직임을 거친다.** 사람이 들어오거나 나가려면 움직여야
하기 때문이다. 그래서 빈 방·정지는 움직임이 끝난 뒤 한 번 판정하고, 다음 움직임이
오기 전까지 쉽게 뒤집지 않는다. 이것이 장시간 오탐을 막는 핵심이다.

```text
        움직임 감지
   ┌──────────────────────────────────────────┐
   ▼                                          │
[motion] ──조용해짐──▶ [deciding] ──W초 동안 움직임 없음──┐
   ▲                        ▲                             │
   │                        └── 확신도 < 기준 ─────────────┤
   │                                                       ▼
   └──────── 움직임 감지 ◀──────────────── [empty] 또는 [static]
```

| 규칙 | 값 | 왜 |
|---|---|---|
| 확신 기준 | 0.60 미만이면 `deciding` | 애매하면 바꾸지 않는다 |
| motion 유지 | **1초** | 입실·활동에는 바로 반응 |
| empty·static 유지 | **5초** | 깜빡임 억제 |
| empty ↔ static 직접 전환 | **10초** | 움직임을 거치지 않은 전환은 특히 의심 |
| RX 손실 | 3초 안에 프레임이 없는 RX 가 하나라도 있으면 `suspended` | 아래 |

**비대칭이 의도다.** 움직임은 1초, 빈 방·정지는 5초. 켜는 건 빨리, 끄는 건 천천히 —
잘못 "빈 방" 이라고 하면 **알림이 가지 않는다.** 틀리는 방향에도 값이 다르다.

**`suspended` 가 왜 필요한가.** RX 한 대만 끊겨도 판단을 멈춘다. 전에는 멈춘 창으로
마지막 상태를 계속 굳혀 보내고 있었다 — 실제로 고친 버그다(`3fff4f6`). "아무 일 없음"
을 확신 있게 보내는 것이 이 시스템에서 제일 위험한 실패다.

**판단을 건너뛴 창은 유지 시간을 지우지 않는다.** 공백을 "확신 없음" 으로 처리하면
유지 시간이 공백마다 처음부터 쌓여 상태가 영영 안 바뀐다. 이것도 겪고 고친 쪽이다.

### 정직하게

이 값들(0.60 · 5초 · 10초)은 **합성 전환 시퀀스로만** 조정됐다. 녹화를 이어 붙인
경계는 사람이 실제로 움직여 생긴 변화가 아니다. 실제 전환 세션 2건은 정답 라벨이 없어
검증에 쓸 수 없었다.

## Q12. 왜 창을 15초로 썼나

### 한 줄 답

**창을 줄여 잃는 것은 창 정확도 0.016, 얻는 것은 반응 시간 15초.** 전환이 잦은
실시간에서는 후자가 크다. 그 교환의 값을 실제로 재고 바꿨다(2026-10-13, 30초 → 15초).

### 자세히

창이 길수록 정지 판정은 좋아지고 움직임 반응은 느려진다 — 교환 관계다.

| 창 | 창 F1 (같은 특징·같은 선형 모델) |
|---|---:|
| 3초 | 0.914 |
| 10초 | 0.977 |
| 30초 | **0.997** |

여기까지만 보면 30초가 맞다. 그런데 10·15·30초를 실제로 재 보면 **세션 단위 정답이
같고**(59/59, 12~13/15) 창 정답률만 0.94 / 0.95 / 0.96 으로 다르다. 즉 15초로 줄여

# 3부 — 서비스와 한계

## Q13. 서비스는 왜 SQLite 와 표준 라이브러리로 만들었나

### 한 줄 답

저장할 것이 **집 하나당 하루 천 몇백 줄**이다. 그 규모에 DB 서버를 띄우면 **지켜야 할
프로세스가 하나 늘 뿐** 이고, SQLite 는 파일 하나라서 그 파일이 곧 백업이다.

### 실제 구성

```text
집 Mac ──HTTPS POST /api/state──▶ Caddy ──▶ 127.0.0.1:8000
   상태 바뀔 때 + 60초마다          (인증서 자동)   cloud/server.py 한 파일
                                                  http.server + sqlite3
                                                  /var/lib/meshsense/home.db
                                                        │
                                                   systemd · EC2 1대
```

외부 의존성은 **`solapi` 하나**다(문자 발송). 나머지는 전부 파이썬 표준 라이브러리다.

### 왜 SQLite 인가 — 네 가지

**① 쓰기량이 작다.** 집 기기는 상태가 바뀔 때와 60초마다 한 번 보낸다. 집 하나당 하루
약 1,500행이다. `events` 가 1년 쌓여도 수십 MB 다. 그리고 **동시에 쓰는 주체가 집 기기
1대**다 — 경합이 생길 구조가 아니다.

**② 운영 비용이 0 이다.** 프로세스 없음, 포트 없음, 비밀번호 없음, 버전 업그레이드 없음.
**DB 가 노출될 포트가 애초에 없다** — 보안 표면이 하나 사라진다. EC2 한 대로 돌리는
시연에서 "지켜야 할 서버 프로세스를 하나 더 늘리는 것" 이 가장 비싼 선택이다.

**③ 백업과 롤백이 `cp` 다.** 파일 하나를 복사해 두면 그게 스냅샷이다. 시연 전날
복사해 두고 무슨 일이 생기면 되돌린다. `pg_dump` 와 복구 절차를 배우고 문서화할 이유가
없었다.

**④ 배포가 짧아진다.** 파이썬에 들어 있으니 `requirements` 가 한 줄로 끝나고, 배포는
`rsync` + `systemctl restart` 다. 저장소 clone 도 필요 없다.

### 포기한 것 — 선이 어디인지 같이 말한다

| 포기한 것 | 지금 어떻게 하고 있나 | 넘어가면 |
|---|---|---|
| 동시 쓰기 | 연결 1개 + 전역 락. 요청이 직렬화된다 (`server.py: q()`) | WAL 켜고 요청마다 연결 |
| 서버 여러 대 | SQLite 는 파일이라 EC2 를 2대로 늘리면 못 쓴다. **지금은 1대** | Postgres(RDS) |
| 무거운 통계 질의 | 질의가 거의 다 "한 기기의 최근 N행" 이고 `events_since` 인덱스로 끝난다 | `events` 롤업 표 |

세 가지 모두 **코드에 주석으로 남겨 두었다** — `q()` 위의 `ponytail:` 주석이
"시연 규모에선 충분하고, 커지면 요청마다 연결" 이라고 적고 있다. 한계를 모르고 고른
것과 알고 고른 것의 차이는 그 한 줄이다.

### 받아칠 거리 — "실서비스에 SQLite 는 안 되는 거 아닌가"

**SQLite 가 느린 게 아니라 다중 서버를 못 하는 것이다.** 한 서버 안에서는 초당 수만
건을 읽는다. 우리 구조의 병목은 DB 가 아니라 **집 기기의 60초 하트비트**다 — 1초에
요청 하나도 안 온다. 서버를 2대로 늘려야 할 때가 오면 그때가 Postgres 로 가는 선이고,
바꿔야 할 코드는 `q()` 한 함수다.

### 같은 판단이 프로젝트 전체에 있다

| 곳 | 선택 | 대신 안 쓴 것 |
|---|---|---|
| 클라우드 | `http.server` + `sqlite3` 한 파일 | Flask/FastAPI + Postgres |
| 제어판 | `http.server` 한 파일, HTML 문자열 하나 | React + 빌드 도구 |
| 로컬 설정·연동 정보 | JSON 파일 (`0600`) | 로컬 DB |
| HTTPS | Caddy (도메인만 적으면 인증서 자동) | nginx + certbot |

설치 절차가 **"파이썬 3 하나"** 로 끝나는 것이 이 프로젝트의 운영 설계다. 졸업 후에
다른 사람이 이어받거나, 발표 당일 노트북이 바뀌어도 돌아가야 한다.

### 근거

| 내용 | 문서 |
|---|---|
| 표준 라이브러리 + sqlite3, Caddy, systemd, 테이블 목록 | `doc/plans/2026-10-23-home-service.md` §5 |
| 상태 전송 주기(바뀔 때 + 60초) | 같은 문서 §4.3 · `realtime/home.py` `HEARTBEAT_S` |
| 스키마, 연결 1개 + 전역 락 주석 | `cloud/server.py` `SCHEMA` · `q()` |

## Q14. 개인정보와 보안은 어떻게 다뤘나

### 한 줄 답

**가장 큰 대책은 영상을 만들지 않는 것**이고, 그 위에 비밀은 해시로, 키는 환경 변수로,

### 자세히

| 항목 | 처리 |
|---|---|
| 계정 비밀번호 | **scrypt** 해시 + 계정별 salt |
| 기기 토큰 | 32바이트 랜덤. 서버는 **SHA-256 해시만** 저장 |
| 세션 서명 키 | 환경 변수, 없으면 첫 실행 때 만들어 `0600` 파일로 (`.gitignore`) |
| SOLAPI 키·발신 번호 | **환경 변수** → `/etc/meshsense/secrets.env` (600). 저장소에 없다 |
| 전화번호 | 숫자만 저장(`01012345678`). 화면에만 `-` 를 붙여 보여 준다 |
| 메일·지인 인증 코드 | 10분 유효, **5번 틀리면 무효**, SHA-256 해시 저장, 재발송 60초 간격 |
| 미인증 계정 | **24시간 뒤 삭제** |
| 문자 상한 | 하루 40건 (서비스 전체) — 사고·악용이 요금으로 번지지 않게 |
| 관리자 화면 | `ADMIN_PASSWORD` 가 없으면 `/admin` 은 **404** — 빈 비밀번호로 열리는 일이 없게 |
| 전송 구간 | 서버는 `127.0.0.1` 에만 바인딩. HTTPS 는 앞단 Caddy |
| 지인에게 문자 | 본인 동의 절차(인증 코드)를 거친 번호만 |

그리고 Q6 의 결론이 여기서 다시 쓰인다 — **DB 가 통째로 유출돼도 나오는 것은
`빈 방/정지/움직임` 과 시각이다.** 영상도 음성도 없다.

## Q15. 한계는 무엇인가

| 상태 기계 값은 합성으로 조정 | 이어 붙인 전환 경계는 사람이 실제로 움직여 생긴 변화가 아니다 |
| 배치 민감도 | 9/16 배치에서 정지 판정이 40% 였다 (다른 날짜는 92~94%) |

### 전환 지연은 한계이자 설계값이다

빈 방 → 움직임 전환이 **6~10초** 걸린다. "넘어진 순간 즉시 감지" 는 아니다. 다만
응급 판단 자체가 **분 단위**(기본 60분 유지)라서 설계상 모순은 아니다. 즉시 감지가
필요한 요구에는 이 구조가 맞지 않는다고 말하는 편이 낫다.

### 다음 단계

1. **새 날짜·새 방 수집** — 설정을 고정한 채로 평가. 지금 가장 비어 있는 칸이다.
2. **긴 연속 실행** — 수 시간 돌려 시간당 오탐을 센다.
3. 실제 전환 세션에 정답 라벨을 붙여 상태 기계 값을 합성 아닌 자료로 재조정.
