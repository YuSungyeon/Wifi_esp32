# 발표용 전체 흐름 — 모델을 뺀 나머지

> 졸업발표에서 **말하는 순서**로 정리했다. 각 단계는
> **한 문장 요약 → 무엇을 했나 → 말할 거리(숫자) → 들어올 질문** 이다.
> 예상 질문의 상세 답은 [presentation-qa.md](presentation-qa.md) 에 있다.

---

## 한 장 그림 — 이걸 칠판에 먼저 그린다

```text
 ┌─ 1단계: 보드 ─────────────────────────────────────────────────────┐
 │  TX ──100Hz 자극 broadcast──▶  RX × 3  (CSI 측정)                 │
 │                                   │                               │
 │                     학습 수집: USB │  실시간: ESP-NOW 업링크       │
 │                                   ▼                               │
 │                              [Mac]        SINK ──USB──▶ [Mac]     │
 └───────────────────────────────────────────────────────────────────┘
 ┌─ 2단계: 모델 입력까지 ────────────────────────────────────────────┐
 │  프레임 172B 검증(매직·버전·CRC) → .csi 저장                      │
 │     → tx_seq 로 3대 정렬 → 공통 구간 → 0.1초 평균 → 상대 진폭     │
 └───────────────────────────────────────────────────────────────────┘
 ┌─ 3단계: 판단 ─────────────────────────────────────────────────────┐
 │  [모델]  0.3초마다 확률 3개                                        │
 │     → 상태 기계 (확신 0.60 · 유지 1/5/10초 · RX 끊기면 정지)      │
 │     → 빈 방 / 정지 / 움직임                                        │
 └───────────────────────────────────────────────────────────────────┘
 ┌─ 4단계: 서비스 ───────────────────────────────────────────────────┐
 │  집: 조명 판단 → 싱크 LED 켜고 끄기                                │
 │  집 ──상태 + 60초 생존신호──▶ 클라우드(EC2) ──▶ 웹앱 · 문자       │
 └───────────────────────────────────────────────────────────────────┘
```

# 1단계. 보드에 무엇을 넣었나

## 한 문장 요약

**펌웨어는 세 종류, 실시간 구성은 보드 다섯 대다.** 그런데 RX 와 싱크는 **같은 펌웨어**이고
빌드 플래그만 다르다.

## 무엇을 했나

| 펌웨어 | 역할 | 하는 일 |
|---|---|---|
| `esp32s3_csi_send_poc` | **TX** (1대) | 100Hz 로 ESP-NOW broadcast. 보내는 내용은 **4바이트 카운터** 뿐 |
| `esp32s3_csi_recv_poc` | **RX** (3대) | TX 프레임의 CSI 를 받아 프레임으로 포장 → USB 또는 무선 업링크 |
| `esp32s3_csi_sink` | **SINK** (1대) | RX 들의 업링크를 받아 **USB 로 그대로 전달**. 내장 LED 를 "집의 불" 로 씀 |

**보드 대수는 쓰는 모드에 따라 이렇다.**

| 모드 | 구성 | 보드 수 | USB 에 꽂히는 것 |
|---|---|---:|---|
| 학습 수집 | TX 1 + RX 3 | **4대** | **RX 3대 전부** |
| 실시간 | TX 1 + RX 3 + SINK 1 | **5대** | **싱크 한 대만** |

> **숫자를 틀리지 말 것** — 실시간 시연 구성은 **다섯 대**다(2026-09-10 실보드 검증).
> 싱크가 자기 CSI 도 함께 흘려 **네 대로 줄이는 것은 아직 "남은 일"** 이고 구현되지 않았다.
> 심사위원이 책상 위 보드를 세어 볼 수 있으니 여기서 틀리면 바로 드러난다.

**RX 를 플래시할 때 주는 플래그 세 개**

```bash
idf.py -DCSI_UPLINK_ENABLED=1 -DCSI_RX_ID=1 -DCSI_UPLINK_OFFSET_MS=4 -p <포트> flash
```

| 플래그 | 뜻 |
|---|---|
| `CSI_UPLINK_ENABLED` | `0` = USB 로 내보냄(학습 수집) · `1` = 무선 업링크(실시간) |
| `CSI_RX_ID` | 보드 번호. **MAC 과 헤더의 `rx_id` 가 이걸로 정해진다** |
| `CSI_UPLINK_OFFSET_MS` | 송신 시점을 `rx_id × 이 값` 만큼 밀어 **RX 끼리 충돌을 피한다** |

## 말할 거리

**ⓐ 보드가 전부 같은 하드웨어다.** 역할은 **펌웨어와 플래그**로만 갈린다.
TX 는 전원만 꽂으면 되고, 설정할 것도 없다.

**ⓑ 역할마다 MAC 을 다르게 박았다.** 이게 없으면 망가진다.

| 역할 | MAC | 왜 |
|---|---|---|
| TX | `1a:…:00` | **RX 의 CSI 필터 기준** — 이 MAC 의 프레임만 CSI 로 통과시킨다 |
| RX | `1a:…:<id>` | 보드마다 달라야 한다 |
| SINK | `1a:…:ff` | RX 가 여기로 unicast 로 보낸다 |

> 전부 같은 MAC 이면 **RX 가 서로의 업링크를 CSI 로 잡아 자기오염된다.** RX 의 필터가
> TX MAC 에만 걸려 있어서, 자기 업링크·다른 RX 의 업링크·싱크의 ACK 는 CSI 로 안 잡힌다.

**ⓒ 송신 시점을 밀어 충돌을 피했다.** RX 가 같은 순간에 올리면 부딪친다.
`rx_id × OFFSET_MS` 로 송신을 분산시켰다.

| 구성 | 결과 |
|---|---|
| RX 2대 (`rx_id × 4ms`) | **손실 7.6% → 0.0%** (2ms 는 1.05%로 부족) |
| RX 3대 (최고 배치, 2026-09-10) | 손실 **0.8~2.9%**, cross-RX 공통 `tx_seq` **97.2%** |

**3대에서는 0% 가 아니다** — 이 숫자를 섞지 말 것. 그리고 3대 구성에서 가장 효과가 컸던
변경은 오프셋이 아니라 **싱크 보드를 90도로 세운 것**(편파)이었다. 계속 최악이던 RX103 이
8.7% → 2.9% 로 떨어졌다. 다만 TX 위치도 같이 바꿔서 **회전 단독 효과는 분리하지 못했다.**

## 들어올 질문

- *"맥북이 직접 받으면 되지 않나?"* → **ESP-NOW 는 Espressif 독자 프로토콜**이라 일반
  Wi-Fi 클라이언트가 해석하지 못한다. 그래서 싱크 보드가 필요하다.
- *"왜 보드마다 MAC 을 다르게?"* → 위 ⓑ.
- *"왜 채널 11·HT20·100Hz 냐"* → QA Q2b·Q2c·Q2d.

# 2단계. 모델 입력 직전까지

## 한 문장 요약

**보드는 재서 담아 보내기만 하고, 해석은 전부 Mac 이 한다.**

## 보드 위에서 하는 일 — 딱 두 가지

```text
CSI 콜백(Wi-Fi 드라이버가 부른다)
   → 프레임으로 포장해서 64KB 링버퍼에 넣기만 하고 즉시 반환
            │
            ▼ (별도 task)
   링버퍼에서 꺼내 USB 또는 무선으로 내보내기
```

**콜백 안에서는 아무것도 안 한다.** 진폭 계산도, 정규화도, 출력도 안 한다.

> 이유가 실측으로 있다 — 콜백 안에서 CSV 를 찍어 보냈더니 **Wi-Fi 드라이버 태스크가 막혀
> 100Hz 가 46Hz 로 붕괴**했다. 그래서 "콜백 안 동기 I/O 금지" 가 금지 사항으로 적혀 있다.

링버퍼가 차면 **오래된 것부터 버린다.** 끊긴 구간이 생기는 게, 현재 데이터가 밀리는 것보다 낫다.

## 프레임 — 172바이트

```text
┌──────────────────────────┬────────────────────────┐
│  헤더 44B                │  CSI 128B              │
│  매직 0x4353 ("CS")      │  64 서브캐리어         │
│  버전 4                  │  × (I, Q) int8         │
│  tx_seq  ← 3대 정렬 키   │                        │
│  rx_id, rssi, 시각 …     │                        │
│  CRC-32                  │                        │
└──────────────────────────┴────────────────────────┘
```

**프레임 종류는 셋이다.**

| 종류 | 쓰임 |
|---|---|
| CSI | 측정값 |
| IDENT | "나는 RX 101 이다" — **esptool 로 포트를 찍어보면 보드가 리셋되니까** 프레임으로 알린다 |
| SINK_STATUS | 싱크의 수신·드롭·LED 수신 개수 — 불이 안 켜질 때 원인을 가른다 |

**싱크는 프레임을 해석하지 않는다.** 서명(매직+버전)만 보고 우리 프레임만 통과시키고,
TX 의 자극 broadcast 는 `foreign` 으로 센다. 그래서 **host 파서가 USB 직결과 똑같다.**

## Mac 이 하는 일 — 두 갈래

```text
① 검증·저장          csi_serial_reader.py
     매직 찾기 → 버전 확인 → CRC-32 → .csi 로 그대로 저장 (raw I/Q, 변환 없음)
                                │
     ┌──────────────────────────┴───────────────────────────┐
     ▼ 학습 경로                                   ▼ 실시간 경로
② export_jsonl.py                        ② 판단 엔진이 .csi 를 tail 로 따라 읽는다
     JSONL (진폭)                             (raw I/Q 직접 읽음)
     ▼
③ preprocess_3rx.py
     tx_seq 로 3대 정렬 → 세 RX 공통 구간 → 50ms 이하 누락만 보간
     → 0.1초 평균 → 톤별 상대 진폭 → 51톤 × 300칸
```

**실시간이 파일을 거쳐 가는 이유** — 원본이 남아서 오탐 순간을 다시 볼 수 있고, **같은
코드에 녹화 파일을 넣으면 그게 곧 오프라인 시험대**가 된다(보드 없이 평가·조정 가능).
대가는 1초 미만의 추가 지연인데, 수십 초 단위 판단에서는 무시할 수 있다.

## 말할 거리

**ⓐ 보드는 숫자를 가공하지 않는다.** raw I/Q 를 그대로 보낸다. 전처리를 바꿀 때마다
보드를 전부 다시 구울 이유가 없다.

**ⓑ 검증이 세 겹이다** — 매직(위치) → 버전(해석) → CRC-32(무결성). 실측 `crc_fail=0`.

**ⓒ 세 대를 맞추는 건 시계가 아니라 번호다.** `tx_seq` 가 같으면 같은 순간이다.
RX 자기 순번(`seq`)은 보드마다 따로 돌아서 정렬에 쓰면 안 된다.

**ⓓ `.csi` 는 append 하지 않는다.** 예전 구조에서 여러 실험이 한 파일에 섞여 데이터가
오염된 적이 있다. 지금은 **배타적 생성**이다.

## 들어올 질문

- *"매직·CRC 까지 과한 것 아닌가"* → QA Q4·Q5. **"틀린 데이터는 멈추지 않습니다. 학습됩니다."**
- *"세 대를 어떻게 시간 맞추나"* → 위 ⓒ. **"시계를 맞춘 게 아니라 안 쓰는 겁니다."**
- *"100Hz 를 그대로 모델에 넣나"* → 아니다. 0.1초 평균(10Hz).

# 3단계. 모델 결과를 실시간 판단으로 바꾸기

## 한 문장 요약

**모델은 0.3초마다 의견을 낸다. 사람 상태는 0.3초마다 안 바뀐다.** 그 사이를 상태
기계가 메운다.

## 설계의 뼈대는 물리다

> **빈 방 ↔ 정지 전환은 반드시 움직임을 거친다.** 사람이 들어오거나 나가려면 움직여야 한다.

그래서 빈 방·정지는 **움직임이 끝난 뒤 한 번** 판정하고, 다음 움직임 전까지 쉽게
뒤집지 않는다. 장시간 오탐을 막는 핵심이다.

```text
        움직임 감지
   ┌──────────────────────────────────────────┐
   ▼                                          │
[motion] ──조용해짐──▶ [deciding] ──W초 동안 움직임 없음──┐
   ▲                        ▲                             │
   │                        └── 확신도 < 기준 ─────────────┤
   │                                                       ▼
   └──────── 움직임 감지 ◀──────────────── [empty] 또는 [static]
```

## 규칙은 다섯 개뿐

| 규칙 | 값 | 왜 |
|---|---|---|
| 확신 기준 | 0.60 미만이면 `deciding` | 애매하면 바꾸지 않는다 |
| motion 유지 | **1초** | 입실·활동에는 빨리 반응 |
| empty·static 유지 | **5초** | 깜빡임 억제 |
| empty ↔ static 직접 전환 | **5초** | 움직임을 안 거친 전환도 후보를 5초 확인 |
| RX 손실 | 3초 안에 프레임 없는 RX 가 하나라도 있으면 **`suspended`** | 아래 |

**비대칭이 의도다.** 움직임은 1초, 빈 방·정지는 5초다. 켜는 건 빨리, 끄는 건 천천히 —
잘못 "빈 방" 이라고 하면 **알림이 가지 않는다.** 틀리는 방향에도 값이 다르다.

**`suspended` 가 왜 필요한가.** 전에는 RX 가 끊겨도 멈춘 창으로 마지막 상태를 계속
굳혀 보내고 있었다. **"아무 일 없음" 을 확신 있게 보내는 것이 이 시스템에서 제일 위험한
실패**라서, RX 한 대만 끊겨도 판단을 멈춘다.

**판단을 건너뛴 창은 유지 시간을 지우지 않는다.** 공백을 "확신 없음" 으로 처리하면
유지 시간이 공백마다 처음부터 쌓여 상태가 영영 안 바뀐다.

## 출력

판단 결과는 세션 폴더의 `realtime_status.json` 에 쓰인다. 제어판 화면, 싱크 LED,
클라우드 전송이 **모두 이 한 곳을 읽는다.**

## 말할 거리

**ⓐ 상태 기계가 깎는 몫을 측정했다.** 유지 시간을 0초로 두면 **81.7% → 85.4%**,
대신 화면 깜빡임이 **27번 → 44번**. 3.7%p 를 주고 안정성을 산 것이다.
**나머지 15%p 는 상태 기계와 무관하다** — 창 15초 지연과 모델 오차다.

**ⓑ 전환 지연은 6~10초다.** 즉시 감지는 아니다. 다만 응급 판단 자체가 분 단위라
설계상 모순은 아니다.

**ⓒ 값은 합성 전환 대본으로 조정했다.** 녹화를 이어 붙인 경계라서 실제 움직임과 다르다 —
이건 한계로 먼저 말한다.

# 4단계. 서비스

## 한 문장 요약

**집은 보고, 클라우드는 판단한다.** 조명은 집에서 결정하고, 알림은 클라우드가 결정한다.

## 왜 이렇게 나눴나 — 이게 핵심 설계다

> **집 시스템이 죽은 것은 집 밖에서만 알 수 있다.**

처음에는 집 Mac 이 직접 문자를 보냈다. 그런데 **집 기기가 꺼지면 아무 문자도 안 간다** —
가장 위험한 상황에서 가장 조용해진다. 그래서 알림 판단을 클라우드로 옮겼다
(로컬 문자 알림은 제거). 로컬과 둘 다 켜 두면 같은 상황에 문자가 두 통 가기도 했다.

## 집 쪽이 하는 일

**① 조명 판단** — 판단 결과로 싱크 LED 를 켜고 끈다.

| 상태 | 조명 |
|---|---|
| 빈 방 | 끈다 |
| 움직임 | 켠다 (수면 중에는 **N초 이상** 움직여야 — 뒤척임에 안 켜지게) |
| 정지 | 수면 중 가만히 **X분**이면 끈다 |
| 판단 중·판단 정지 | **건드리지 않는다** (모르면 그대로) |

**② LED 명령은 1바이트다.** `'1'` 켬 / `'0'` 끔. 1초마다 같은 값을 다시 쓴다.

- 1초 재전송이라 **싱크가 리셋돼도 1초 안에 원래 불로 돌아온다.** 변경 추적이 필요 없다.
- **유효한 명령이 10초 끊기면 싱크가 스스로 끈다** — 측정 종료·맥 꺼짐·USB 분리를 한
  곳에서 처리한다. **감지가 멈추면 불도 꺼진다.**

**③ 상태를 클라우드로 보낸다.** 바뀔 때 즉시, 아니면 **60초마다**. 엔진 안의 별도
스레드가 HTTP 를 맡아 0.3초 판단을 막지 않는다.

## 클라우드 쪽이 하는 일

```text
POST /api/state  ──▶  EC2 (cloud/server.py 한 파일)
  {state, since, led, rx}        · 요청 자체가 생존 신호
                                 · 응답에 설정을 실어 돌려준다
                                 · 30초마다 알림 검사
                                 · 180초 안 오면 "끊김"
```

**이 요청 하나가 세 가지를 동시에 한다** — 상태 보고 · 생존 신호 · 설정 내려받기.
따로 만들지 않았다.

**알림 네 가지**

| 종류 | 언제 |
|---|---|
| 응급 | 사람이 있는데 너무 오래 가만히 있을 때 (기본 60분) |
| 침입 | 외출 모드인데 움직임이 잡힐 때 |
| 끊김 | 집 기기 신호가 180초 이상 없을 때 |
| 나만의 상황 | 사용자가 만든 규칙 (예: "밤에 집에 안 들어옴") |

**수면 시간 규칙이 중요하다.** 응급 시계는 수면 동안 **멈췄다가 수면이 끝난 시각부터
다시** 센다. 23:50 에 쓰러져도 **07:00 + N분**에 알림이 간다 — 자는 사람에게 응급
문자를 보내지 않으면서, 아침 안부 확인이 된다.

**받는 사람** — 나에게 / 나에게 보내고 확인 없으면 지인에게 / 둘 다 동시에. 지인 번호는
**본인 동의 절차(인증 코드)** 를 거친 번호만 쓴다.

## 웹앱

반응형 한 페이지. 홈 화면은 **상태가 바뀌는 순간 서버가 밀어 준다(SSE)** — 예전에는
15초마다 전체를 새로 고쳐서 화면이 깜빡이고 애니메이션이 끊겼다.

## 기술 구성과 그 이유

| 항목 | 선택 | 왜 |
|---|---|---|
| 서버 | EC2 1대, `cloud/server.py` **한 파일** | 외부 의존성은 문자 발송 하나뿐 |
| 웹서버 | 표준 라이브러리 `http.server` | 제어판과 같은 방식 |
| DB | **SQLite** | 집 하나당 하루 ~1,500행. 포트도, 프로세스도, 백업 절차도 없다 |
| HTTPS | **Caddy** | 도메인만 적으면 인증서 자동. 서버는 `127.0.0.1` 에만 붙는다 |
| 상시 실행 | systemd | |
| 배포 | `rsync` + 재시작 | 저장소 clone 불필요 |

**보안은 한 줄로** — 비밀번호 scrypt, 기기 토큰은 **해시만** 저장, 문자 키는 환경 변수
(저장소에 없음), 하루 문자 상한 40건, 관리자 비밀번호가 없으면 `/admin` 은 404.
**그리고 가장 큰 대책은 영상이 없다는 것이다** — 다 유출돼도 나오는 건
`빈 방/정지/움직임` 과 시각뿐이다.

## 들어올 질문

- *"여러 사용자면 SQLite 안 되지 않나"* → **막히는 건 사용자 수가 아니라 서버가 한 대라는 점.**
  쓰기량으로는 집 1,000곳까지 여유(초당 17건). 상세는 QA Q13.
- *"왜 알림을 집에서 안 보내나"* → 위 "왜 이렇게 나눴나".
- *"집 기기가 꺼지면?"* → 180초면 끊김 알림. 그리고 불도 10초 뒤 자동으로 꺼진다.
